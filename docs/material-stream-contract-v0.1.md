# Контракт материальных соединений Gravia, v0.1

Дата: 11 сентября 2026 года. Статус: конкретный проект спецификации для реализации и обсуждения с владельцем. Нормативные формулировки ниже задают предлагаемое поведение v0.1; они не означают, что API уже реализован в приложении или официально сертифицирован по CAPE-OPEN.

**Уточнение статуса, 12 сентября 2026:** документ частично устарел и сохраняется как история предложения. Текущие OWN-11/12 задают единицы плагинов с подготовленным пересчётом Gravia и отдельные видимые ноды предметных преобразований. OWN-13–17 уточняют дерево контекстов/полей, предварительное описание и отделение конкретных условий от общего определения свойства. Поэтому обязательное SI в разделе 3, условия в `PropertyDefinition` и отдельные определения плотности по температуре в разделе 4, а также размещение предметных вычислений через `PropertyPlan` нельзя автоматически переносить в реализацию. Актуальная основа — [продукт](product.md#описание-потока-поля-и-значения) и [требования](requirements.md). Полный новый контракт пока не утверждён; арифметические формулы адаптеров ниже этим уточнением не пересматриваются.

## 1. Зафиксированные исходные условия

Используются предоставленные владельцем проверенные модели FCC и риформинга. FCC и его суррогат считаются взаимозаменяемыми реализациями с одинаковыми внешними входами и выходами. Особенности вызовов конкретного кода скрывает адаптер. Разработка новой химии, пересмотр пригодности моделей и замена их другой кинетикой в задачу интеграции не входят. По сообщению владельца, риформинг защищался в докторской работе.

Модель компаундирования ещё не разработана. Предварительный перечень её входов используется для проектирования расширяемого набора свойств; это не существующая функция, под которую требуется подгонять всю платформу.

## 2. Однозначное устройство соединения

Материальное ребро соединяет один выходной порт узла с одним входным портом. Оно передаёт неизменяемый результат `MaterialBatch`: одну или несколько независимых реализаций одного материального потока. Ребро не считает свойства и не изменяет расход.

У узла могут быть несколько продуктов с отдельными выходными портами. Многократное подключение одного выхода означает чтение того же результата, а не физическое разделение потока. Если материал распределяется между потребителями, нужен узел распределения либо явные доли отбора в модели-потребителе. Исполнитель проверяет сумму отборов при учёте материального баланса.

Один входной материальный порт имеет один источник. Несколько компонентов смешения подключаются к нескольким входным портам модели блендинга. Дополнительные входы этой модели можно создавать динамически.

При локальном выполнении передаётся ссылка на неизменяемый объект/буфер. При обращении к внешнему процессу сериализуется тот же контракт. GUI хранит идентификаторы рёбер, портов и результаты для просмотра; вычисления не пересылают числовые массивы через React.

### Состав MaterialBatch

| Поле | Смысл и обязательность |
| --- | --- |
| `contractVersion` | `gravia.material/0.1`; обязательное. |
| `runId`, `caseIds[B]` | Задание и устойчивые идентификаторы независимых расчётных точек. Порядок одинаков на всех соединениях данного пакета. |
| `streamId`, `materialId` | Идентификатор выходного потока и версия описания материала/продукта. Название для GUI не используется как ключ. |
| `status[B]`, `issues` | Успех или ошибка каждой точки; ошибка включает caseId, узел, код и данные для сообщения. |
| `massFlow[B]` | Массовый расход в kg/s. Обязателен для успешной строки материального потока. |
| `compositions[]` | Ноль или несколько представлений состава. Каждое с ID/version схемы, фиксированным порядком компонентов и матрицей массовых долей B×C. |
| `properties[]` | Колонки свойств: ID определения свойства, значения B, маска наличия B, ссылки на происхождение. |
| `origins` | Словарь версий моделей, паспортов, методов и входных зависимостей. Общие сведения передаются один раз, а не на каждую точку. |

Все числовые значения вычислительного контракта — float64. Это формат обмена; он не заставляет нейросеть менять внутреннюю float32-арифметику. Массив состава плоский, row-major: `values[row*C+component]`. Число B может быть равно 1. Для JSON отсутствующие значения представлены нулевым числом с маской false; NaN/Infinity запрещены. Маска, а не число, определяет наличие. В бинарном представлении допустим такой же validity bitmap.

Неуспешная строка сохраняет свой caseId; потребитель не использует её числовые значения. Исходная ошибка распространяется по зависимым узлам. Для нулевого массового расхода состав может быть неопределён; смешение пропускает нулевой поток. Узел, которому нужна температура или давление, требует их явно. Положительный поток для простого массового смешения не обязан содержать полный термодинамический flash-state.

Метаданные схематически:

```text
MaterialBatch
  massFlow [B]                     kg/s
  composition reforming.c5plus/v1 [B,32]  kg/kg
  property group.normalParaffins [B]     kg/kg
  property group.isoParaffins    [B]     kg/kg
  property density.liquid.293K   [B]     kg/m³
  property sulfur.mass          [B]     kg/kg
  origin model:reforming:<hash>, passport:unit-1:reformate:v3, ...
```

Инварианты сериализации: B≥1; caseIds уникальны в задании; status и massFlow имеют длину B; property values/present имеют длину B; composition values имеют длину B×C, present — B; originIds имеют длину 1 (общий источник) либо B. Все ссылки на propertyDefinition, compositionSchema и origin должны разрешаться в зафиксированном реестре задания. Наличие полного состава требует конечных неотрицательных долей с суммой 1 в заданном численном допуске. Допуск задаётся профилем адаптера и записывается в конфигурацию; перенормировка допустимого округления, если используется, должна быть явным преобразованием с origin. Реестр запрещает две противоречащие версии одного активного значения свойства.

Конкретные схемы FCC, риформинга и свойства бензинов поставляются модулями. Ядро знает структуры, размерности, идентификаторы и механизм разрешения свойств, но не знает индексов A6, кинетических уравнений или бензиновых корреляций.

## 3. Единицы и основы данных

Внутри вычислительного графа применяются SI-единицы. В интерфейсе разрешены °C, т/ч, кПа, проценты, ppm. Преобразование выполняется при вводе, импорте и вызове legacy-модели. Локаль RU/EN меняет формат отображения, а не значение в расчёте. [SI, BIPM](https://www.bipm.org/en/measurement-units/si-base-units).

| Величина | Единица в Gravia | Правило импорта |
| --- | --- | --- |
| Массовый расход | kg/s | т/ч ÷ 3,6; кг/ч ÷ 3600 |
| Масса / запас | kg | т × 1000; хранится в сценарии запасов, не вместо расхода |
| Мольный расход при обращении к модели | mol/s | кмоль/ч × 1000/3600 |
| Молярная масса в описании компонентов | kg/mol | кг/кмоль ÷ 1000 |
| Температура | K | °C + 273,15 |
| Давление | Pa, абсолютное | кПа × 1000; bar(a) × 100000; для избыточного давления ещё требуется абсолютное опорное давление |
| Время | s | мин × 60; ч × 3600 |
| Масса катализатора | kg | Не является временем, даже если независимая переменная названа t |
| Плотность | kg/m³ | г/мл или г/см³ × 1000; температура и состояние входят в определение свойства |
| Массовая доля | kg/kg, число 0…1 | масс.% ÷ 100; ppm mass или mg/kg × 10⁻⁶ |
| Мольная доля на границе модели | mol/mol, число 0…1 | мол.% ÷ 100 |
| Объёмная доля свойства | m³/m³, число 0…1 | об.% ÷ 100; опорная температура обязательна |
| RON, MON | 1, числовая шкала октанового числа | 95 остаётся 95, не 0,95 |
| T10/T50/T90/T95 | K | °C + 273,15; метод перегонки и основа recovered/evaporated — часть определения |
| Стоимость | единица валюты/kg | цена за т ÷ 1000; валюта и дата/сценарий фиксируются отдельно |

Основной состав в межузловом контракте — массовый. Мольные входы риформинга преобразует его адаптер. Внутренние величины модели могут оставаться в исходных единицах: переписывать её численные константы не требуется.

Массовая и объёмная доли не считаются одинаковыми даже при совпадении численного масштаба. `benzene.mass` и `benzene.volume@293.15K` — разные свойства. Если паспорт содержит только второе, для первого нужен явно выбранный метод пересчёта с необходимыми плотностями; повторно пометить тот же показатель как массовый запрещено. `ppm` без основы импортер просит уточнить один раз при настройке источника.

## 4. Определения свойств, а не произвольные названия колонок

Реестр `PropertyDefinition` содержит ID/version, размерность, каноническую единицу, basis, опорные условия, метод определения и форму значения. Смысл свойства одинаков для всех узлов. Идентификатор метода измерения определяет измеряемую величину; версия вычислительной корреляции хранится в происхождении.

Начальный набор бензинового модуля:

| ID (предлагаемые имена v0.1) | Семантика |
| --- | --- |
| `temperature`, `pressure` | Текущее состояние выбранного потока; K, Pa absolute. |
| `group.normalParaffins.mass`, `group.isoParaffins.mass`, `group.olefins.mass`, `group.naphthenes.mass`, `group.aromatics.mass` | P/I/O/N/A как доли от массы всего передаваемого продукта. P не включает I. |
| `benzene.mass`, `sulfur.mass`, `oxygen.mass`, `isobutane.mass` | Доли соответствующего вещества/элемента от массы всего продукта. Бензол входит в ароматику и не добавляется к ней повторно. |
| `density.liquid@293.15K` | Плотность жидкости при 20 °C в kg/m³; условия/метод зафиксированы определением. Значение при 15 °C получает другой ID. |
| `vaporPressure.reid` | ДНП по принятому определению Reid, Pa; не произвольное давление насыщенного пара при температуре реактора. |
| `octane.research`, `octane.motor` | ИОЧ/МОЧ как целевые величины; происхождение различает лабораторное значение и оценку модели. |
| `distillation.D86.volumeRecovered.T10`, `T50`, `T90`, `T95` | Отдельные зарегистрированные скалярные свойства температуры при заданном восстановленном объёме. Если выбран иной метод, используются другие ID. |

Для общего продукта с оксигенатами сумма пяти PIONA-долей может быть меньше 1. Пример: 90% углеводородного бензина + 10% MTBE → сумма углеводородных групп 0,9. Её нельзя принудительно нормировать к 1 и потерять оксигенат. Полная композиция с MTBE и частичные дескрипторы PIONA — разные структуры. `oxygen.mass` перекрывается с массой кислородсодержащих веществ, а не является шестой непересекающейся PIONA-группой.

Типы оксигенатов задаются компонентами/дескрипторами материала (`MTBE`, `ethanol` и т. п.), а не кодируются числами в поле массовой доли. Схема полного состава декларирует полноту; частичный паспорт не выдаётся за полный компонентный анализ.

## 5. Откуда берутся свойства: исполнимый план

Каждый выходной порт имеет `PropertyPlan`, составленный до запуска. Для каждого востребованного свойства назначен ровно один активный поставщик:

1. результат выбранной модели;
2. детерминированное преобразование её выходов;
3. выбранная корреляция/модель свойства;
4. значение паспорта конкретного продукта установки;
5. явно заданное допущение/константа сценария.

Список выше — способы поставки, не алгоритм скрытого переключения источников. Начальная конфигурация выбирает модельное значение, если оно предоставлено; иначе известное преобразование; иначе паспорт. Корреляцию вместо паспорта пользователь или конфигурация модуля назначает явно. При наличии нескольких паспортов требуется выбранная версия, а не «последний попавшийся» файл. После компиляции графа выбор фиксирован.

Паспорт привязан к установке, продукту, версии и области применимости: сырьё/режим/дата/партия, насколько эти сведения известны. «Паспорт установки» в программе означает пакет паспортов её выходных продуктов. Содержание серы сырья нельзя автоматически наследовать продукту реактора: план должен ссылаться именно на продукт либо на модель переноса серы.

`Origin` содержит kind, sourceId/version/hash, время/идентификатор анализа при наличии, ID метода и входных зависимостей, область применимости. Неизвестная погрешность хранится как неизвестная, а не как нулевая. При ручном допущении хранится его текст и значение.

Если паспортное свойство фиксировано, оно остаётся фиксированным на всех точках оптимизации: это часть постановки. Выход за заявленную область источника даёт `OutsidePropertyDomain`; молчаливой подмены корреляцией нет. Если источник не задаёт область, отчёт явно говорит «не задана» и показывает принятую область сценария. Сходимость оптимизатора не доказывает точность постоянного паспортного свойства при изменении режима.

Вызов потребителя происходит после выполнения PropertyPlan для всех его обязательных свойств. Отсутствие обязательного источника обнаруживается до оптимизации; ошибка вычисления свойства в отдельной точке помечает только эту точку. Необязательные свойства могут отсутствовать. Добавление нового свойства не меняет структуру MaterialBatch или существующие связи.

В GUI план доступен в инспекторе продукта: «PIONA — FCC», «сера — паспорт №…», «плотность — корреляция …». Создавать отдельную ноду на каждое свойство не нужно. Самостоятельная модель свойств может быть видимым узлом, когда этого требует сценарий.

## 6. Адаптер FCC и суррогата

Обе реализации предоставляют один внешний контракт и одну схему портов. Переключение реализации не меняет соединения и PropertyPlan, кроме origin/modelVersion.

Уточнение владельца от 11 сентября 2026 года: Gravia передаёт запрос к режиму расчёта (включая максимальную точность), а модуль сам выбирает внутренний способ выполнения. Эта спецификация материальных данных не назначает ядру переключение между FCC и суррогатом. Согласованная граница ответственности и открытые детали API описаны в [продукте](product.md#управление-точностью-расчёта).

Входной порт `feed`: массовый расход + согласованный состав FCC. Параметры узла: температура K, время контакта s, конфигурация катализатора. Адаптер передаёт выбранной реализации °C (`K−273.15`), секунды и исходные массовые доли. Массовый расход не участвует в предоставленной нормированной кинетике: он масштабирует количество продуктов. Все подготовительные действия predictor остаются внутри адаптера, не на рёбрах.

Модель возвращает доли 16 групп общего продукта. Адаптер формирует пять выходных портов:

| Порт | Индексы/имена групп |
| --- | --- |
| `gasoline` | Nl, nPl, iPl, Ol, Al |
| `lco` | Nm, Pm, Om, Am |
| `gas` | DG, PPF, BBF |
| `coke` | Coke |
| `heavyResidue` | Nh, Ph, Ah |

Для любой группы продукта S: `yieldS = Σw[i]`, `massFlowS = massFlowFeed × yieldS`, `compositionS[i] = w[i]/yieldS`. Доли нормируются только внутри выбранного продукта. Нулевой выход означает нулевой расход и неопределённый состав. Все пять продуктов участвуют в балансе; неподключённые выходы остаются в отчёте, не исчезают.

Для бензина порядок P/I/O/N/A соответствует nPl/iPl/Ol/Nl/Al. Из этого получается групповой состав на массовой основе. Бензол, сера, плотность, ДНП и перегонка берутся из PropertyPlan. Подключение бензина FCC к смешению работает даже при полностью паспортных недостающих свойствах.

Разделение на пять продуктов следует определению групп существующей модели, а не вводит новую модель промышленной ректификации. Вычисленная в FCC температура используется как режим модели; свойства жидкости при 20 °C и состояние стабилизированного продукта не приравниваются к температуре реактора.

## 7. Адаптер риформинга

Входной порт `feed`: уже подготовленная смесь углеводородов и H2 в схеме 38 компонентов, массовый расход kg/s и полный массовый состав. Для прямого использования исходных данных есть импортёр `x0.txt + F0.txt`; он один раз переводит их в этот формат. Отдельные потоки водорода и сырья можно объединить узлом подготовки входа, но сама модель получает прежнюю смесь.

Имена/порядок компонентов берутся из версии описания модуля, соответствующей существующей модели. Внутренние коэффициенты и механизм не меняются.

### Точные формулы входа

Пусть `q` — kg/s, `w[i]` — kg/kg, `M[i]` — kg/mol. Тогда:

```text
n[i] = q * w[i] / M[i]                 mol/s
nTotal = sum(n[i])                     mol/s
x0[i] = n[i] / nTotal                  mol/mol
F0 = nTotal * 3.6                      kmol/h
TT[j] = reactorTemperatureK[j] - 273.15 °C
Period[j] = sum(catalystMassKg[0..j])   kg
```

Для штатных `Period=[3220,10700,29320]` индивидуальные загрузки равны `[3220,7480,18620]` kg. Это накопленные координаты решателя по массе катализатора. Значение не конвертируется в секунды. Основание: конкретный раздел «Описание файлов» задаёт Period в kg и KK0 в kmol/(h·kg catalyst), что согласуется с расходом состояния kmol/h. Ранее прочитанные общие пояснения со словом «время» не используются для единицы параметра.

### Выход

Адаптер получает конечное состояние модели до прореживания текстового экспорта. Для компонентных расходов `F[i]` в kmol/h и `MM[i]` в kg/kmol:

```text
componentMassFlow[i] = F[i] * MM[i] / 3600   kg/s
```

Порт `reformate`: сумма X6…X37; полный массовый состав этих 32 групп нормируется на их общий расход. Порт `offgas`: X1…X5 и X38, с собственным нормированным составом. Это те же границы продукта C5+, что в исходном коде.

Расход риформата считается по компонентным расходам, а не восстановлением из `YIELD_rif`: знаменатель относительного выхода в исходном коде имеет собственное определение. Показатель исходной модели сохраняется отдельно как её KPI.

P/I — NP/IP C5…C11; N — ACH+ACP; A — A6…A11. Бензол — A6 в согласованной схеме модели (отдельное отображение версии модуля). Олефины для данной модели: явно зарегистрированное допущение «не представлены в механизме, O=0 в этом приближении». Его можно заменить паспортным значением в PropertyPlan без изменения адаптера.

`ONRM_rif` публикуется как модельная оценка `octane.research`; `octane.motor` имеет отдельный источник. Плотность может поступать из паспорта. Допустимый первоначальный расчёт по компонентным плотностям: `rho = 1 / Σ(w[i]/rho[i])` при одной опорной температуре и допущении аддитивности объёмов. В origin указывается этот метод и допущение. Это дополнительная модель свойства, не «точная термодинамика» от наличия таблицы DN.

У входного порта блендинга будет `InputRequirement`: список необходимых propertyId и, при необходимости, схема состава. Пока модель не разработана, перечень можно изменять без изменения транспорта. Полезный первый профиль входа — расход, PIONA, бензол, сера, плотность, ДНП, заданные точки перегонки, кислород и сведения об оксигенатах. Цена и доступность поступают из сценария ресурсов.

Внутренние переменные рецептуры предлагается вести по массе. Объёмные рецепты импортируются через плотности при одной температуре: `massFraction[i] = volumeShare[i]*rho[i] / Σ(volumeShare[j]*rho[j])`, когда volumeShare относится к объёмам дозируемых компонентов. Это не утверждение аддитивности конечного объёма смеси. Модель конечных свойств смеси разрабатывается отдельно.

## 9. Выполнение графа и обновления

1. При соединении проверяются тип порта и доступность схемы/преобразователя. Произвольного преобразования FCC-16 в reforming-38 нет. Подключение к общим свойствам блендинга не требует такой реконструкции.
2. При подготовке задания компилируются зависимости моделей и PropertyPlan. Для каждого обязательного свойства существует один вычислитель/источник. Циклы зависимостей свойств отклоняются. Обычное ребро не становится скрытым решателем рецикла.
3. Снимок задания фиксирует граф, реализации моделей, параметры, паспорта, источники свойств и их версии.
4. Выполняется модель; адаптер формирует продукты; выполняются требуемые преобразования/свойства; результат становится неизменяемым и передаётся потребителям.
5. Изменение режима инвалидирует модельный результат и зависимые свойства; изменение паспорта — зависящие от него свойства/потребителей. Ключ кэша включает все фактические зависимости и версии, а не только температуру и имя модели.

Пакетная операция и одиночный стандартный вызов используют одни определения материалов и единиц. Пакетный суррогат сохраняет векторный инференс. Автоматический внешний параллелизм этим контрактом не вводится.

## 10. Граница CAPE-OPEN

Смысл материального объекта, состава, потоков, свойств и единиц берётся из [Thermodynamics v1.1](https://www.colan.org/wp-content/uploads/2015/05/CO_Thermo_1.1_Specification_311.pdf). Отображение в адаптере: temperature/pressure → соответствующие свойства; massFlow → totalFlow с mass-basis; полная компонентная композиция → fraction с mass-basis и согласованным compound list.

Нефтяные свойства, имеющие соответствующее определение, отображаются в [Petroleum Fractions](https://www.colan.org/wp-content/uploads/2017/10/Petroleum_Fractions_Interface_Specification.pdf): RON, MON, ReidVaporPressure и т. п. Наши provenance, паспорта, caseIds, пакетные колонки и идентификаторы кривых — расширения Gravia. Они не выдаются за стандартные поля CAPE-OPEN.

Полная двоичная совместимость реализуется отдельным мостом `ICapeUnit`/Material Object. Частичная композиция PIONA не подменяет полный термодинамический compound list. Перед стандартным вызовом адаптер получает требуемые T/P, компоненты и термодинамические службы. Обязательства [Unit Operation](https://www.colan.org/wp-content/uploads/2016/05/CO_Unit_Operations_v6.25.pdf) исполняются в мосте, включая необходимое состояние выходов. Существование внутреннего контракта не является заявлением уже работающей двоичной совместимости.

Выбор JSON/MessagePack/Arrow не меняет этот контракт. Для первого адаптера допустим JSON с колоночными массивами; его производительность должна измеряться на нужных B. Внутри C# сериализация между нодами не нужна. Ни конкретный IPC, ни обязательная Windows-зависимость здесь не вводятся.

## 11. Проверки реализации и материал для научной работы

Критерии можно реализовывать одновременно с адаптерами:

- Преобразования °C↔K, kmol/h↔mol/s, mass↔mole проходят контрольные примеры и обратное преобразование.
- Формирование продуктовых потоков сохраняет сумму компонентных расходов. Численный допуск химической модели и допуск арифметического адаптера различаются; адаптер не маскирует невязку кинетики нормированием всего процесса.
- Состав каждого ненулевого продукта согласован с его расходом. Агрегация PIONA соответствует именам/индексам версии модели.
- Batch из B точек совпадает с B одиночными вызовами по установленным допускам; ошибки не переставляют строки.
- Изменение источника или паспортной величины отражается в origin и инвалидирует зависимый результат. Ошибка корреляции не вызывает скрытый переход на паспорт.
- Недостающие обязательные свойства выявляются до вычислений; отдельное нулевое значение отличается от отсутствующего.
- Интегрированный вызов совпадает с исходной проверенной моделью на контрольных режимах. Это проверка адаптера, не повторная защита кинетики.

В статье описываются уровни: проверенная кинетика → адаптер состава/единиц → получение свойств → модель смешения/оптимизация. Для каждого дополнительного свойства указываются источник, метод, область применимости и известная погрешность. При постоянных паспортных свойствах выводы об оптимуме условны относительно этих значений; влияние существенных неопределённостей проверяется чувствительностью/сценариями. Такой подход согласуется с разделением входных величин и производных результатов при [оценивании неопределённости NIST](https://www.nist.gov/publications/evaluating-expressing-and-propagating-measurement-uncertainty-nist-reference-materials).

В `researches/material-contract-v0.1` сохранены C#-структуры, арифметические преобразования и исполняемые проверки. Это эталонный пример предложенного контракта, не готовый runtime Gravia и не изменение предоставленных моделей.
