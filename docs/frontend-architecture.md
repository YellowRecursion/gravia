# Архитектура фронтенда Gravia Lab

Дата: 13 сентября 2026. Статус: **FSD выбран владельцем к реализации** после
обсуждения вариантов. Каркас и проверка импортов реализованы; предметные экраны,
рабочий документ и история редактирования пока не реализованы.

## Сценарий и основание выбора

Пользователь выделяет ноду, инспектор показывает её параметры. Изменённое значение
передаётся Host; C# проверяет бизнес-правила, интерфейс отображает подтверждённый
результат либо ошибку поля. Код выделения, панели, действия и связи с API имеет
разных владельцев — изменение инспектора не должно требовать доступа к внутренностям
холста или создавать второй источник параметров ноды.

Сравнивались два подхода:

- Общие components/hooks/services: меньше стартовых соглашений, но один сценарий
  разнесён по техническим каталогам; допустимые связи между функциями не определены.
- FSD: стандартная терминология, слайсы по назначению, направленные зависимости и
  публичные точки входа. Для кода, который преимущественно пишет LLM, выбран этот
  вариант: соглашения можно проверять ESLint, а не только помнить из переписки.

Это организация клиентского кода, не перенос Clean Architecture и C# Domain в TS.
Новые UI-тестовые фреймворки не устанавливаются: UX проверяет владелец. Проверки
архитектурных ограничений — технические Node-тесты, не тестирование дизайна.

## Слои и обязанности

| Слой | Зачем нужен в Gravia | Примеры, не созданные заранее |
| --- | --- | --- |
| app | Запуск и сборка всего приложения | Провайдеры, корневой UI, общие стили |
| pages | Композиция целого экрана и связь его крупных частей | Экран редактора |
| widgets | Самостоятельные крупные блоки сложного экрана | Холст схемы, инспектор, журнал |
| features | Значимые действия пользователя, переиспользуемая логика взаимодействия | Открыть проект, изменить параметры, запустить расчёт |
| entities | Общие клиентские представления предметных понятий | Представление проекта, данные запуска |
| shared | Непредметные средства, общие для остальных слоёв | Клиент API, UI-примитивы, локализация |

Не каждая кнопка — feature, не каждая панель автоматически — widget. Непереиспользуемый
код остаётся рядом с владельцем; выделение нового слайса должно решать конкретную
задачу. Не добавлять глобальные свалки utils/services/hooks и слои «на всякий случай».

Реальные каталоги сейчас:

```text
renderer/
  index.html
  tsconfig.json
  app/
    entrypoint/main.tsx
    providers/AppProviders.tsx
    ui/App.tsx
    styles/global.css
  shared/
    i18n/
      index.ts
      initialize.ts
```

Pages/widgets/features/entities появятся с настоящими задачами. Тестовые примеры
слоёв находятся исключительно в tests/fixtures и не входят в renderer/поставку.
Orval настроен на shared/api/generated; каталог появится при первом настоящем API.

## Импорты и публичные интерфейсы

Порядок зависимостей: `app → pages → widgets → features → entities → shared`.
Можно пропускать слои, но нельзя импортировать вверх. Слайсы одного слоя не
импортируют друг друга; их взаимодействие собирается выше. Типы, реэкспорты и
ленивая загрузка подчиняются тем же ограничениям.

- Между слайсами — только через корневой `index.ts` или `index.tsx` с именованными
  экспортами. Не создавать общий barrel для целого слоя: features/index.ts и т. п.
- Внутри слайса — относительные прямые импорты; не импортировать собственный index
  обратно из внутренних файлов, чтобы не создавать циклы.
- App — единый композиционный слой, его сегменты могут зависеть друг от друга.
- Shared не содержит предметных слайсов. В нашем каркасе его сегменты api/ui/lib/
  config/i18n могут использовать друг друга через свои index. Их внутренности
  скрыты от остальных сегментов и верхних слоёв. Это локальное уточнение FSD.
- Новый shared-сегмент или отдельные публичные точки входа для выросшей UI-библиотеки
  сначала обсуждаются; не обходить действующую политику глубокими импортами.
- FSD допускает специальные cross-import API сущностей (@x), но в Gravia они пока
  не разрешены. Если действительно потребуются, пересмотреть границу с владельцем.
- Алиас `@/` указывает в renderer и одинаково настроен в TS, Vite и ESLint.

```ts
// В widgets/inspector: допустимо, когда такой feature существует.
import { EditNodeParameters } from '@/features/edit-node-parameters';

// Недопустимо даже для import type или относительного пути.
import { useDraft } from '@/features/edit-node-parameters/model/useDraft';
```

Renderer не импортирует Node/Electron или исходники shell. Shell не содержит
предметных правил. Импорты должны быть статически анализируемыми: require,
вычисляемый import и import.meta.glob в renderer запрещены. Новую схему загрузки
расширений нельзя вводить обходом линтера.

## Владение состоянием и контрактами

| Данные | Владелец на клиенте | Ограничение |
| --- | --- | --- |
| Ответы API, загрузка и обновление серверных данных | TanStack Query; предметные query-функции рядом с владельцем | Не зеркалить кеш в Zustand |
| Выделение, активный инструмент, общее UI-состояние | Zustand внутри соответствующего слайса | Не один глобальный store всей программы; жизненный цикл связан с UI-сессией |
| Ввод и временное состояние одной формы | Сама форма/React | Не распространять локальный draft без необходимости |
| Производные значения | Вычисление/селектор | Не сохранять второй синхронизируемый экземпляр |
| Рабочий документ, несохранённые изменения, undo/redo | **Решение отложено** | Не реализовывать скрыто как копию Query или React Flow JSON |

При добавлении состояния явно указать его источник, область жизни, момент сброса
и способ обновления. Для выделения хранить ID, а не копию выбранной ноды. При смене
проекта нельзя сохранять его выделение/ошибки/черновики в общей сессии случайно.

Бизнес-правила и окончательная предметная валидация — C#. Модуль модели предоставляет
контракт параметров/портов и выполняет свои вычисления; UI не угадывает физические
условия или совместимость по названиям. Пользователь принимает предметные решения.
Фронт отвечает за ввод, предварительные подсказки и понятное отображение отказа.

Данные API генерирует Orval. Код shared/api/generated не редактируется; наружу
shared/api экспортирует только необходимые имена. Не заводить вручную второй набор
DTO «на всякий случай»; UI-модель и преобразование вводятся при реальном отличии
представления. Генерация сама по себе не определяет обработку HTTP-ошибок и отмены.

React Flow используется в модуле холста, Dockview — в композиции рабочего места;
их API/типы не становятся общими предметными контрактами или форматом файла проекта.
Адаптеры и преобразования создаются в месте интеграции. Не оборачивать весь Ant ради
абстракции: собственные UI-компоненты нужны для повторяющегося поведения/оформления.

## Ошибки, язык и оформление

- Ошибки Host различаются по стабильному code и структуре ProblemDetails, не по
  тексту Message. Ожидаемый отказ показывается около действия/поля, а не как краш.
- Аномалии UI изолируются React error boundary в app/самостоятельной панели по мере
  их появления. Асинхронные ошибки запросов обрабатываются отдельно; error boundary
  не перехватывает любые Promise/event-handler ошибки автоматически.
- Технические сообщения не заменяют пользовательский результат. Будущий канал
  диагностики frontend→Host согласуется отдельно, не создаётся новый файловый лог.
- Язык и тема настраиваются централизованно и передаются библиотекам. Собственные
  строки локализуются; цвета опираются на токены. Текущий тёмный пустой фон не задаёт
  окончательный UX или поведение переключения тем.

## Автоматическая защита и проверка

`tooling/architecture.mjs` задаёт единую политику eslint-plugin-boundaries, которую
используют обычный lint и tests/architecture.test.mjs. TypeScript-resolver проверяет
реальный путь, поэтому относительный импорт или алиас не обходят границу. Неизвестные
слои/локальные зависимости запрещены. Сгенерированные файлы не линтятся, но импорт
их внутренностей снаружи shared/api по-прежнему запрещён.

`npm run build` включает lint и typecheck, поэтому обычный Run Host тоже проверяет
границы. Перед завершением изменения LLM обязана выполнить `npm run check` в Desktop.
После изменения запуска/ресурсов — сборку Host и существующий `npm run smoke`.

Это не доказательство правильного владения состоянием, отсутствия всех циклов или
корректности бизнес-логики: это проверяемые правила импортов плюс ручная оценка.
Не выключать правила и не добавлять исключения ради зелёной проверки. Изменение
политики сопровождается положительным и отрицательным тестом и согласованием.

До первого редактируемого документа нужно отдельно согласовать: владение черновиком,
ревизии/применение команд, сохранение, undo/redo и защиту от устаревших ответов Host.
UI-расширения плагинов и несколько окон могут потребовать нового решения о границах;
эта архитектура не объявляет их уже поддержанными.
