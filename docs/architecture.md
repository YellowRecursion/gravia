# Архитектура Gravia: предложение

Дата: 12 сентября 2026 года. **Статус: общая архитектура ниже остаётся предложением; реализованные и согласованные части отмечены отдельно.** В solution добавлены `Gravia.Domain`, `Gravia.Application`, `Gravia.Infrastructure`, `Gravia.Host` и отдельный xUnit-проект для каждого на .NET 10. Host теперь запускает локальный HTTP сервер и пустую Electron-оболочку `Gravia.Desktop` (npm-проект). Подключены MediatR, FluentValidation, журнал и обработка ошибок. Предметные сценарии пока не реализованы. `Gravia.Execution` не создавался; его выделение остаётся предложением, а не принятым решением.

Текущие ссылки каркаса: `Application → Domain`, `Infrastructure → Domain, Application`, `Host → Application, Infrastructure`; у Domain ссылок на другие проекты нет. Отсутствие Execution пока не означает переноса его предлагаемых обязанностей в другой слой.

Далее — краткая карта предлагаемой реализации. Сценарии, альтернативы, источники, устройство полей, плагины, жизненный цикл и критерии проверки — в [полном разборе](../researches/Архитектура%20Gravia%20и%20границы%20проектов.md).

## Реализованная пустая оболочка

По прямому запросу владельца Run у Gravia.Host открывает пустой Electron без первого
экрана. React, TypeScript, Vite и UI-библиотеки не установлены; архитектура фронтенда
будет обсуждаться отдельно. Host владеет процессом Electron, передаёт реальный адрес
локального HTTP сервера после запуска. Оба компонента завершаются совместно;
подробности и команды — [README Desktop](../src/Gravia.Desktop/README.md).
Это не начало реализации пользовательского проекта или плагинов.

## Доменные ошибки и клиенты

Web UI подтверждён владельцем; MCP остаётся возможным будущим клиентом. Оба должны
использовать одни сценарии Application без дублирования предметных правил.
Реализован `Domain/Common/DomainException`: стабильный `Code`, безопасный `Message`,
словарь `Extra` и необязательный `InnerException` для внутренней диагностики.
HTTP-статусов и зависимостей от транспорта в Domain нет.
Использование и границы реализации — [errors.md](errors.md).

## Реализованная регистрация и валидация

- `Application/DependencyInjection.cs`: `AddApplicationServices()` регистрирует обработчики MediatR и публичные валидаторы FluentValidation из сборки Application, а также `ValidationBehavior<,>`.
- `Infrastructure/DependencyInjection.cs`: `AddInfrastructureServices()` подключает заменяемый журнал в памяти и ILoggerProvider.
- `Host/DependencyInjection.cs`: `AddHostServices()` объединяет регистрации Application и Infrastructure. `Program` через DesktopHost создаёт WebApplication с этими регистрациями; Host слушает loopback и управляет Electron.
- Методы расширяют `IServiceCollection`: регистрация внутренних слоёв не требует конфигурации Host. У Domain нет DI-файла и зависимостей на MediatR или FluentValidation.

MediatR закреплён на **12.5.0** после обсуждения с владельцем, а не на новой 14.x: [лицензия выбранной версии — Apache-2.0](https://github.com/jbogard/MediatR/blob/v12.5.0/LICENSE). FluentValidation и его DI-расширение — **12.1.1**, [стабильный выпуск на дату подключения](https://www.nuget.org/packages/FluentValidation.DependencyInjectionExtensions/12.1.1). Обновление MediatR на новую основную версию не считается автоматическим решением.

Валидаторы scoped и запускаются через `ValidateAsync` последовательно, поскольку могут разделять scoped-зависимости, не поддерживающие параллельное использование. Ошибки всех валидаторов собираются в `ValidationException`; при ошибке или отмене обработчик не запускается. Запросы без валидаторов передаются обработчику. Предметные инварианты остаются в Domain. Правила конкретных команд пока не созданы.

Логирование предоставляет Generic Host; отдельные logging/performance behaviors не добавлены. Pipeline не подавляет исключения обработчиков. В Host зарегистрирован ExceptionHandler с общей классификацией ошибок; HostProcess подключён в Main как внешняя граница awaited-жизненного цикла приложения с bootstrap-диагностикой. HTTP middleware переводит ошибки в ProblemDetails; MCP-адаптера нет. Границы и ограничения — в [errors.md](errors.md), проверки — в [tests/README.md](../tests/README.md).

По последним указаниям владельца реализован [заменяемый журнал в памяти](diagnostics.md): ILogJournal/DTO в Application, ограниченный буфер и ILoggerProvider в Infrastructure, регистрация/настройки в Host. Файлов нет; механизм не знает о моделировании/оптимизации. Актуальные проблемы схемы, вычислительные итоги, UI и SDK остаются отдельными будущими частями.

## Общая форма

Один локальный backend с явными границами библиотек. Desktop — клиент backend. Python-модели подключаются через адаптер и SDK. Разделение C#-проектов не означает разделение на процессы.

| Проект | Отвечает за |
| --- | --- |
| `Gravia.Domain` | Предметный проект пользователя: схема, ноды, связи, описание потоков/полей, свойства, единицы, условия, правила совместимости, постановка исследования. |
| `Gravia.Application` | Действия пользователя: открытие и редактирование проекта, сопоставления, ревизии, запуск/отмена, просмотр результатов, управление расширениями через интерфейсы. |
| `Gravia.Execution` | Зафиксированный снимок вычисления, подготовка и выполнение плана, пакетные данные, конверсии, статусы и вызов исполнителей нод. |
| `Gravia.Infrastructure` | Реализации внешних механизмов: файлы, каталоги пакетов, Python-окружения/workers, IPC, адаптер библиотеки единиц. |
| `Gravia.Host` | Исполняемый backend: сборка зависимостей, API для desktop, время жизни приложения. |

Все, кроме Host, — Class Library. Первым предметным проектом предлагается `Gravia.Domain`; самостоятельные `Core`, `Engine`, `Modeling.Domain` одновременно с этой схемой не нужны.

## Правило зависимостей

Разрешённые прямые ссылки между этими пятью C#-проектами:

```text
Domain          → ничего
Execution       → Domain
Application     → Domain, Execution
Infrastructure  → Domain, Execution, Application
Host            → Application, Infrastructure
```

Интерфейс объявляет сторона, которой нужна операция. Например, `INodeSession` принадлежит Execution, а Python-адаптер из Infrastructure его реализует. Domain и Execution не знают типов Python, GUI, файлового формата или RPC.

Внутри проектов код группируется по задачам. DDD применяется к предметным понятиям и инвариантам; каждую техническую папку не объявляем отдельным bounded context. Команды и read DTO разделены на уровне Application. Undo/redo проектируется отдельно; Event Sourcing и отдельные БД из этого не следуют. Численный цикл работает непосредственно с Execution-сессией.

## Четыре частых вопроса

| Вопрос | Ответ |
| --- | --- |
| Где проект пользователя? | Его предметная модель — Domain; открытая сессия и история — Application; формат и запись файла — Infrastructure. |
| Где единицы и конвертеры? | Описания и предметные правила — Domain; подготовка/применение численного перехода — Execution; конкретная библиотека — за адаптером Infrastructure. |
| Где rho20 → rho15? | Отдельная видимая нода. Метод предоставляет расширение, пользователь выбирает и настраивает его. |
| Где Python-плагин? | Отдельный пакет с описанием и Python-кодом; SDK обслуживает протокол. Infrastructure подключает его к интерфейсу Execution. |

Проект, снимок запуска и результаты — разные объекты. Изменение схемы не меняет уже запущенный расчёт. Результат содержит ссылку на использованные описания и условия, а не получает их из текущего редактора.

## Внешние контракты и SDK

- `contracts/plugin` — семантика и протокол расширений, общие контрольные примеры.
- `sdk/python` — описание модели, удобный API вычисления и worker.
- `sdk/dotnet` — появляется вместе с первым внешним C#-плагином.
- `contracts/desktop` — API нашего интерфейса к backend.
- `apps/desktop` — клиентский проект; точный GUI-стек ещё требует согласования.

Внутренняя Domain-библиотека не является публичным контрактом SDK. Плагин может добавлять типы нод, определения и вычисления через поддержанный контракт, но не получает доступ к контейнеру сервисов и изменяемому проекту пользователя.

## Порядок проверки

1. Описания двух портов, сопоставление полей, переименование, единицы и несовпадающие условия.
2. Независимый снимок и пакетный расчёт на тестовых C#-исполнителях.
3. Тот же сценарий через Python SDK с проверкой экземпляров, ошибок и завершения процесса.
4. Команды редактора, сохранение/открытие и минимальный desktop.
5. Реальный FCC/суррогат, численное сравнение и измерение накладных расходов.

До реализации соответствующих частей остаются отдельные решения: динамические условия и структурные настройки, необходимость рециклов в первом сценарии, API режимов, библиотека единиц, runtime/окружения, транспорт и формат хранения. Их варианты и влияние на границы описаны в полном разборе. Прежние обещания об обязательном gRPC, shared memory или общем worker для совместимых плагинов не считаются утверждёнными.
