# Доменные исключения

Дата: 2026-09-12. Статус: согласовано владельцем; DomainException, классификация
ошибок и внешняя граница обработки Host реализованы и проверены.
При подключении пустой Electron-оболочки добавлены локальный HTTP Host и middleware
перевода ошибок в ProblemDetails. Предметного HTTP API, экранов и MCP пока нет.

## Сценарий и выбор

Пользователь пытается выполнить действие, нарушающее предметное правило. Domain
отклоняет действие; Application не превращает отказ в успех. Будущий адаптер передаёт
клиенту код причины и данные для отображения, например ID проблемного объекта.
Проверяемый результат: отказ имеет стабильный код и структурированные данные;
клиенту не нужно повторять правило или разбирать текст сообщения.

Самый простой вариант — обычное исключение с текстом. Он не даёт клиенту надёжной
идентификации причины. Выбран знакомый владельцу подход td-backend: конкретные
доменные исключения от общего DomainException с Code, Message и Extra. В отличие от
td-backend, HTTP Status отсутствует: web UI обязателен, а будущий MCP не должен
зависеть от HTTP-семантики. Отдельную универсальную Result-обёртку сейчас не вводим.

## Как использовать

Пример формы (не утверждённое правило Gravia и не готовый предметный класс):

```csharp
using Gravia.Domain.Common;

public sealed class ExampleRuleException : DomainException
{
    public ExampleRuleException(Guid nodeId)
        : base("example_rule_rejected", "The operation violates an example rule.")
    {
        Add("nodeId", nodeId);
    }
}
```

- Конкретный класс располагается рядом со своей предметной областью в Domain.
  Не создаём заранее исключения для ещё не определённых правил.
- Code — устойчивый ключ, не имя C#-класса и не переводимый текст. Рекомендуемый
  стиль собственных кодов — snake_case, ключей Extra — camelCase.
- Message — безопасное пояснение; клиент может локализовать сообщение по Code.
  Неизвестный код не должен ломать UI: нужен общий вариант отображения.
- Extra всегда доступен, без данных пуст. Add в конструкторе добавляет или заменяет
  ключ. Внешняя запись в словарь запрещена. Значения не копируются глубоко:
  передавать безопасные неизменяемые сериализуемые данные, не сущности, секреты,
  исключения или служебные объекты. Стабильность ключей и типов — часть контракта.
- InnerException предназначен только для диагностики. Не сериализовать Exception
  целиком и не отправлять клиенту произвольные Exception.Message/StackTrace.

## Границы обработки

Настройки (13 сентября 2026): IntSetting и DoubleSetting проверяют необязательные
включительные Min/Max; DoubleSetting принимает только конечные числа. StringSetting
проверяет необязательные включительные MinLength/MaxLength через string.Length
(UTF-16), не обрезает и не нормализует текст; null не допускается.
Неподходящее значение, включая default, отклоняется через InvalidSettingValueException
с кодом `setting_value_invalid` и Extra.settingId. Само введённое значение не включается
в ошибку. Default и обычное изменение используют одну проверку; при отказе текущее
значение не меняется. Противоречивые/отрицательные ограничения длины, Min > Max и
неконечные числовые границы — ошибки объявления настройки (ArgumentException),
а не штатный отказ пользователю. Конкретные настройки находятся в Domain/Settings/Entities;
привязка к app/project, сохранение и UI пока не реализованы.

ChoiceSetting хранит строковый ID выбранного SettingOption; вариант содержит ID и
LocalizedText Title. Список непустой, копируется с сохранением порядка и доступен
только для чтения. ID вариантов уникальны с учётом регистра; подписи могут совпадать.
Default и новое значение должны точно совпадать с ID одного из вариантов, иначе
возвращается тот же `setting_value_invalid` с Extra.settingId. Null/пустой список,
null-элемент и дубли ID — ошибки аргументов при объявлении настройки.

Зафиксировано владельцем: DomainException применяется **только к отказу по
бизнес-правилу**, а не как обёртка любого сбоя. У каждого конкретного доменного
исключения закрепляется постоянный код. Непредвиденное исключение не превращается
в штатную бизнес-ситуацию из-за того, что у него есть Message или InnerException.

| Исключение | Категория / код | Обработка |
| --- | --- | --- |
| DomainException | Domain / собственный Code | Безопасные Message и Extra; без технического Error-лога. |
| FluentValidation.ValidationException | Validation / validation_failed | Список Field/Code/Message; без AttemptedValue и CustomState, без Error-лога. |
| OperationCanceledException при отменённом токене текущей операции | Cancelled / operation_cancelled | Штатная отмена, без Error-лога. |
| Остальные, включая незапрошенную отмену и обёртку над доменным исключением | Internal / internal_error | Безопасное общее сообщение и TraceId; исключение — в техническом логе. |

Валидаторы должны задавать безопасные сообщения и устойчивые ErrorCode для
клиентской обработки; отсутствие кода заменяется на invalid_value. Автоматическое
удаление секретов из произвольного текста не обещается: ErrorMessage/Domain.Message
и Extra формирует доверенный код. Не использовать внутренние служебные коды
internal_error, validation_failed, operation_cancelled как коды предметных правил.

Domain определяет предметную причину, Application выполняет общий сценарий,
транспортный адаптер выбирает формат ответа и транспортный статус. Клиент выбирает
отображение и дальнейшее действие пользователя. Правила конкретной модели остаются
у плагина; этот внутренний C#-класс не становится межъязыковым контрактом SDK.

HTTP-адаптер подключён через HttpExceptionMiddleware: доменные отказы и валидация
возвращают 400, аномалии — 500, формат application/problem+json с code, traceId,
extra и errors. Для будущих предметных API при необходимости добавляется явное
соответствие кодов другим HTTP-статусам; Domain по-прежнему не хранит Status.
При разрыве запроса тело не отправляется; начатый ответ не переписывается.
MCP-ответы ещё не определены.
FluentValidation.ValidationException остаётся отдельной ошибкой проверки запроса.
Неизвестное исключение нельзя автоматически выдавать за ожидаемый доменный отказ.

Уточнение 13 сентября 2026: проверка выбранной папки и её паспорта в Create/Open
может завершиться ValidationException на границе IProjectStore: например, папка занята,
паспорт отсутствует/повреждён, версия не поддерживается или доступ запрещён.
Это проверка пригодности входных данных запроса, не бизнес-правило Domain.
Поле — directoryPath; стабильные коды и границы — [projects.md](projects.md).
Прочие I/O-сбои не преобразуются в ValidationException или DomainException.

Логирование не выполняется в DomainException или месте throw. Неожиданный сбой
логируется один раз на границе обработки; технические подробности остаются в журнале.
ExceptionLoggingBehavior не добавлен. Штатная отмена — не доменная ошибка.
Несходимость отдельной точки массового расчёта должна отражаться в результате точки,
а не требовать отдельного исключения или HTTP-ответа на каждую точку. Владелец
фонового запуска отвечает за его итоговый статус, независимо от запроса запуска.

## Текущее подключение

- `Host/Errors/ExceptionHandler` зарегистрирован singleton в AddHostServices.
  Возвращает ErrorDetails с категорией, кодом, сообщением, TraceId, Extra и Errors.
  Это внутренняя модель границы, не финальный JSON-контракт HTTP/MCP.
- TraceId берётся из текущей Activity, иначе создаётся. Только неожиданный сбой
  вызывает LogError; ответ не содержит сам Exception или его произвольный текст.
  Сбой сменного логгера не превращает исходную ошибку в успех и не раскрывает её.
- `Program.Main` вызывает HostProcess.RunAsync вокруг DesktopHost.RunAsync.
  Обработаны синхронные и awaited-ошибки построения, запуска, работы и освобождения
  ресурсов. DesktopHost владеет WebApplication и ElectronSession, завершает их
  перед выходом. Дополнительного Dispose в Program нет.
- Для этой последней границы используется отдельный bootstrap console logger:
  доступен до сборки DI и после освобождения Host. Технические сведения идут в
  stderr, файлы не создаются. Обработчик из DI использует обычные провайдеры Host,
  включая журнал в памяти; его использует HTTP middleware, он доступен будущим
  адаптерам и владельцам операций.
- Код процесса: 0 — успешное завершение или запрошенная отмена; 1 — обработанный
  отказ/сбой жизненного цикла Host. Даже ожидаемая доменная причина, помешавшая
  запустить Host, не означает успешный запуск. При отказе печатается код и TraceId.
- «Глобальный» здесь означает внешнюю границу **ожидаемой задачи Host**, не перехват
  любого исключения в CLR. Detached/fire-and-forget задачи и произвольные потоки
  сюда не попадают. OutOfMemoryException не подавляется: штатное восстановление
  при нехватке памяти не обещается. BackgroundService управляется Generic Host;
  его ошибка не обязана пробрасываться через RunAsync. Будущие расчётные задачи
  обязаны иметь собственную границу и явный итоговый статус.
- Сам обработчик пишет одну запись на один вызов для аномалии; не вызывать его
  повторно на каждом rethrow. Generic Host может дополнительно писать собственные
  сообщения lifecycle. Сквозного подавления дублей внутри фреймворка не добавлено.

## Основания и проверка

- Локальный образец: `C:/Projects/td-backend/Domain/Common/DomainException.cs` и
  `Web/Middlewares/ExceptionHandlingMiddleware.cs`, просмотрены 2026-09-12.
- [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html): машинно-читаемые HTTP-ошибки,
  расширения и отделение клиентского описания от внутренней диагностики. Это основание
  будущего HTTP-адаптера, не требование использовать HTTP внутри Domain.
- `dotnet test tests/Gravia.Domain.Tests --configuration Release` проверяет базовый
  контракт. Сериализация в тесте — пример проекции выбранных данных, не готовый API.
- [Microsoft: Generic Host](https://learn.microsoft.com/en-us/dotnet/core/extensions/generic-host)
  описывает построение, запуск, shutdown и обязанности Host; это не HTTP-конвейер.
- `dotnet test Gravia.slnx --configuration Release --no-restore`: 70 тестов прошли.
  `dotnet build Gravia.slnx --configuration Release --no-restore -warnaserror`:
  0 предупреждений и ошибок. Проверены классификация, безопасная проекция,
  корреляция единственной записи обработчика, отмена и ошибки логгера/вывода.
- Реальный `dotnet src/Gravia.Host/bin/Release/net10.0/Gravia.Host.dll
  --InMemoryLogging:CapacityBytes=0`: код завершения 1, internal_error и traceId
  в stderr; bootstrap-лог содержит ArgumentOutOfRangeException. В stdout
  технического исключения нет. Это намеренно некорректная конфигурация для проверки.
