# Диагностика и консоль Gravia

Дата: 12 сентября 2026 года. **Реализован заменяемый журнал в памяти**, без файлов и без знания о моделировании/оптимизации.
Последние решения владельца заменяют прежние предложения файлового хранения и выбора режима внутри логирования.
Панель desktop, HTTP API и SDK плагинов ещё не созданы; для их подключения предоставлен контракт чтения/записи.
История проектирования: [исследование](../researches/Диагностика%20и%20консоль%20Gravia.md).

## Использование сейчас

Код Application/Infrastructure/Host получает обычный `ILogger<T>` через DI:

```csharp
using Microsoft.Extensions.Logging;

using var scope = logger.BeginScope(new Dictionary<string, object?>
{
    ["RunId"] = runId,
    ["NodeId"] = nodeId
});
logger.LogWarning(new EventId(10, "ExampleWarning"),
    "Получено значение {Value}", value);
```

Имена свойств контекста не интерпретируются журналом: для него RunId/NodeId — такие же пары ключ/значение, как другие.
Контекст переносится через async scopes, строки копируются; исходные объекты и исключения не сохраняются в журнале.
Уровни и категории настраиваются стандартным `Logging` .NET; alias провайдера — `Gravia`.
Для вычисления дорогих аргументов дополнительно проверять `logger.IsEnabled(level)`: обычный C# вычисляет аргументы до вызова метода.
Категории должны быть стабильными (обычно ILogger<T>), не отдельными строками для каждого кандидата: стандартный ILoggerFactory кэширует категории вне кольцевого буфера. Динамические ID передаются через scope.
`LogError` не меняет состояние расчёта и не бросает исключение из-за уровня Error.

Доступ для клиента/будущего адаптера — `Gravia.Application.Logging.ILogJournal`:

```csharp
var page = journal.Read(new LogQuery
{
    AfterSequence = cursor,
    Limit = 100,
    MinimumLevel = LogLevel.Warning,
    Properties = new Dictionary<string, string?> { ["RunId"] = runId.ToString() }
});
// В UI: upsert строки по Sequence; продолжить с page.NextSequence.
var stats = journal.GetStatistics();
journal.Clear();
```

Есть фильтры уровня, точной категории, подстроки сообщения/исключения и свойств контекста.
Адаптер другого источника может вызвать `TryWrite(LogMessage)` напрямую. В таком случае фильтрацию до формирования сообщения выполняет адаптер; `ILogger`-фильтры не применяются к прямому вызову журнала.

## Гарантии и ограничения реализации

- По умолчанию выделен кольцевой `byte[]` на **16 MiB (16 777 216 байт)**. В квоту входят все сохранённые поля и 44 байта заголовка каждой строки. Никакого растущего словаря или очереди нет.
- Это лимит сохраняемого содержимого, **не всей RAM процесса**. Дополнительно есть один фиксированный scratch-буфер до MaxEntryBytes, временные объекты форматирования и отделённые результаты чтения. У вызывающего кода могут быть собственные большие строки/форматтеры; провайдер не может ограничить произвольный код formatter/ToString.
- Размеры задаются при запуске через `InMemoryLogging` в `src/Gravia.Host/appsettings.json`; настройки также переопределяются аргументами CLI и переменными окружения Generic Host. Файл читается из каталога приложения, а не зависит от рабочего каталога.
- MaxEntryBytes включает заголовок; при превышении данные последовательно сокращаются и выставляется IsTruncated. Ограничены число свойств, их имена/значения, категория, текст и сведения об исключении. Пределы могут усечь адресный контекст, поэтому усечённую запись нельзя считать полной диагностикой.
- Старые записи вытесняются целиком, независимо от уровня, включая Error. Есть счётчики Written/Evicted/Cleared/Rejected/Truncated. Гарантии вечного хранения ошибок нет.
- По умолчанию сворачиваются только **соседние полностью одинаковые записи**, включая контекст, код и уровень. Хранятся первый/последний момент, RepeatCount, стабильный Sequence и меняющийся LastSequence. Усечённые записи не сворачиваются, чтобы не объединить разные исходные сообщения с одинаковым обрезанным префиксом.
- Произвольная группировка повторов по всем кандидатам не реализована. Она не нужна для соблюдения объёма и не вносится в логгер как знание об оптимизации.
- Чтение порционное: максимум 500 возвращаемых строк и 256 KiB просматриваемых бинарных записей за порцию по умолчанию, до 2048 новых записей для фильтрации. Размер JSON будущего API и память UI требуют собственных ограничений.
- NextSequence продвигается и по отфильтрованным записям. HasMore требует продолжить чтение, даже если текущая страница пуста. Пропуск старых заголовков до курсора может быть линейным по числу сохранённых строк: это простой bounded buffer, не индексированная БД.
- HasGap означает, что часть более старой истории очищена/вытеснена. Новый JournalId после перезапуска требует сбросить курсор. Future cursor вызывает явную ошибку. Журнал не предоставляет exactly-once доставку через ещё не созданный IPC.
- Clear действительно очищает этот временный журнал для всех читателей, обнуляет сохранённый буфер и сохраняет монотонность курсора. Очистка только представления UI в будущем должна выполняться отдельным клиентским курсором. Результаты/проект/предметные проблемы Clear не затрагивает.
- После закрытия приложения история теряется. Файлы журналов, автоматическая телеметрия, результаты расчётов, актуальные проблемы схемы и локализация предметных сообщений не входят в реализованный модуль.
- Потокобезопасность обеспечивается короткой синхронизацией записи/чтения; форматирование пользовательского ILogger-состояния происходит до входа в журнал. Нет ожидания браузера, файловой записи и вызова MediatR на сообщение.

## Подключение и замена

- Application/Logging: интерфейс и DTO, зависимость только от стандартной logging abstraction.
- Infrastructure/Logging: InMemoryLogJournal, ILoggerProvider, настройки и регистрация.
- Infrastructure/DependencyInjection.cs подключает `AddInMemoryLogJournal()`.
- Host объединяет DI и связывает настройки. Domain не изменён и не зависит от логирования.
- Для замены достаточно зарегистрировать свой singleton `ILogJournal` **до** AddInfrastructureServices либо заменить дескриптор через DI до построения Host. Регистрация провайдера идемпотентна; отдельные реализации для нод/запусков не создаются.
- Низкоуровневое представление кольца — внутренний формат памяти, не публичный протокол SDK или файловый формат.

Основание адаптера: [Microsoft, custom logging provider](https://learn.microsoft.com/en-us/dotnet/core/extensions/logging/custom-provider).
Он использует стандартный механизм провайдеров/фильтров .NET, не вводит собственный диспетчер команд.

## Рекомендуемое решение

Одна панель диагностики с двумя представлениями: актуальные проблемы схемы и история сообщений.
Статусы и значимые замечания к результатам хранятся с результатами, а не вычисляются из логов.

- Автор плагина получает `context.Log.Info/Warning/Error`; контекст ноды/вызова задаёт платформа. Для значимых замечаний к численному результату предусмотрены структурированные `issues` результата.
- Неправильные входные данные выявляются до расчёта, если это возможно. Проверка привязана к ревизии; старый ответ не заменяет новый.
- `Log.Error` не означает автоматическую отмену. Failed одной точки, нарушение ограничения оптимизации, падение worker и отмена — разные исходы.
- Запись содержит устойчивый код, текст/аргументы, адрес объекта, контекст запуска и идентификатор. Переименование не ломает ссылку; исторические сообщения не притворяются диагностикой текущей ревизии.
- Повторы группируются. Сводка неуспешных кандидатов строится по результатам, а не по числу строк в консоли.
- «Очистить» очищает представление, не удаляет результаты или актуальные проблемы.
- Значимые замечания доступны после закрытия приложения и без установленного плагина. Не обещаем без потерь сохранять все произвольные Debug-сообщения.
- Обычные технические логи остаются на `ILogger<T>`. Не выводим автоматически весь системный журнал в пользовательскую панель.

## Режимы и объём журналов — уточнение 12 сентября

Владелец уточнил: моделирование запускает схему один раз, оптимизация — десятки/сотни тысяч раз; объём логов должен быть ограничен (16 МБ — пример значения).

- Моделирование: подробные Info/Warning/Error по нодам; Debug по запросу.
- Оптимизация: события исследования и сводки Warning/Error; внутренние Info/Debug по умолчанию выключены до сериализации. Подробности выбранной ноды/кандидата включаются явно.
- Предлагается единая дисковая квота автоматических журналов пользователя, например 16 MiB, а не отдельная квота каждому плагину/запуску. Старые записи вытесняются. Размер проверяется до записи с учётом UTF-8 и метаданных; простого Collapse недостаточно.
- Очереди RAM, группы, SDK-буферы и UI ограничиваются отдельно. Жёсткий размер дискового журнала не является гарантией такого же потребления RAM.
- Все произвольные логи навсегда не сохраняются. Статусы/необходимые обстоятельства результатов хранятся отдельно и компактно; полные логи нельзя прятать туда для обхода квоты.

Полный механизм, сравнение с исходниками Unity/Serilog и граничные проверки — в §13 полного разбора. Предыдущие 16 MiB только для live-буфера не обеспечивали общий предел.

## Границы компонентов

| Где | Что |
| --- | --- |
| Domain | Предметные причины отказа; без логгера и DI |
| Application/Diagnostics | Контракт записей и журнала, контекст и операции пользовательской диагностики |
| Infrastructure/Diagnostics | Ограниченные буферы, хранение, выборка; приём сообщений плагинов через их адаптеры |
| Host | Регистрация через DependencyInjection.cs, API чтения и обновлений |
| Web/desktop | Список, фильтры, подробности, переход к ноде/полю/результату |

Новый C#-проект не нужен. Каждое сообщение не проходит через MediatR.
Формат хранения и транспорт остаются открытыми; для первого UI достаточно порционного чтения после курсора.
