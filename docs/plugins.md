# Плагины: первый срез и протокол v0

Дата: 21 октября 2026. Статус: решения владельца по первому срезу зафиксированы;
точный протокол и авторский API развиваются по шагам. Реализованы манифест,
описание исполнения и backend PluginManager с подключением к проектной сессии.
Процессный хост, ProcessPlugin, реальные фабрики исполнения и окно менеджера
ещё не реализованы; сетевой hello world пока не выполнен.
Требования — [requirements.md](requirements.md) (OWN-28…OWN-50), основания —
[исследование](../researches/Плагины%20SDK%20и%20межъязыковое%20выполнение.md).
Решения ниже — ответы владельца; неподтверждённые детали отмечены как открытые
и не выдаются за согласованные.

Плагины расширяют саму Gravia: при активации регистрируют в ней предоставляемые
возможности (например, ноды, единицы измерения и определения свойств потока),
а при деактивации удаляют эти регистрации.
Плагины не вызывают методы друг друга: доступ к общим определениям, в том числе
предоставленным зависимостями, получают через Gravia.

## Границы первого среза

- Первый проверяемый сценарий — hello world: плагин подключается и пишет строку
  в журнал Gravia. Нод, `describe` и расчётных вызовов в нём нет.
- Менеджер плагинов делается сразу, а не временная команда разработчика.
- Проверяются оба способа запуска: управляемый Gravia и ручной.
- Включённые управляемые плагины запускаются при открытии проекта; при закрытии
  проекта плагины выключаются.
- Сценарий проверяется двумя реализациями: минимальным скриптом на чистом Python
  и тем же сценарием через SDK. Это показывает, что контракт реализуем без SDK,
  и что именно снимает SDK.
- После hello world первый этап возможностей — только ноды. Собственные настройки
  приложения/проекта, оптимизаторы, единицы и определения свойств плагинами
  не добавляются; их будущий API не утверждён.

## Менеджер и проект

- Менеджер — отдельное окно, как настройки.
- Список плагинов относится к проекту: добавить папку, включить/выключить,
  видеть состояние подключения. Для ручного режима показывается адрес.
- Плагин — папка с `plugin.json`. Согласованная форма манифеста и реализованные
  типы описаны ниже; вычислительные возможности в него сейчас не входят.
- Путь к папке внутри проекта хранится относительно корня проекта (OWN-37).
  Политика для папок вне проекта не выбрана.
- Список подключений хранится в `plugins.json` в корне проекта отдельным файлом.
- Несколько копий Gravia работают одновременно для разных проектов (OWN-43).

### Подключения проекта: plugins.json

Формат согласован владельцем 21 октября 2026: массив записей с `path` и `enabled`.

```json
[
  {
    "path": "plugins/properties",
    "enabled": true
  },
  {
    "path": "plugins/models",
    "enabled": false
  }
]
```

`path` указывает папку плагина относительно корня проекта. ID, версия,
зависимости и исполнение читаются из её `plugin.json`. Отдельных полей для
ручного запуска в записи подключения нет: у процессного плагина это определяется
отсутствием `Command` в описании исполнения.

Владелец допускает другие способы подключения в будущем. Их формат и API пока
не выбраны; текущий срез поддерживает подключение по пути к папке.

### Backend PluginManager

Реализованный сервис Application владеет экземплярами `Plugin` одного проекта,
читает манифесты и сохраняет только `path`/`enabled`. Фабрика проектной сессии
вызывает `InitializeAsync` при открытии; сессия освобождает менеджер перед
настройками и общим хранилищем при закрытии.

- `Connections` — доступная только для чтения коллекция `PluginController`.
  Менеджер не формирует DTO или представление для UI; это ответственность
  отдельного будущего CQRS Request. Контроллеры отражают текущее состояние подключений.
- `AddAsync(path)` проверяет манифест и добавляет выключенное подключение.
- `SetEnabledAsync(path, enabled)` сохраняет выбор, затем применяет его.
  Ошибка активации оставляет плагин включённым и записывается в журнал.
- `RemoveAsync(path)` деактивирует экземпляр и удаляет запись; папку не удаляет.
- `ReloadAsync(path)` перечитывает манифест, предварительно деактивировав этот
  плагин и его включённых потребителей. После этого повторяет активацию.
- `DisposeAsync` выключает экземпляры в обратном порядке активации, пытается
  освободить все даже после ошибок и не меняет сохранённую включённость.

Зависимости обозначают требования к доступным расширениям самой Gravia;
плагины напрямую друг с другом не общаются (уточнение владельца 21 октября).
Перед активацией проверяются наличие, включённость и npm-диапазон версии
зависимости. Циклы и повторяющиеся ID блокируют активацию. Зависимости
активируются раньше потребителей. Автовключения выключенных зависимостей нет;
выключение или удаление зависимости запрещено, пока включён её потребитель.
Два разных подключения с одним ID не поддерживаются в текущем менеджере.

`PluginController` в Application/Plugins/Services управляет одним плагином:
читает его манифест, создаёт экземпляр через фабрику, активирует и деактивирует
его, включая очистку после частичной активации. Менеджер координирует контроллеры:
хранит список в `plugins.json`, проверяет уникальность ID и зависимости,
определяет порядок активации и деактивации.
Проверки состояния экземпляра, повторная очистка и журналирование сбоев его
жизненного цикла находятся в контроллере; менеджер получает результат активации
и не обращается к экземпляру `Plugin`. Неуспешные попытки также учитываются в
порядке деактивации: после сбоя очистки у контроллера могут остаться ресурсы.

Конкретные экземпляры создают реализации `IPluginFactory`: выбирается ровно
одна фабрика, поддерживающая `PluginExecution`. Ей передаются абсолютная папка
и манифест; создание возвращает неактивный `Plugin`. Контроллер вызывает его
`ActivateAsync`/`DeactivateAsync` и не содержит TCP, Process.Start или загрузчика
DLL. Если фабрики нет, ошибка записывается в журнал; успешная активация не
имитируется. Конкретные фабрики ещё предстоит добавить в DI.

`Plugin.IsLoaded` реализован в базовом классе: изначально `false`, становится
`true` после успешной активации и сбрасывается в начале деактивации, даже если
очистка завершится ошибкой. Конкретные реализации переопределяют
`OnActivateAsync`/`OnDeactivateAsync`; отдельного `Active` в `PluginController` нет.

Операции сериализованы. Ошибки отдельных плагинов при открытии не мешают
другим; повреждённый список `plugins.json` отклоняет открытие без перезаписи.
Непрочитанные манифесты остаются в списке для исправления через Reload/Remove.
При частично неуспешной активации вызывается деактивация; если очистка тоже
неуспешна, экземпляр сохраняется для следующей попытки освобождения.
Фактический сетевой статус и уведомления UI этим срезом не добавлены.

### Манифест

`PluginManifest` содержит обязательные `Id`, `Version`, `Name`, необязательный
`Description`, непустой `Execution` и словарь `Dependencies` (по умолчанию пустой).
По умолчанию `Execution` — `ProcessPluginExecution` без команды запуска.
У процессного плагина `Command` необязателен: без него процесс запускает
пользователь и подключает к Gravia вручную; с ним процесс запускает Gravia.
Отдельный признак ручного запуска в `plugins.json` для этого не требуется.
Зависимости задаются как `ID плагина → диапазон версий` в
[npm-синтаксисе](https://github.com/npm/node-semver#ranges). Поддерживаются точная
версия (`2.1.0`), `^1.2.3`, `~0.4.2`, `1.x.x`, явные сравнения и альтернативы
через `||`. Пустые/null-ограничения отклоняются; для любого стабильного релиза
нужно явно указать `*`. Предрелизы допускаются по правилам npm: обычный диапазон
их не включает, предрелиз нужно указать явно для соответствующей тройки версии.
Для `0.x.y` действуют правила выбранного оператора, а не обещание стабильности
SemVer: например, `^0.4.2` допускает патчи до `0.5.0`, а `^0.0.2` — только `0.0.2`.

При создании манифеста проверяются ID и синтаксис диапазонов; входной словарь
копируется в неизменяемый с регистрозависимыми ключами. Разбор собственных версий
плагинов (строгий SemVer 2.0.0) и диапазонов выполняет
[Semver 3.0.0](https://github.com/WalkerCodeRanger/semver); собственный regex версии
удалён. `Version` остаётся точной версией, а не диапазоном.
Проверка версий подключений, наличия зависимостей, циклов и порядка активации
реализована в backend PluginManager. Проверка по фактическому сетевому `hello`
ожидает процессного хоста. Автоустановка плагинов не добавлена.
Диапазон совместимости не заменяет фиксацию точных версий
при расчёте; формат такой фиксации ещё не выбран.
Свойства задаются через `init`; ID проверяется
по существующему правилу: минимум три разделённых точками сегмента, каждый
начинается с латинской строчной буквы и далее содержит `[a-z0-9_-]`.
Версия — строка [SemVer 2.0.0](https://semver.org/), включая prerelease и build
metadata; версия протокола передаётся отдельно в `hello`.

`Name` и `Description` используют `LocalizedText`: JSON-строку без
указанного языка либо плоский объект переводов. Пример с camelCase-настройками
`System.Text.Json`:

```json
{
  "id": "org.gravia.example",
  "version": "0.1.0",
  "name": { "en": "Example", "ru": "Пример" },
  "description": "Минимальный пример",
  "dependencies": {
    "org.gravia.properties": "^1.2.3",
    "org.gravia.models": "~0.4.2",
    "org.gravia.solver": "2.1.0"
  },
  "execution": {
    "type": "process",
    "command": "runtime/python.exe",
    "arguments": ["main.py"]
  }
}
```

`Execution` имеет тип `PluginExecution`; при отсутствии поля используется
процессное описание по умолчанию, явный JSON null отклоняется. Зарегистрирован только
`ProcessPluginExecution`, JSON-дискриминатор `type: "process"`. В JSON `type`
располагается первым внутри `execution`. `Command` — необязательный путь или имя
программы: отсутствие поля и null означают ручной запуск; пустая или пробельная
строка отклоняется, null-команда при сериализации опускается. Ручное подключение
можно явно записать как `"execution": { "type": "process" }`.
`Arguments` — массив отдельных аргументов без shell-экранирования;
по умолчанию пустой. null вместо обязательных значений, null-массив и
null-элементы аргументов отклоняются. Относительные пути трактуются от папки
плагина; фактическое разрешение путей будет реализовано в адаптере запуска.

Типы описывают конфигурацию и не запускают процессов. Пути подключения в
проекте, включение и состояния соединения в манифест не входят.
Будущая .NET-разновидность ещё не реализована.

## Подключение

- Gravia слушает loopback; плагин подключается клиентом.
- Порт выбирается заново при каждом запуске Gravia. Адрес показывается при
  каждом подключении (OWN-40).
- Управляемый режим: Gravia запускает процесс и передаёт адрес аргументом
  командной строки. Пользователь ничего не настраивает.
- Ручной режим: пользователь запускает программу сам и передаёт ей показанный
  адрес.
- Управляемый процесс принадлежит Gravia. Внешний процесс Gravia не завершает.
- Если плагин представился чужим ID или несовместимой версией протокола,
  Gravia отвечает ошибкой, закрывает соединение и показывает состояние «Ошибка».

## Протокол v0

- JSON-RPC 2.0, UTF-8, одно сообщение на строку. Переводы строк внутри строк JSON
  экранированы и границу сообщения не ломают.
- `hello` — запрос плагина: `protocol`, `id`, `version`. Gravia сверяет ID
  с ожидаемой записью и версию протокола.
- `log` — уведомление: `level`, `message`. Категория журнала выводится из ID
  плагина, а не присылается плагином.
- stdout/stderr процесса остаются диагностикой запуска и падения, а не основным
  каналом журнала.
- Аутентификация в v0 не решена; доступ ограничен loopback.
- Таймауты, предельный размер сообщения и поведение при переполнении открыты.
