# Единицы для Gravia: проверка предметных случаев в C#

Вопрос: достаточны ли библиотека единиц и заранее подготовленный пересчёт для независимых моделей НПЗ и 100 000 проходов оптимизации?

Дата: 11 сентября 2026. Статус: исследовательский эксперимент и разбор всех 36 случаев из [исходной таблицы](../Совместимость%20свойств%20и%20потоков%20разных%20моделей%20НПЗ.md). Система единиц, библиотека и новый SDK **не согласованы**. Подтверждено владельцем только поведение: Gravia обеспечивает необходимый пересчёт, тождественный пересчёт не исполняет. Python не используется.

Продолжение 12 сентября: по запросу владельца подготовлен [целостный проект контракта](../Контракт%20свойств%20единиц%20и%20преобразований%20Gravia.md) с сущностями, каталогами, C#-эскизом и порядком исполнения. Это предложение для обсуждения, а не изменение результатов эксперимента или утверждённый SDK.

## Что именно проверялось

Рабочий сценарий: инженер соединяет два готовых модуля, сопоставляет поля, запускает поиск. Модуль-получатель должен получить значение нужного свойства, в нужных единицах и условиях. Проверка включает не только правильный коэффициент, но и отказ от ложного преобразования. Исполняемый пример проверяет численную часть и демонстрирует контрпримеры; реестр свойств и полноценный проверяющий механизм в нём не реализованы.

Проверены NuGet-пакеты UnitsNet **5.75.1** и EngineeringUnits **2.2.143**. Версии и транзитивные зависимости закреплены в `packages.lock.json`. Сборка Release, .NET SDK **10.0.302**, runtime **10.0.10**, Windows x64 10.0.26100, AMD Ryzen 5 4600H, 6 ядер / 12 логических процессоров. Расчёт однопоточный. Это среда эксперимента, а не выбор версии .NET для продукта.

## Первичные основания

- [UnitsNet maintenance/v5 README](https://github.com/angularsen/UnitsNet/blob/maintenance/v5/README.md): типы величин, перечисления единиц, динамические вызовы и пользовательские конверсии. Расширение возможно: собственные IQuantity/enum, регистрация функций и сокращений. Поэтому тезис «UnitsNet нельзя расширить» неверен; но произвольные определения, загружаемые как данные плагина без генерации типов, этим не обеспечиваются автоматически. Такой полный сценарий здесь не реализован.
- [EngineeringUnits](https://github.com/MadsKirkFoged/EngineeringUnits): численные объекты и алгебра единиц. NuGet-метаданные пакета указывают commit `839b790017e897f373d183bf7c1f4b36a34c9c51`; [BaseUnitExtensions](https://github.com/MadsKirkFoged/EngineeringUnits/blob/839b790017e897f373d183bf7c1f4b36a34c9c51/EngineeringUnits/BaseUnitExtensions.cs) содержит As/GetValueAs. Описанные ниже результаты получены именно с пакетом, а не выведены из примеров master.
- [CAPE-OPEN Petroleum Fractions, таблица 1](https://www.colan.org/wp-content/uploads/2017/10/Petroleum_Fractions_Interface_Specification.pdf): отдельно перечислены виды нефтяных показателей, методы и условия. Бромное число в контракте выражено kg/kg, хотя лабораторная запись часто означает g/100 g. Это практическое основание не приравнивать безразмерность к произвольному Ratio.
- [EIA: API gravity](https://www.eia.gov/tools/glossary/index.php?id=API_gravity): API = 141,5 / SG60/60°F − 131,5. Нелинейная смена шкалы при определённой относительной плотности; плотность при произвольной температуре не подставляется вместо SG.
- [ASTM D1250](https://store.astm.org/d1250-19e01.html): отдельная методика температурной и барической коррекции нефтяных объёмов. Чтение общедоступного описания не является реализацией алгоритма стандарта.
- [NIST, PVTt](https://www.nist.gov/publications/gas-flowmeter-calibrations-26-m3-pvtt-standard): стандартный газовый расход сообщается с опорными температурой и давлением; обозначение объёма само по себе недостаточно.
- [ASTM D445](https://store.astm.org/standards/d445): связь динамической и кинематической вязкости через плотность. [D2887](https://store.astm.org/d2887-16.html), [D5191](https://store.astm.org/d5191-10.html), [D4737](https://store.astm.org/d4737-21.html): метод перегонки, расчёт DVPE и ограничения цетанового индекса нельзя подменять единицами.
- [AFPM, вопрос 86](https://www.afpm.org/data-reports/technical-papers/qa-search/question-86-what-test-method-eg-astm-d86-d1160-or-d2887-do): практики обсуждают различающиеся методы перегонки и учёт метода в расчётных моделях. Это историческое свидетельство, не новый опрос пользователей Gravia.
- [IAPWS: свойства насыщения](https://www.iapws.org/relguide/Supp-sat.html): отдельные свойства насыщенных жидкости и пара. Для двухфазного состояния требуется информация о соотношении фаз.

Остальные предметные основания и локальные модели перечислены в исходном исследовании. Здесь не выполнялась новая научная валидация FCC/риформинга или корреляций.

## Проход по всей таблице

«Одних единиц достаточно» ниже предполагает, что уже сопоставлены одинаковые свойства одного объекта. «Нужен метод» не означает, что пользователь обязан написать код: расчёт предоставляет автор готового модуля. Тексты инспектора — проверяемые сценарии обсуждения, а не утверждённые макеты. Обозначения U/E/C относятся к исполняемым проверкам в Program.cs; остальные строки проверены аналитически и по источникам, а не интеграционным тестом.

Итог таблицы: в постановке строк 1,2,5,25 достаточно обычной конверсии после проверки смысла. Это **не статистика частот** на реальном НПЗ: таблица специально насыщена сложными случаями. В остальных строках могут присутствовать простые конверсии, но они не решают весь переход. Успех системы — и правильная арифметика, и предотвращение ложного автоматического сопоставления.

## Что показали именно C#-библиотеки

**UnitsNet:** прошли расход, температура/перепад, плотность, обе вязкости, масштаб долей, отказ между массовым и объёмным расходом. Плотность представлена struct. Наличие типа Density не означает наличие температуры/фазы определения: соответствующих свойств в проверенном типе не обнаружено. Ratio не различает массовую и мольную основу. Динамический enum-путь и типизированный путь имеют разные затраты — см. измерения.

**EngineeringUnits:** прошли плотность, температура, отношения, составление плотности из массы/объёма, новая единица массы и составная kg/(m³·s) без изменения библиотеки. Выражение `1 kg/(m^3*s)` разобрано; `1 Nm3/h` завершилось FormatException. Это наблюдение о конкретном вводе, не утверждение, что библиотека принципиально нерасширяема. Массовое отношение1kg/2kg и мольное1mol/2mol дают одинаковый тип Ratio и50%; смысл нужно хранить отдельно. Две пользовательские единицы с одним символом и масштабами25/30 были созданы одновременно: подпись не годится как единственный идентификатор.

**Обнаружено ограничение ΔT в EngineeringUnits.** Старый TemperatureDelta помечен obsolete с рекомендацией использовать Temperature. Его FromDegreesFahrenheit(18).Kelvins вернул0 вместо10. Разность50°F−32°F, явно обёрнутая в Temperature, даёт10K; отображение этой же разности как DegreeCelsius даёт−263.15, как DegreeFahrenheit —−441.67. Причина проверенного сценария: разность затем интерпретируется как абсолютная температура. Это не доказательство отсутствия любого обходного решения; это доказательство, что прямой перенос такого API в SDK не обеспечивает нужную защиту. Наблюдения сохранены отдельно, не замаскированы общим счётчиком успешных проверок.

Первый запуск содержал одну проваленную проверку старого API (`results-initial.json`). В итоговом коде obsolete-вызов перенесён в раздел наблюдаемых ограничений, добавлена проверка актуальной разности в K и наблюдения её неверной интерпретации в °C/°F. **39 численных проверок прошли, но три описанных результата работы с ΔT остаются ограничениями**, а не исправленными дефектами. Никакая библиотека в этом эксперименте не прошла полноценную приёмку SDK Gravia.

## Производительность

Медианы7 повторений после прогрева. Входной массив100000значений, выходной массив выделен заранее. Проверены все результаты вне измеряемого участка. DOTNET_TieredCompilation=0, одинаково для всех вариантов. Динамический путь UnitsNet не разбирает строки: сравнение не ухудшено заведомо лишним парсингом.

Полные диапазоны — в [results.json](results.json). Это микрозамер конверсии одной известной линейной величины. Он не измеряет IPC, модель, оптимизатор, проход графа, нелинейные шкалы, изменение условий, интерфейс, параллелизм и разрозненные скалярные вызовы. Копирование показано отдельно: отсутствие конверсии не обещает нулевой транспортной стоимости.

Коэффициент1000 объявлен непосредственно для известного линейного случая. Компилятор конверсий из библиотечных метаданных не реализован. Вывод о форме ax+b по двум пробным значениям недопустим: контрпример °API не является линейным. Структура Plan — локальный инструмент эксперимента, не утверждённый публичный API.

## Какие варианты остаются после проверки

| Вариант C# | Чем покрывает требования | Что не решено |
|---|---|---|
| Самый простой: UnitsNet как каталог обычных единиц, подготовленные численные операции | Проверенные готовые коэффициенты/типизированные величины, простой вычислительный путь | Новые составные единицы и определения как данные плагинов требуют дополнительного механизма; смысл/условия отдельно |
| EngineeringUnits как механизм алгебры/расширения при подготовке | Экспериментально создаёт пользовательские и составные единицы | ΔT требует отдельного решения; объекты дороги в поэлементном цикле; семантика НПЗ отдельно |
| Собственное описание размерностей/шкал с ограниченным C#-исполнителем | Можно точно сформировать расширяемый межъязыковой контракт | Максимальная ответственность за математику, каталоги и тесты; нынешний Plan не доказывает готовность такого механизма |

Предварительный вывод: **не выбирать ни библиотеку, ни собственный движок окончательно**. Старое предположение, что расширяемая алгебра единиц сама решает задачу Gravia, опровергнуто строками12,19,29 и другими. Вместе с тем C#-измерение поддерживает отделение подготовки от численного исполнения для известных линейных конверсий.

Для всех вариантов необходимо независимо описывать смысл свойства, условия и единицы. Необходимость следует из таблицы, а не из предпочтения классов. Ядро может проверять объявленные ограничения без знания химии; модуль определяет смысл и даёт необходимые предметные методы; пользователь сопоставляет поля, задаёт доступные данные и выбирает метод при неоднозначности. Точные декларации и UX ещё обсуждаются. Если зависимое преобразование использует плотность/состав текущего кандидата, структура вычисления готовится один раз, а значения зависимостей читаются заново при каждом расчёте.

Пример инспектора для обсуждения: при g/cm³→kg/m³ строка готова и показывает820kg/m³; при rho20→rho15 показывает разные условия и наличие/отсутствие метода; при неизвестном Nm³/ч — какие именно опорные данные отсутствуют. При mol%→mass% недостаточно предложить замену символа: нужен состав с молярными массами. Эти сообщения должен обеспечивать контракт Gravia, а не пользовательская догадка о внутренностях библиотеки.

Открытые проверки, способные изменить выбор: динамическое подключение двух независимых C#-плагинов с новыми определениями и коллизиями; сериализация без зависимости от CLR-типов библиотек; точные нелинейные шкалы; условий как параметров текущего прохода; прототип инспектора; измерение на реальном быстром суррогате вместе с транспортом. Это следующий уровень доказательств, а не уже выполненная работа.

## Воспроизведение

Из C:\Projects\gravia, PowerShell:

```powershell
dotnet restore researches/units-dotnet-audit/UnitsAudit.csproj --locked-mode
dotnet build -c Release --no-restore researches/units-dotnet-audit/UnitsAudit.csproj
$env:DOTNET_TieredCompilation = '0'
dotnet run --no-build -c Release --project researches/units-dotnet-audit/UnitsAudit.csproj

Данные входов синтетические; библиотеки установлены только как зависимости изолированного проекта исследования. Продакшен-код Gravia и исходные модели не изменены.
