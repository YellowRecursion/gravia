Вопрос: как показать API плагина на предоставленных моделях, включая локализацию и подготовку входов будущего блендинга?

Дата: 11 сентября 2026 года. Статус: проверка исходных интерфейсов и эскизы SDK для обсуждения. `gravia_sdk`, атрибуты, классы и методы предлагаемого SDK ниже не реализованы. Примеры не являются запускаемыми плагинами; химические модели и их артефакты не запускались. Требование минимум одного языка плагина подтверждено владельцем; остальные детали API предложены.

## Локализация

Предложение: manifest указывает `defaultLocale` и словари; хотя бы один словарь обязателен и полностью покрывает используемые ключи. Пример фрагмента manifest:

```json
{
  "id": "example.fcc",
  "version": "0.1.0",
  "defaultLocale": "ru",
  "locales": { "ru": "locales/ru.json", "en": "locales/en.json" }
}
```

Пример `ru.json`:

```json
{
  "model.fcc": "Каталитический крекинг",
  "port.feed": "Сырьё",
  "port.gasoline": "Бензин FCC",
  "parameter.temperature": "Температура",
  "error.feed": "Точка {caseId}: требуется состав сырья Nh/Ph/Ah"
}
```

Это сокращённый словарь; поставка должна содержать ключи остальных портов и параметров. `en.json` содержит те же ключи с английскими строками. Один `ru.json` без `en.json` допустим. Предлагаемый fallback: запрошенная локаль → базовый язык локали → defaultLocale. При неполном дополнительном переводе fallback применяется к конкретному ключу. Эта политика ещё не согласована. Данные и коды ошибок не переводятся; отображаемые сообщения, названия портов/режимов/параметров и подсказки используют ключи ресурсов. Не обещать автоматический перевод сторонних текстов.

## Что объявляет плагин FCC

Каталог модели описывает вход `feed` (расход kg/s и версия схемы массового состава), параметры температуры K и времени s, пять выходных продуктов и локализованные подписи. Это общее описание портов, не форма «для подключения именно к блендингу».

Для примера совместной кинетики/суррогата выбран трёхгрупповой вход Nh/Ph/Ah: неотрицательные конечные доли с суммой 1 в явно заданном допуске. Кинетическая реализация допускает больше групп; суррогат строит признаки по Ph/Nh. Не следует молча отбрасывать лёгкие группы, если они пришли во входе. Проверку схемы предоставляет описанный контракт плюс авторская диагностика. TS-600 соответствует имеющемуся bundle. Подтверждённый диапазон применимости и параметры других катализаторов этим примером не устанавливаются.

Пример вызова **существующей** кинетики для одной точки:

```python
from fcc_model import FCCKineticModel

kinetic = FCCKineticModel(catalyst="TS-600")  # подготовка сессии
fractions = kinetic.predict(
    T_celsius=temperature_K - 273.15,
    time_seconds=contact_time_s,
    feed_comp=feed_mass_fractions,
)
```

Модель возвращает доли всех 16 групп. Ни расход сырья, ни паспортные свойства в `predict` не передаются. Расходом сырья адаптер масштабирует выход продуктов.

Ниже показана реальная арифметика адаптера на Python. `stream` и `property_value` — предлагаемые конструкторы SDK, которые получают выходной ID/caseId от контекста и сохраняют происхождение. `model_origin` содержит версию кода/артефактов, `conversion_origin` — версию этого отображения и зависимость от модельного результата. Проверку конечности, формы и неотрицательности результата адаптер выполняет до этого фрагмента. Исходная невязка не маскируется общей перенормировкой.

```python
PRODUCT_GROUPS = {
    "gasoline": ["Nl", "nPl", "iPl", "Ol", "Al"],
    "lco": ["Nm", "Pm", "Om", "Am"],
    "gas": ["DG", "PPF", "BBF"],
    "coke": ["Coke"],
    "heavy_residue": ["Nh", "Ph", "Ah"],
}

PIONA = {
    "group.normalParaffins.mass": "nPl",
    "group.isoParaffins.mass": "iPl",
    "group.olefins.mass": "Ol",
    "group.naphthenes.mass": "Nl",
    "group.aromatics.mass": "Al",
}

def products_from_fcc(feed_kg_s, fractions, ctx):
    products = {}
    for port, groups in PRODUCT_GROUPS.items():
        product_yield = sum(fractions[g] for g in groups)
        flow = feed_kg_s * product_yield
        composition = (
            {g: fractions[g] / product_yield for g in groups}
            if flow > 0 else None
        )
        products[port] = ctx.stream(
            port=port,
            mass_flow_kg_s=flow,
            composition_schema=f"example.fcc.{port}/1",
            mass_fractions=composition,
            origin=ctx.conversion_origin("fcc-products/1"),
        )

    gasoline = products["gasoline"]
    if gasoline.mass_fractions is not None:
        for property_id, group in PIONA.items():
            gasoline.properties[property_id] = ctx.property_value(
                gasoline.mass_fractions[group],
                unit="kg/kg",
                origin=ctx.conversion_origin("fcc-piona/1"),
            )
    return ctx.freeze(products)
```

Конструкторы работают с подготовленным реестром схем/свойств: сам текст ID без зарегистрированного определения не доказывает совместимость. Изменяемый builder до `freeze` принадлежит адаптеру. Остальные продукты сохраняются для баланса, даже если на схеме подключён только бензин. Нулевой поток не получает выдуманную композицию; потребитель смешения пропускает его, если такой случай допустим его постановкой.

Пакетный слой SDK собирает результаты по caseId. Для кинетики выполняется последовательный вызов `predict` на строку внутри рабочего процесса; ошибка строки сохраняет её ID. Для суррогата используется его **существующая пакетная ветка**, а не N одиночных инференсов:

```python
from fcc_surrogate_model import FCCSurrogatePredictor

# Один раз; путь предоставляет пакет плагина.
surrogate = FCCSurrogatePredictor(
    bundle_path=str(artifacts / "fcc_ts600_bundle.joblib"),
    normalize_feed=False,
    device=device,
)

# temperature_K/contact_time_s — NumPy-массивы равной длины,
# feed_dicts — проверенные составы соответствующих точек.
rows = surrogate.predict(
    T_celsius=temperature_K - 273.15,
    time_seconds=contact_time_s,
    feed_comp=feed_dicts,
)
```

Результаты `rows` проходят тот же адаптер продуктов. Режим запроса и выбор вычислителя остаются внутри плагина по OWN-10; значения enum/режимов этим примером не утверждаются. Исходный predictor имеет список словарей на выходе: SDK упаковывает его в MaterialBatch один раз перед межпроцессной передачей. Настройки локализации не участвуют в выборе модели.

## Риформинг: C#-обёртка и фактическая граница MATLAB

Текущий `calc2()` не имеет аргументов и возвращаемого результата: читает файлы, использует globals, пишет прореженный экспорт и вызывает `plot`/`pause`. Для автоматического плагина автор должен выделить расчёт без интерактивных остановок и вернуть конечное состояние **до прореживания**. Последняя строка существующего OUT-файла не гарантирует конечную точку решателя. Уравнения не меняются в рамках адаптации; рабочую версию из нескольких `calc2copy*` ещё нужно подтвердить.

Пример C#-адаптера результата после подготовленного автором MATLAB-вызова. Предполагается, что `finalFlowKmolH` содержит 38 компонент конечного состояния в порядке X1…X38, `mmKgKmol` — соответствующие MM. Это не готовая функция из исходного MATLAB-пакета и не реализация его запуска:

```csharp
// Методы Conversions уже представлены в арифметическом эксперименте.
var componentKgS = Conversions.ReformingComponentMassFlows(
    finalFlowKmolH, mmKgKmol);

// C# индексы с нуля: MATLAB X6…X37 -> 5…36.
var reformate = Conversions.SelectProduct(
    componentKgS, Enumerable.Range(5, 32).ToArray());
var offgas = Conversions.SelectProduct(
    componentKgS, [0, 1, 2, 3, 4, 37]);

if (reformate.MassFractions is { } w)
{
    double p = Enumerable.Range(0, 7).Sum(i => w[2 * i]);
    double iso = Enumerable.Range(0, 7).Sum(i => w[2 * i + 1]);
    double n = w.Skip(14).Take(12).Sum();
    double a = w.Skip(26).Take(6).Sum();
    double benzene = w[26]; // X32=A6 согласно схеме этой версии

    // Далее эти числа публикуются как свойства с origin:
    // group.normalParaffins.mass, group.isoParaffins.mass,
    // group.naphthenes.mass, group.aromatics.mass, benzene.mass.
}
```

Нулевое содержание олефинов **не** получается из отсутствия соответствующего поля: в схеме нет олефиновых групп. Для примера можно явно назначить допущение O=0 в приближении модели либо источник из паспорта продукта. Его статус хранится отдельно от вычисленных P/I/N/A. Если паспортный O противоречит исчерпывающей композиции модели, нельзя просто добавить его к нормированным P/I/N/A: нужен согласованный альтернативный набор свойств/состава. Проверка не должна принимать P+I+N+A=1 и O>0 как полный корректный PIONA-набор.

Перед MATLAB-вызовом адаптер преобразует поток обратно в родные единицы модели: `n_i=q*w_i/M_i`, нормирует мольные доли, переводит суммарный mol/s в kmol/h, температуру K в °C. Это уже описано и показано в `Conversions.ToReformingInput`. Для соответствующего исследуемого формата `Period` — накопленная масса катализатора в kg. C#-обёртка не устраняет необходимость выбранного MATLAB/Runtime/иного исполнения; его поставка остаётся отдельным открытым вопросом.

## Вход блендинга: требования к данным

Рассмотрены три варианта: блендинг сам знает FCC/MATLAB; отдельный конвертер для каждой пары моделей; производители публикуют предметные свойства, а потребитель объявляет требования. Первый проще для двух фиксированных моделей, но каждый новый поставщик потребует менять блендинг. Второй удобен для особых преобразований, но размножает попарные адаптеры. Предлагается третий, уже представленный в материальном контракте: общий формат плюс расширяемые определения свойств. Химические преобразования реализуют плагины, ядро проверяет совместимость определений и исполняет выбранный план.

Для примера выбрана **массовая** основа, как в проекте материального контракта. В исходном описании блендинга `% масс/об`, `ppm` без основы и массовые/объёмные рецепты оставлены альтернативами. Это ещё не однозначный контракт реальной модели. Опорные условия плотности и метод ДНП/перегонки также должны войти в окончательное определение входов. Нельзя автоматически объявить любую плотность/ДНП теми же свойствами.

Сокращённый эскиз описания будущего порта на Python:

```python
components = MaterialInput(
    many=True,  # отдельное подключение каждого компонента смешения
    label="port.components",
    requires=[
        "group.normalParaffins.mass", "group.isoParaffins.mass",
        "group.olefins.mass", "group.naphthenes.mass",
        "group.aromatics.mass", "benzene.mass", "sulfur.mass",
        "density.liquid@293.15K", "vaporPressure.reid",
        "distillation.D86.volumeRecovered.T10",
        "distillation.D86.volumeRecovered.T50",
        "distillation.D86.volumeRecovered.T90",
        "distillation.D86.volumeRecovered.T95", "oxygen.mass",
    ],
)
```

Названия ID — проект определений, не доказательство выбора Reid/D86 конкретной будущей моделью. Числа в MaterialBatch передаются в канонических единицах. Если внутреннему блендингу нужны mass %, ppm mass, kPa, °C, его адаптер делает точные пересчёты: долю ×100, долю ×10^6, Pa÷1000, K−273.15. Массовая и объёмная доли не заменяются простым пересчётом единиц.

Кроме показанных свойств, полный вход из Model_Description требует:

| Вход | Представление/условие |
| --- | --- |
| ID компонента | Стабильный ID продукта; имя локализуется независимо |
| Тип кислородсодержащего компонента | Категория или описание оксигенатного состава, обязательное при ненулевом кислороде по окончательному контракту модели; не угадывается по одному oxygen.mass |
| i-C4 | `isobutane.mass` для бутанового компонента, если этого требует выбранная модель; агрегат BBF у FCC сам по себе не определяет i-C4 |
| Цена | Данные сценария, обязательны при выборе критерия стоимости; фиксируются валюта и единица |
| Доступность/запасы | Данные ресурсного сценария для критерия вовлечения и ограничений; расход kg/s не равен запасу kg, нужен горизонт/план поступлений |
| Доли рецепта | Вход оценки заданной рецептуры или переменные оптимизации; устройство оптимизатора ещё не определяется этим портом |

Модель блендинга пока не реализована, поэтому здесь нет фиктивного `blending.predict`, обещающего готовый расчёт. Критерии и ограничения описания не задают автоматически выбранную библиотеку оптимизации Gravia.

## Где берутся недостающие свойства

Плагин FCC/риформинга возвращает всё, что действительно выводится его моделью. В инспекторе продукта пользователь назначает недостающим свойствам паспорт или известную модель свойства. Для конкретного запуска выбор фиксирован. Источник относится к продукту, а не автоматически к исходному сырью. Константное паспортное свойство не начинает зависеть от режима установки само по себе.

| Данные | FCC gasoline | Риформат |
| --- | --- | --- |
| Расход | Расход сырья × доля бензиновых групп | Сумма компонентных расходов C5+ |
| P/I/N/A | Группировка и нормирование на бензин | Группировка и нормирование на риформат |
| O | Ol бензиновой части | Явное допущение модели или согласованный источник состава |
| Бензол | Паспорт/модель свойства | A6 согласно отображению компонент |
| Сера, плотность, ДНП, перегонка | Выбранные паспорта/модели свойств | Выбранные паспорта/модели свойств |
| Кислород и его тип | Известные данные либо явные допущения | Известные данные либо явные допущения |

Пользовательская схема остаётся `FCC.gasoline → Блендинг.components` и `Риформинг.reformate → Блендинг.components`. Инспектор показывает, например: «PIONA — результат FCC; сера — паспорт продукта №…; ДНП — источник не задан». При обязательном отсутствующем ДНП расчёт блендинга не начинается, пока не выбран источник. Не создаём отдельную обязательную ноду на каждое свойство.

## Проверки и границы готовности

- Локализация: один язык проходит; отсутствие обязательного ключа defaultLocale обнаруживается; смена локали не меняет данные/ID.
- Адаптеры: синтетические различающиеся доли выявляют перестановку PIONA; потоки продуктов дают исходный баланс; нулевая масса не приводит к делению на ноль.
- Реальное подключение: одинаковые входы дают одинаковые результаты исходного вызова и обёртки; для риформинга проверяется именно конечное состояние, а не последняя строка прореженного экспорта.
- Источники свойств: отсутствующее значение отличается от нуля; mass/volume, температура и метод определения проверяются; конфликтующие составы не принимаются.
- Пакеты: caseIds сохраняются; ошибка строки не сдвигает последующие результаты; суррогат использует пакетный вызов.

В этом дополнении новые исполняемые тесты не запускались. Существующий арифметический эксперимент содержит контрольные проверки части преобразований; его прежний результат не подтверждает работу показанного SDK. Исходные пользовательские модели не изменены.
