# Архитектура Gravia и границы проектов

Вопрос: как разделить растущую Gravia на понятные проекты, чтобы добавление моделей, изменение интерфейса и развитие расчётов не требовали переделывать всю систему?

Дата: 12 сентября 2026 года. Статус: архитектурное предложение для обсуждения с Вадимом. Исследованы документы проекта и первичные источники; проведена проверка предложения на сценариях и изменениях требований. Производственный код, SDK и сквозной benchmark не реализованы. Названия проектов и интерфейсов ниже предлагаются, а не фиксируются как уже принятые решения.

## 1. Предлагаемое решение

Один локальный backend Gravia с пятью C#-проектами: `Domain`, `Application`, `Execution`, `Infrastructure`, `Host`. Внутри — предметные разделы и сценарии, а на границах — небольшие интерфейсы, принадлежащие потребителю. Desktop и SDK плагинов — отдельные проекты своих языков. Backend поставляется вместе; внешние процессы моделей запускаются по необходимости.

Пользовательский проект существует как редактируемый предметный документ. Запуск получает независимый снимок документа; вычислительный план и результаты принадлежат запуску. Плагин публикует описание возможностей и реализует публичный протокол, не получает внутренний `Project` Gravia и не изменяет его.

Главное правило размещения кода: **предметный смысл — Domain; действие пользователя — Application; численное выполнение — Execution; конкретная внешняя технология — Infrastructure; подключение приложения и сборка зависимостей — Host.** Разделы 5–6 уточняют спорные случаи, включая единицы и проект пользователя.

Это развитие Clean Architecture с выделенной вычислительной подсистемой. Отдельная `Execution` нужна для самостоятельного жизненного цикла расчёта и подключения разных методов исследования; аргумент не зависит от обещания сверхнизких накладных расходов.

## 2. Исходные условия и исправление прежних предположений

### Подтверждено владельцем

- Gravia — предметная среда НПЗ; химия и конкретные модели принадлежат расширениям. Требования: [product](../docs/product.md), [requirements](../docs/requirements.md), AGENTS.md.
- Сохраняются пакетные вычисления, обычные автоматические конверсии единиц и отдельные видимые ноды предметных преобразований: OWN-04, OWN-11, OWN-12.
- Уточнения 12 сентября из другого чата: поток описывается деревом контекстов и полей; входы/выходы описаны до расчёта; определение свойства отличается от конкретного поля; поля имеют устойчивые ID; разные плагины могут иметь разные деревья; `Value` содержит данные, а не условия.
- Обязательный отдельный класс `Phase` не принят. Групповое автоматическое сопоставление — предложение, не утверждённый UX.
- В текущем запросе приоритеты архитектуры: легко расширять, мало путаницы, чёткие границы. Большой ожидаемый размер проекта сам по себе не требует большого числа сборок.

### Что не следует считать принятым

Предыдущие ответы ассистента последовательно называли `Engine`, `Core`, `Domain`, затем `Modeling.Domain`; это не четыре согласованных решения. Аналогично не утверждены gRPC, shared memory, объединение совместимых плагинов в один worker, обязательный единый Python на все будущие расширения и отдельный bounded context для каждой технической подсистемы.

Фраза владельца о небольшой роли оптимизации обвязки принимается как приоритет понятной реализации. Относительная стоимость Gravia и моделей пока неизвестна. Она не отменяет продуктовую задачу оптимизации НПЗ и обязательность batch. Если под фразой подразумевалось изменение продуктового приоритета, это отдельное решение; здесь оно не вводится.

Старый [материальный контракт v0.1](../docs/material-stream-contract-v0.1.md) частично устарел: условия в `PropertyDefinition`, отдельные определения плотности по температуре, обязательное SI на границе и размещение вычисляемых преобразований требуют пересмотра. Новое указание владельца разрешает конкретное расхождение об условиях; старые формулы адаптеров не объявляются от этого неверными.

### Неизвестное, способное изменить устройство

| Предположение / вопрос | Проверено сейчас | Если не подтвердится |
| --- | --- | --- |
| Условия поля всегда константны до запуска | Не подтверждено. Заранее известное описание не означает постоянную температуру во всех точках. | Понадобятся ссылки из описания условия на другое поле/параметр и проверки по точкам; рассмотрено в §7. |
| Накладные расходы всегда малы | Нет. Есть только микрозамер единиц; быстрый FCC-суррогат ранее описывался владельцем отдельно. | Изменится адаптер обмена/пакетирование, а не предметная модель. |
| Один Python подходит всем 20 плагинам | Нет подтверждённых зависимостей 20 плагинов. | Матрица поддержанных runtime и отдельные окружения; исключается автоматическое обещание совместимости. |
| Начальный граф допускает только ациклическое выполнение | Первый полный сценарий ещё не утверждён. | При обязательном рецикле нужен согласованный итерационный решатель; одной топологической сортировки недостаточно. |
| Сторонним моделям достаточно декларативных форм | Для первого расчётного SDK это проверяемое предложение. | Пользовательские UI-расширения получат отдельный контракт, без доступа к Domain. |
| Достаточен один редактор документа | Совместная многопользовательская работа не заявлена. | Потребуется пересмотр конкурентного редактирования и истории, не простое добавление сетевого транспорта. |

## 3. Сценарии, на которых проверяется архитектура

### A. Схема и соединения до расчёта

Автор Python-плагина предоставляет описание выходного потока: контексты нефтяной части и частиц катализатора, поля плотности и размера частиц, единицы, условия, формы значений. Другой модуль требует часть этих данных в иначе организованном дереве. Пользователь добавляет ноды, задаёт исходные данные и сопоставляет конкретные поля.

Gravia показывает структуры без вычисления кинетики. Она проверяет заявленный смысл, контекст, форму данных, условия и единицы. Для одного и того же размера частиц µm → m подготавливает численный пересчёт. Если требуется другое определение среднего размера, либо плотность при другой температуре, нужна соответствующая видимая нода. Названия на экране не участвуют в идентичности.

Проверка результата: сопоставление переживает переименование; изменение условий выявляется; вывод диагностики не зависит от наличия рассчитанного значения; неподготовленная связь не допускает запуск зависимой части расчёта.

### B. Расчёт и редактирование одновременно

Пользователь запускает сценарий на ревизии проекта 12 и во время вычисления изменяет параметр, получая ревизию 13. Запуск продолжает использовать снимок ревизии 12. Результат подписан своим `RunId` и снимком; интерфейс явно показывает, что текущая схема уже изменилась.

Проверка: вычислитель ни разу не читает изменяемый документ; сохранённый результат можно открыть без текущих Python-процессов. Ошибка одной точки отличается от нарушения ограничения и от отмены всего запуска.

### C. Многократные исследования одной схемы

Пользователь задаёт переменные, ограничения, критерии и вариант вычисления, предоставляемый модулем. Метод исследования многократно вызывает подготовленную схему, затем при необходимости пересчитывает выбранные решения с другим запросом к модулю. Пользовательские изменения проекта при этом не имитируются для каждого кандидата.

Проверка: связь `caseId → входы → результат` сохраняется; различимы поиск и пересчёт; повторно рассчитаны зависимые выходы; модельная ошибка не заменена ядром выдуманным штрафом. Форма запроса точности остаётся открытой по OWN-10.

### D. Добавление и обновление плагина

Автор добавляет новый тип установки без изменения C#-кода предметного ядра. Пользователь устанавливает пакет, использует его в проекте, позже открывает тот же проект на другом компьютере или после установки новой версии.

Проверка: новый модуль появился через описание и SDK; существующие проекты сохраняют выбранную версию; отсутствие пакета оставляет ноды и их данные доступными для просмотра; миграция показывает изменения схемы и сохраняет исходный файл до успешного сохранения новой версии.

Теоретические основания: [Robert C. Martin, Dependency Rule](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html) — зависимости внутренних политик не направляются на внешние механизмы; [Eric Evans, DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) — единый язык, явные границы моделей и согласованность агрегатов; [Martin Fowler, CQRS](https://martinfowler.com/bliki/CQRS.html) — разделение моделей записи/чтения имеет цену и применяется избирательно. Эти принципы не требуют микросервисов, отдельной БД на чтение либо одного проекта на каждую сущность.

Ранее выполненные местные эксперименты: [единицы в C#](units-dotnet-audit/README.md), [арифметика адаптеров](material-contract-v0.1/README.md), [совместимость UI-библиотек](stack-audit-2026-09-11/README.md). Их ограничения сохраняются. Новых интервью, запуска COCO/IDAES/Dakota и измерений реальных моделей в этой работе нет.

Первые четыре — Class Library, Host — исполняемый проект. Конкретный шаблон Host выбирается с транспортом desktop↔backend; для начала достаточно Console. ASP.NET Core не является следствием наличия Host. C#/.NET опирается на предпочтение OWN-07 и существующие эксперименты; версия SDK фиксируется при создании каркаса.

### Исчерпывающие зависимости между пятью проектами

Стрелка означает C# `ProjectReference`, а не направление вызовов:

```text
Domain          → нет ссылок на другие проекты Gravia
Execution       → Domain
Application     → Domain, Execution
Infrastructure  → Domain, Execution, Application
Host            → Application, Infrastructure
```

Host получает собранные сервисы через регистрацию Infrastructure и публичные операции Application. Транзитивная доступность типов не разрешает обход Application из endpoint. Execution не ссылается на Application; её порты исполнения определены внутри Execution. Infrastructure реализует их. В момент выполнения вызов может идти Execution → Python-адаптер Infrastructure, хотя зависимость исходного кода направлена обратно.

Domain и Execution могут сосуществовать в одном процессе; разделение `.csproj` не создаёт ни процесса, ни IPC. Внешние Python-процессы — способ подключения языка, не микросервисы Gravia.

```text
  Gravia.ArchitectureTests/
```

Это карта назначения, не поручение немедленно создать все пустые каталоги и проекты. `contracts/` не обязан быть C#-библиотекой; Python SDK не является проектом .NET. Формат схем и генератор пока не выбраны. При генерации C# DTO они остаются во внешнем адаптере или отдельной внешней сборке протокола; Domain их не использует.

`sdk/dotnet` может совершенно законно содержать библиотеку C# интерфейсов. Ошибкой прежнего обсуждения было приравнивание такой библиотеки ко всему межъязыковому контракту. Синхронная семантика SDK и wire-протокола проверяется общими примерами, а не ссылкой Python на C# DLL.

## 6. Где находятся проект пользователя, единицы и конвертеры

### Проект пользователя

| Представление | Владелец | Содержание |
| --- | --- | --- |
| `Project`, `Flowsheet`, `StudyDefinition` | Domain | Что пользователь моделирует: экземпляры нод, соединения, сопоставления, конфигурация, исходные данные, выбранные зависимости, переменные и критерии |
| `ProjectSession` | Application | Открытый документ, ревизия, dirty-state, история редакторских действий, последовательность изменений |
| Документ на диске и его миграции | Infrastructure | Версионированный DTO-формат; чтение/сохранение, вложения и ссылки на результаты |
| `RunSnapshot`, `ExecutionPlan` | Execution | Зафиксированные данные и описание данного вычисления; план операций, разрешённые поля и зависимости |
| `RunRecord` и доступ к архиву | Application + её порт хранения | Идентичность запуска, статусы, ссылка на снимок, записи результата; физическая запись реализована Infrastructure |
| Позиции нод, выбранный элемент, масштаб, панели | Desktop; сохраняемая часть через Application | Состояние представления, отделённое от физического смысла схемы |

Файл `.gravia` и объект `Project` не тождественны. Формат хранения содержит собственную версию; изменения внутреннего класса не должны автоматически менять файл. Положение ноды может входить в сохранение проекта, но не влияет на численный снимок. Сведения о runtime на диске — техническая часть записи воспроизводимости, а не поля физической модели.

Рекомендация по DDD: `Flowsheet` — граница согласованного изменения нод и их связей. Удаление ноды удаляет её связи в одной операции. `Project` организует документы/постановки и зависимости; не превращается в объект со всеми массивами всех запусков. Изменение схемы может сделать постановку исследования неготовой; при запуске Application проверяет совместимость выбранных ревизий. Это не требует транзакции на весь архив результатов.

### Единицы: одна ответственность, несколько этапов

| Работа | Где |
| --- | --- |
| Что такое величина/единица, её идентичность, размерность, температурная разность; что объявлено у поля | Domain, раздел `Quantities` и описание поля |
| Проверить одинаковый смысл, область материала, основу и условия сопоставленных полей | Чистая политика Domain; Application показывает результат, Execution применяет ту же политику при подготовке |
| Загрузить каталог единиц, разобрать внешнее выражение или вызвать выбранную библиотеку | Infrastructure через узкий порт подготовки; библиотечные типы не выходят наружу |
| Подготовить точный известный численный переход единиц | Execution через `IUnitConversionProvider`; реализация может быть чистой для простых определений либо адаптером библиотеки |
| Выполнить `t/h → kg/s` над пакетом | Execution, заранее подготовленная операция |
| Отобразить значение в выбранной единице | Application формирует представление для UI через тот же механизм единиц; форматирование локали — Desktop |
| Пересчитать плотность к другой температуре, перейти mass → mole по молярным массам | Реализация отдельной ноды в расширении; узел виден в проекте по OWN-12 |

Идентичное преобразование исключается из плана. Общая размерность — необходимая, но недостаточная проверка. Например, доли разных основ и разные виды среднего размера нельзя отождествлять по `%` или `m`.

Проверка имеет два результата: предметная совместимость и готовность механизма передачи. Domain сравнивает разрешённые описания/условия, а не вызывает Python или библиотеку единиц. Общая предварительная проверка в Execution приводит сравнимые константные условия к согласованному представлению через механизм единиц, вызывает политику Domain и проверяет поддержку нужной конверсии. Application использует эту же предварительную проверку для редактора, не поднимая расчётные сессии. Так неизвестная единица не превращает правильное по смыслу сопоставление в ложное обещание готовности, а правило не дублируется в UI и runtime.

`IUnitConversionProvider` принимает наши определения, а возвращает подготовленную операцию либо диагностику отсутствия поддержки. Известная аффинная операция содержит scale/offset и отдельный признак identity; она выводится из определения, не угадывается по двум пробным значениям. Формулы, требующие текущей плотности, состава, опорного давления или предметного метода, остаются видимыми вычислениями. Возможные другие чистые шкалы должны иметь явно поддержанную семантику, а не неявно втиснуты в `ax+b`.

Сравнение механизмов уже есть в [C#-аудите](units-dotnet-audit/README.md): готовый каталог UnitsNet, алгебра EngineeringUnits, собственные определения. Их не нужно заново выбирать только из-за структуры сборок. Предлагаю сначала изолировать подготовку и доказать расширение двумя независимыми пакетами, а библиотечные типы не публиковать в SDK. Это оставляет ограниченный участок для изменения решения. Каталог стандартных определений и определения плагина разрешаются в снимке; установкой нового пакета нельзя переопределить используемую единицу по совпадению подписи.

## 7. Предметная модель потока с учётом новых уточнений

### Словарь и идентичность

| Понятие | Смысл |
| --- | --- |
| `PropertyDefinition` | Переиспользуемое определение свойства: например, плотность. Не содержит выбранное для конкретного поля значение 20 °C. Допустимые виды условий и смысл метода должны быть описаны явно. |
| `StreamContext` | Узел дерева: к какой части материала относятся дочерние поля. Имя для отображения, устойчивый ID и предметное описание контекста разделены. |
| `FieldDescriptor` | Конкретное поле конкретной схемы: свой ID, ссылка на определение свойства, контекст, единица, условия, форма/ось данных и правила наличия. |
| `PortSchema` | Полное предварительное описание дерева конкретного порта, с версией/отпечатком. |
| `FieldRef` | Адрес использования поля: экземпляр ноды + порт + ID поля. Схема и её версия разрешаются из снимка. |
| `FieldBinding` | Выбранное соответствие конкретного источника конкретному входному полю. Сохраняется в схеме пользователя. |
| Значение / пакет значений | Данные для `FieldRef` в конкретном запуске; интерпретация берётся из зафиксированной схемы. |

ID свойства и ID поля решают разные задачи. GUID поля гарантирует возможность сослаться на него, но не доказывает физическую эквивалентность другому полю. Две ноды одного типа могут использовать одинаковые ID полей своей схемы, потому что их `NodeId` различаются. Копирование ноды создаёт новый `NodeId`, а не переименовывает поля типа. Динамические повторяемые элементы требуют сохраняемой идентичности экземпляров; числовая позиция в массиве не должна незаметно стать ID.

В опубликованной схеме плагина ещё нет `NodeId` проекта пользователя. Внутренние ссылки описания поэтому относительные: порт + ID поля либо ID параметра данного типа ноды. При создании экземпляра/снимка они разрешаются в полный `FieldRef`. Эти два вида ссылки нельзя смешивать; иначе описание одного типа невозможно безопасно использовать в двух нодах.

Определения, опубликованные независимо, получают пространство имён и версию пакета; совпадение `density` в двух пакетах не разрешает подмену. Повторное использование общего определения предпочтительно, когда смысл действительно общий. Ручное сопоставление разных определений фиксирует явное утверждение соответствия и его основание; известное несовпадение метода/основы/условий оно не исправляет. Как описывать эквивалентность независимых определений в удобном UI, ещё надо проверить с владельцем.

### Пример: плотность в двух условиях

```text
PropertyDefinition: density

Поле A:
  id: oil-density-20
  property: density
  context: нефтяная часть
  unit: g/cm³
  conditions: temperature = 293.15 K

Поле B:
  id: oil-density-15
  property: density
  context: нефтяная часть
  unit: kg/m³
  conditions: temperature = 288.15 K
```

Имена ID здесь условные. Определение свойства общее, поля и условия разные. Обычная смена единиц не делает A подходящим B; пользователь вставляет ноду преобразования. Конкретная корреляция в этом исследовании не выбирается.

### Дерево не является системой автоматического вывода смысла

`Нефтяная часть / Частицы катализатора / Средний размер` используется как пользовательский пример структуры, не как подтверждённая физическая классификация катализатора. Нужно различать композицию материала, принадлежность поля и чисто визуальные группы. Ядро не выводит ни одно из них из строки пути.

Семантический контекст описывает объект/подмножество, к которому относится свойство. Если автор предоставил только произвольную подпись, автоматическая совместимость не доказана. Ядро может проверять общие структурные правила и зарегистрированные соответствия; толкование конкретной смеси или группы задаётся определением модуля и явным пользовательским сопоставлением.

Предлагаю не вводить неявное наследование условий по дереву в первой реализации. Каждое поле имеет разрешённый набор условий; SDK может давать удобный способ задать их группе с разворачиванием в описании. Иначе перенос узла дерева незаметно меняет условия всех потомков. Если наследование понадобится как продуктовая функция, его правила и влияние на переподготовку должны быть специфицированы отдельно.

Переименование и перевод не меняют связь. Перенос поля в другой **семантический** контекст требует повторной проверки, даже если ID сохранён. Перемещение только в визуальной группировке этого эффекта не имеет. Изменение физического смысла поля или определения требует новой семантической версии и явной миграции, а не использования старого ID с новым значением по умолчанию.

### Условия, меняющиеся между кандидатами

Утверждение «условия вне Value» реализуемо двумя способами:

1. Только константные условия: самый простой вариант, например паспортная плотность при 20 °C. Он не выражает плотность при текущей температуре, если эта температура меняется.
2. Декларация условия содержит константу **или ссылку** на объявленное поле/параметр: `temperature = field(outlet, temperatureId)` относительно текущего экземпляра. При подготовке она разрешается в полный `FieldRef`. Данные температуры лежат в своей колонке значений; у плотности по-прежнему нет внутреннего словаря условий.

Рекомендую второй способ как расширяемую форму контракта, но его необходимость для первого среза требует подтверждения. Он не разрешает произвольный код в условии. При подготовке известны зависимости; при расчёте проверяются фактические условия кандидата. Наличие двух разных ссылок ещё не доказывает равенство температур. Пока такая проверка не реализована, неподдержанный случай диагностируется, а не считается совпадением.

Единицы и правила равенства условий тоже должны быть явными: 20 °C и 293.15 K могут обозначать одно условие; 20 °C и 15 °C — нет. Допуск сравнения не придумывается UI; он относится к поддержанному контракту величины/условия. Отсутствующее условие отличается от явного «не применимо».

### Предварительная схема и изменяемые настройки

Структура порта известна для конкретной конфигурации ноды до вычисления. Структурная настройка — число продуктов, набор компонентов — может потребовать нового описания. Она меняется в редакторе и инвалидирует сопоставления/план. Обычный численный параметр не должен менять схему посреди пакета. Нулевой выход продукта выражается значением/наличием данных, а не исчезновением объявленного порта.

Статическое описание поставляется с пакетом либо получается от лёгкой операции описания и сохраняется. Если схема зависит от конфигурации, SDK поддерживает получение такой схемы до запуска; это не обязательно запуск кинетики или загрузка всех весов. При подготовке фактический вычислитель подтверждает отпечаток схемы. Сохранённый проект содержит использованное описание для просмотра при отсутствии плагина; это описание не заменяет исполняемую модель.

При отсутствующем плагине можно показать последнюю зафиксированную схему. Но изменение структурной настройки, для которой требуется его операция описания, нельзя выдавать за успешно проверенную новую схему. Она остаётся неподтверждённой до разрешения зависимости. SDK должен получать экспортируемые метаданные и runtime-описание из одного авторского источника, а conformance-проверка выявлять их расхождение.

### Материальная связь и численные данные

Материальное соединение связывает выходной поток с входным портом и содержит список сопоставлений его полей. Произвольное сопоставление свойств не должно незаметно собирать один материал из несвязанных источников. Дополнительная исходная величина может быть явным отдельным входом/назначенным источником с происхождением. Точный UI ручного дополнения потока не меняется этим предложением.

Несколько потребителей могут читать один результат. Это не физическое умножение или разделение расхода. Физический отбор и баланс описывает соответствующая модель/явная схема распределения. Само дерево не определяет, какие его ветви образуют полный состав и что можно суммировать: полнота, основа и область состава объявляются метаданными. Проверяющее правило ядра применимо только к объявленному смыслу; нельзя складывать перекрывающиеся свойства или нормировать частичный анализ до 1.

Данные пакета: `caseIds`, ссылка на схему, колонки полей, присутствие и диагностика. Для численного поля с формой `[C]` пакет имеет форму `[B,C]`; ось кандидатов не равна времени и не равна компонентной оси. Порядок компонентов задаётся описанием. Ошибка строки и отсутствующее необязательное поле различаются. Не все будущие формы данных обязаны поддерживаться первым исполнителем; неподдержанная форма выявляется до вызова модели.

## 8. DDD, Clean Architecture, CQRS: точные обязанности

DDD здесь означает предметную модель с поведением, общей терминологией и явными границами согласованности. `Flowsheet.Connect(...)` проверяет структурные инварианты; `FieldCompatibility` решает предметную часть сопоставления. Application координирует вызовы, не копирует эти правила в каждый обработчик. Типизированные ID и небольшие value objects полезны там, где предотвращают реальную подмену понятий.

`Modeling`, `Studies`, `ExtensionManagement` — первоначальные области кода. В Modeling слово «нода» означает редактируемый экземпляр, в Execution — подготовленную вычислительную операцию; это разные модели с явным преобразованием. Однако Python workers, Units и каждая папка сами по себе не становятся bounded contexts. Границы DDD устанавливаются различием предметного языка и обязанностей, а не желанием получить симметричное дерево `.csproj`.

Внутри сборок организация по задачам: например, `Application/Flowsheets/ConnectFields`, `Application/Runs/StartRun`, `Infrastructure/Projects`, `Infrastructure/Python`. Не нужны каталоги `Managers`, `Helpers`, `Common` с неопределёнными владельцами. Один универсальный `IService`, DI service locator и доступ плагина к контейнеру разрушили бы заявленные границы.

Для редактора рекомендую команды с намерением (`ConnectFields`, `RemoveNode`, `SetParameter`) и отдельные read DTO для дерева, инспектора и результатов. На старте обе стороны могут читать одно согласованное состояние в памяти. Это ограниченное применение разделения команд/запросов; отдельная БД, message broker и Event Sourcing не следуют из него. MediatR также не обязателен.

Undo/redo — самостоятельное поведение редактора: применённое изменение и данные для отмены/повтора. Идентичность удаляемых/восстанавливаемых элементов сохраняется. Отмена удаления ноды возвращает её связи. Запуск внешней модели не становится обратимым из-за команды `StartRun`; `CancelRun` — отдельная операция. Установка пакета и экспорт файла не попадают автоматически в undo графа.

CQRS не участвует в каждом численном вызове. Application один раз создаёт запуск; метод исследования далее обращается к подготовленной Execution-сессии. UI получает ограниченные уведомления о ходе работы и читает нужные результаты, а не обрабатывает событие на каждое число.

## 9. Интерфейсы и жизненный цикл расчёта

### Минимальные порты и их владельцы

Названия ориентировочные, смысл должен сохраниться при выборе сигнатур.

| Порт | Объявлен | Реализован | Нужен для |
| --- | --- | --- | --- |
| `IProjectStore` | Application | Infrastructure/Projects | Открытие/сохранение через независимый формат |
| `IPluginCatalog` | Application | Infrastructure/Plugins | Получение разрешённых пакетов и их описаний; отсутствие зависимости не разрушает документ |
| `IPluginInstaller` | Application | Infrastructure/Plugins | Явная установка/удаление, отдельно от чтения каталога |
| `IRunStore` | Application | Infrastructure/Runs | Хранение снимка, статусов и опубликованных результатов |
| `INodeExecutorFactory`, `INodeSession` | Execution | Infrastructure/Python; тестовый исполнитель; позже адаптер C# | Подготовка экземпляра и многократный вызов модели, не зная её языка |
| `IUnitConversionProvider` | Execution | Простой численный механизм или Infrastructure/Units | Подготовка обычной конверсии без публичной зависимости от библиотеки |
| `IGraphEvaluationSession` | Execution | Execution | Подготовленный граф как вычислитель для одиночного расчёта, перебора и будущего оптимизатора |

Интерфейс появляется из реальной границы с альтернативным механизмом или внешним эффектом. Для каждого record, чистой функции или единственного внутреннего класса интерфейс не нужен. Если потребитель — Execution, порт не помещается в Application: иначе образуется цикл.

### Последовательность запуска

1. Application согласованно читает документ и конфигурацию исследования, проверяет ревизию и выбранные зависимости. Разрешает версии пакетов и источников, собирает диагностические сообщения. Проект может быть сохранён незавершённым; возможность запуска проверяется отдельно.
2. Execution получает независимый `RunSnapshot`: схему, конфигурацию, описания/условия, сопоставления, фиксированные входы, переменные, требуемые выходы и запрос к режиму. Снимок не содержит ссылок на изменяемые коллекции редактора или открытые файлы.
3. При подготовке определяются зависимости, проверяются поля, формы и условия, подготавливаются единицы. Сопоставления по ID разрешаются в численные слоты. Если понадобятся значения динамических условий, их зависимости и проверки включаются в план.
4. Через `INodeExecutorFactory` создаются нужные сессии. Infrastructure запускает worker и доставляет конфигурацию; плагин загружает модель и подтверждает схему. Отчёт о подготовке фиксирует фактические runtime, пакет и артефакты. После частичной ошибки подготовки уже созданные ресурсы освобождаются.
5. Для каждого пакета Execution передаёт значения по зависимостям. Константы и схемы не разбираются заново. Полученные выходы проверяются на соответствие форме и статусам контракта. Проверки области применимости физической модели принадлежат модулю.
6. Завершённые блоки результатов публикуются с `RunId`, `caseId`, стадией и происхождением. Application передаёт их хранилищу и обновляет состояние запуска; UI читает представление нужного объёма.
7. При завершении/ошибке/отмене освобождаются сессии. Терминальный статус записывается отдельно от частичных результатов. Закрытие приложения использует тот же управляемый жизненный цикл.

`ExecutionPlan` сначала может быть обычным списком подготовленных операций. Генерация IL, expression trees, unsafe и shared memory не требуются для выполнения этого контракта. Сам термин «компиляция плана» означает подготовку, а не обязательную генерацию машинного кода.

### Ошибки, отмена и состояние

- Неподдержанная схема/единица, неразрешённое сопоставление — ошибка подготовки с адресом поля. Расчёт не стартует на предположениях.
- Несходимость модели — неуспешный `caseId`; по зависимой ветви распространяется отсутствие корректного результата. Нарушенное ограничение при успешном расчёте — отдельный результат исследования, не exception модели.
- Неверная длина/состав ответа — нарушение контракта пакета. Падение процесса — ошибка сессии. Переназначение режима, повторный вызов или выдача паспортного значения не происходят молча.
- Отмена кооперативна; Python/C++/GPU-вычисление может не обработать её немедленно. Принудительное завершение worker завершает все его сессии и отражается в статусах. Конкретная политика ожидания требует отдельной проверки с моделью; нельзя считать закрытый RPC доказательством остановки расчёта.
- Разделение весов между экземплярами допустимо только по решению автора и при отсутствии смешения изменяемого состояния. По умолчанию один экземпляр не вызывается одновременно.
- Независимые точки не используют скрытое продолжение предыдущего кандидата. Seed и изменяющееся состояние должны быть явными. Stateful/динамические модели потребуют отдельной семантики, а не переименования оси batch в время.
- Память результата после публикации принадлежит читателю/хранилищу по явному договору. В первом варианте допустима копия. Переиспользование буфера не должно менять уже показанный результат; read-only view сам по себе не обеспечивает неизменяемость underlying array.

### Циклы и оптимизация

Предложение первого исполняемого среза — ациклические связи с понятной диагностикой цикла. Это ограничение среза, не определение допустимого НПЗ. Если первый реальный сценарий требует рецикла, до реализации алгоритма нужно сравнить явный итерационный блок с решателем сильно связанных компонентов. Нельзя молча разорвать связь или считать цикл завершённым после одного обхода. Начальные приближения, сходимость и невязки являются частью постановки решателя.

Оптимизатор получает `IGraphEvaluationSession`, описание управляющих переменных и критериев. Он не редактирует `Project` и не вызывает команды UI на каждый кандидат. Постановка исследования живёт в Domain, запуск метода — в Application, оценка схемы — в Execution, конкретный алгоритм — за отдельным интерфейсом метода при его реализации. Он не обязан реализовывать интерфейс установки с материальными портами. Публичное расширение для оптимизаторов добавляется отдельно; callback из Python-оптимизатора потребует протокола с обратными запросами и проверки reentrancy, а не одной добавленной команды worker. Выбор такого механизма сейчас не требуется для расчётного SDK.

Применение режимов FCC следует OWN-09/10. Объявленные модулем режимы остаются обсуждаемой формой; ядро не вводит enum с названиями конкретных моделей. Поиск и проверка используют соответствующие запросы и отдельные записи результатов. Пакетный интерфейс поддерживает B=1; метод, которому следующий кандидат нужен после предыдущего, должен работать корректно, даже если его невозможно эффективно упаковать в большие batch.

## 10. Плагины, SDK и 20 Python-модулей

### Три разные границы

1. Публичный семантический контракт: описание ноды/полей, конфигурация, подготовка, вычисление, ошибки, завершение, версии. Это обязательства Gravia и автора независимо от языка.
2. Протокол переноса: сообщения и кодирование чисел между процессами. Он реализует эти обязательства, но не определяет сам физический смысл поля.
3. SDK языка: удобное описание ноды и обычная функция/класс вычисления плюс служебный worker. Автор модели не обязан самостоятельно писать RPC-сервер или работать с байтовыми дескрипторами.

C# Domain — внутренняя реализация понятий. Входной DTO плагина преобразуется в неё адаптером; .NET assembly с доменными агрегатами не является публичным SDK. Такое разделение не оправдывает ручное ведение четырёх несовместимых схем: нормативное описание контракта, общие fixtures и проверки сериализации должны быть едиными.

Пакет может предоставлять несколько типов нод, определения свойств/единиц и артефакты. Пакет без вычислителя может содержать каталог. Модель, предметный преобразователь, импортёр, оптимизатор и UI-панель не обязаны иметь один универсальный интерфейс. Первый SDK охватывает расчётные ноды и их описания; остальные типы расширения добавляются при конкретном сценарии через отдельные контракты.

### Установка, окружение, процесс и экземпляр

Это четыре разных сущности. [Документация Python venv](https://docs.python.org/3/library/venv.html) описывает окружения поверх базового Python с отдельными зависимостями; окружения следует воспроизводить, а не считать переносимыми копиями. [Import system](https://docs.python.org/3/reference/import.html) подтверждает кэш модулей по именам в интерпретаторе. Из этого не следует возможность загрузить любые конфликтующие версии библиотек вместе простым изменением sys.path.

| Выбор | Самый простой вариант | Рекомендация и цена |
| --- | --- | --- |
| Место установки | Отдельная копия пакета в каждом проекте | Пользовательское версионированное хранилище пакетов; проект фиксирует зависимости. Меньше дублирования, но перенос требует восстановления пакетов. |
| Python | Системный Python пользователя | Управляемая поддержанная версия базового runtime, если зависимости проверенных модулей совместимы. Новые несовместимые требования либо явно не поддерживаются, либо расширяют матрицу runtime; это не обещание одного Python навсегда. |
| Зависимости | Один изменяемый site-packages для всех | Окружение по зафиксированному набору зависимостей и платформе. Не нужно ждать runtime-ошибки, чтобы изолировать его. Идентичные воспроизведённые окружения можно переиспользовать; произвольно «похожие» не объединяются. |
| Worker | Все активные плагины в одном процессе | Для первой надёжной реализации — отдельный долгоживущий worker на активный пакет/окружение в расчётной сессии. Это проще по состоянию, несовместимым импортам и отказам, но увеличивает RAM. |
| Несколько нод одного плагина | Процесс на каждую ноду | Отдельные экземпляры внутри worker, последовательные вызовы. Общие неизменяемые артефакты — ответственность автора. |

Таким образом, **20 установленных плагинов не равны 20 запущенным процессам и не обязательно равны 20 базовым установкам Python**. Но если в одном запуске нужны 20 разных Python-пакетов, предлагаемая простая изоляция действительно может потребовать 20 процессов и отдельных наборов зависимостей. Стоимость памяти честно измеряется. Уменьшение числа процессов за счёт проверенного совместного размещения — отдельное развитие, а не обещание «обычно всё в одном worker».

Предложение о worker на пакет продолжает вариант из [исследования SDK](Плагины%20SDK%20и%20межъязыковое%20выполнение.md); меняет последующее необоснованное обещание ассистента автоматически объединять плагины. У нас ещё нет реализации, поэтому миграции кода нет. Политика установки и изоляции остаётся предложением до обсуждения владельцем.

Проект фиксирует версии и хеши пакетов/описаний/артефактов; запись запуска дополнительно фиксирует разрешённое окружение и платформу. Один lock-файл не гарантирует наличие wheel, драйверов или битовую воспроизводимость чисел. Различные версии можно хранить рядом. Обновление установки не меняет зависимости существующего снимка. Для development-ссылки на изменяемый каталог воспроизводимость обеспечивается зафиксированной копией/хешами входных файлов; иначе ограничение должно быть видно в записи запуска.

### Протокол первого адаптера

Сравнение преждевременно выбранных вариантов:

- JSON через каналы процесса: минимум внешних зависимостей и простой контрольный образец; нужны собственные framing, request ID, отделение логов, пределы сообщений и отмена.
- [gRPC/Protobuf](https://grpc.io/docs/what-is-grpc/introduction/): генерируемые сообщения и готовый жизненный цикл RPC, но свои зависимости и настройки; сам по себе не обещает передачу без копирования. [Отмена RPC](https://grpc.io/docs/guides/cancellation/) требует участия обработчика вычисления и не равна принудительному прерыванию модели.
- Shared memory: может уменьшить копирование, но требует протокола владения, освобождения и обработки падений. Не заменяет управляющие сообщения.

Рекомендую реализовать первый проверочный C#↔Python вызов простым протоколом в изолированном адаптере, а публичную фиксацию транспорта сделать после проверки авторского SDK и размеров реальных пакетов. JSON подходит как baseline, не объявляется ни заведомо непригодным, ни заведомо достаточным. Когда конкретный протокол опубликован, его изменение — версия протокола и совместимый путь перехода, а не прозрачная замена для уже выпущенных сторонних плагинов.

Служебные события и данные проходят backend↔worker; числовые массивы не путешествуют через React. Desktop↔backend имеет отдельный контракт команд/запросов и не повторяет протокол модели.

## 11. Производительность без преждевременного усложнения

Приоритет понятности совместим с тремя недорогими правилами: подготовить схему/единицы один раз; удерживать модель загруженной; передавать доступные независимые точки пакетами. Этого достаточно как исходного дизайна. Автоматический внешний параллелизм остаётся отложенным.

Проверяемое разделение затрат:

```text
T = Tподготовки + сумма(Tмодели + Tобмена + Tконверсий + Tуправления + Tзаписи)
```

Численный пример, **не измерение**: 100 000 точек × 20 последовательных внешних нод = 2 000 000 вызовов при B=1. Если один обмен стоит условные 0,1 мс, это 200 с только фиксированных расходов. При доступном B=256 получится 391 × 20 = 7 820 пакетных вызовов, или 0,782 с той же фиксированной части. Объём переданных данных, время сериализации и время моделей этим делением не исчезают. У адаптивного последовательного метода B=256 может быть недоступен.

Отсюда нельзя ни гарантировать, ни отвергнуть малую цену обвязки. Сравнивать нужно реальную кинетику и быстрый суррогат с теми же входами. Микрозамер `units-dotnet-audit` не измеряет эту величину. Ранее заявленные 40 000 точек/с остаются оценкой владельца по памяти.

Первый сквозной замер после реализации: B=1, 32, 256, 1024; identity-модуль для цены обмена и реальный суррогат для доли затрат; 1 и 20 активных нод; холодная подготовка, прогретые пакеты, суммарное время, RAM и выделения памяти. Это конкретная проверка гипотезы, не условие начать писать предметный код. Численный допустимый бюджет нужно установить с владельцем, а не выдать собственные 10% за требование.

Не предлагаются сейчас общий кэш вычислений, распределённый планировщик и принудительное совместное размещение workers. Кэш особенно опасно вводить без подтверждения чистоты модели и полного набора зависимостей. Результаты прошлого запуска и кэш, который можно использовать для следующего расчёта, — разные вещи.

## 12. Проверка расширяемости конкретными изменениями

| Изменение | Где меняется код/данные | Что проверяем |
| --- | --- | --- |
| Новый FCC-плагин на Python | Пакет + Python SDK; при соблюдении контракта без изменений Domain/Application | Прямой и интегрированный вызов совпадают; два экземпляра не смешивают настройки |
| Новое свойство или обычная единица из независимого пакета | Данные каталога и схема плагина | Нет коллизий по подписям; редактор отображает поле; совместимость не определяется только размерностью |
| Новый вид значения, например новая форма кривой | Явное расширение контракта и поддержка соответствующих читателей | Старый потребитель получает UnsupportedSchema, не неверный массив. Расширяемость не означает поддержку неизвестной структуры без кода |
| rho20 → rho15 | Новый/готовый пакет с нодой, её настройка в проекте | Видны метод и входы; ядро не получает нефтяную корреляцию |
| Переименование поля / перевод | Подписи в пакете или проекте | Сохранились ID, связи и численные результаты |
| Изменение физического контекста при сохранённом ID | Версия описания + миграция сопоставлений | Старое соответствие пересматривается |
| Сохранение в другом файловом формате | Infrastructure/Projects и миграции | Domain и расчётный SDK не изменились; round-trip сохраняет ID и настройки |
| Замена Python IPC | Infrastructure и служебная часть Python SDK, версия wire-протокола | Тот же семантический набор fixtures и численные результаты |
| Новый алгоритм оптимизации | Реализация метода за API вычисления; интеграция в Application | Он не изменяет Project на каждого кандидата; ошибки не теряют смысл |
| Новый desktop-интерфейс | Клиент и при необходимости новые read DTO | Расчёты доступны через тот же Application API |
| Рецикл / динамическая модель | Расширение постановки и Execution, возможно отдельный контракт модели | Явные состояния, критерии сходимости/оси; это значимое расширение, а не обещанная бесплатная замена плагина |

Граница «расширить данными» заканчивается там, где появляется новый смысл, требующий поведения ядра. Нельзя обещать, что абсолютно любая будущая функция подключится без изменения Gravia. Зато каждое такое изменение имеет определённого владельца.

## 13. Проверяемые правила разработки

1. Архитектурные тесты проверяют разрешённый граф ProjectReference и namespace-зависимостей. Domain/Execution не импортируют типы GUI, JSON, ORM, Python или транспорта; Host endpoint обращается к Application. Проверка пакетов .NET дополняет, а не заменяет проверку собственных ссылок.
2. Предметные тесты покрывают различие PropertyDefinition/FieldDescriptor, идентичность, удаление ноды со связями, разные контексты/условия и отсутствие обязательного значения. Сам факт компиляции record не является достаточным тестом.
3. Execution проверяется на тестовом вычислителе: цепь и ветвление, B=1 и B>1, ошибка строки, несоответствующая схема, отмена, изменение проекта во время запуска, неподдержанный цикл, неизменность опубликованных результатов.
4. Общий набор conformance fixtures запускается для C#-адаптера и Python SDK: описание до расчёта, ID/формы, единицы, версии, caseIds, ошибки и жизненный цикл. Структурная JSON/Protobuf-валидация сама по себе не проверяет смысл.
5. Интеграционные тесты проверяют реальный запуск/завершение worker, сериализацию, два экземпляра, отсутствие пакета, сохранение/открытие и явную миграцию. Для модели — сравнение с её исходной проверенной реализацией, а не только с mock.
6. Тесты UI проверяют редакторский сценарий и готовность, RU/EN, light/dark, сохранённую раскладку; библиотека нод не становится источником предметного документа.
7. Новая зависимость/публичное поле/слой обосновываются сценарием и тестом. Для значимых решений сохраняется запись причины и альтернатив. Правила в файлах поддерживаются вместе с кодом.

### Очередь реализации после обсуждения

| Шаг | Результат, который можно показать | Какие части появляются |
| --- | --- | --- |
| 1 | Создать схему с двумя описанными портами; сопоставить поля с разными путями; переименовать; проверить несовпадающие условия и обычные единицы | Domain + предметные тесты. Проверочный набор описаний, ещё без выбранного транспорта |
| 2 | Зафиксировать схему, выполнить пакет на детерминированных C#-вычислителях, сохранить caseIds/ошибку, изменить исходный документ без изменения результата запуска | Execution + тесты; простой численный провайдер единиц |
| 3 | Выполнить тот же сценарий через Python SDK и реальный worker; проверить загрузку один раз, два экземпляра и завершение | Контракт плагина, Python SDK, Infrastructure/Python. Небольшой консольный тестовый host |
| 4 | Открыть/сохранить документ, связать команды редактора, ревизии и запуск с минимальным UI | Application, Infrastructure/Projects, production Host, Desktop |
| 5 | Подключить реальный FCC/суррогат, измерить обмен, проверить исходные контрольные расчёты и сценарий поиска/пересчёта | Реальный пакет, интеграционные проверки; конкретизация API режимов и публичного транспорта |

Application может появиться раньше в каркасе, но её пользовательские правила проверяются на шаге 4. Библиотеки не нужно наполнять выдуманными абстрактными фабриками заранее. Имена и направления зависимостей определены уже сейчас; пустое содержимое будущих разделов не является реализацией.

## 14. Что предлагается согласовать и что остаётся открытым

Предлагается принять пять обязанностей и граф зависимостей из §5, публичный контракт плагина отдельно от Domain, разделение документа/снимка/результата, предварительное описание полей и принадлежность единиц/преобразований из §6–7. Это даст устойчивую карту для разработки.

Отдельные решения, которые не нужно маскировать названиями библиотек:

- допускаются ли в первом срезе условия-ссылки и структурно меняющиеся схемы;
- нужен ли рецикл уже в первом реальном сценарии;
- точный авторский API режимов и первоначальный набор форм значений;
- базовый runtime и политика окружений после проверки зависимостей FCC;
- точный IPC/генератор контракта, формат файлов, GUI-стек и .NET-библиотека единиц;
- сценарий сопоставления большого дерева с владельцем: сведения, которые он реально видит и может подтвердить.

Эти вопросы имеют конкретные места изменения и критерии проверки. Предложение не требует решить их все перед первым предметным тестом, но требует не публиковать неподтверждённые формы как стабильный SDK.
