# Модульная среда моделирования и глобальной оптимизации НПЗ

> Статус: важный исследовательский материал, зафиксированный 2026-09-10. Предложенные архитектурные решения являются кандидатами для обсуждения, а не утверждёнными решениями проекта. Источники и выводы требуют последовательной проверки.


## 1. Что именно ты хочешь построить

Рабочая формулировка проекта сейчас выглядит примерно так:

> **Открытая расширяемая среда для построения технологических схем НПЗ из независимых моделей установок и проведения глобальной, в том числе многокритериальной, оптимизации всей связанной системы.**

Ядро не должно заранее знать, что такое FCC, каталитический реформинг, изомеризация или компаундирование. Они подключаются как **модули / аддоны**.

Первый прикладной сценарий — бензиновый контур:

`FCC → компоненты бензинового пула`
`Reforming → компоненты бензинового пула`
`Isomerization → компоненты бензинового пула`
`прочие потоки → Blending → товарные бензины`

Причём режимы установок являются переменными общей оптимизации, а не заранее фиксированными входами для блока blending.

Это важно: проект не обязан быть «своим HYSYS». Его центр тяжести может быть именно в **глобальной оптимизации сети произвольных моделей**.

# 2. Главный стандарт, который надо изучить: CAPE-OPEN

Правильное название — **CAPE-OPEN**, не CASE-OPEN.

Это практически обязательное чтение перед проектированием собственного plugin API.

CAPE-OPEN создан именно для того, чтобы независимо разработанный Process Modelling Component можно было вставлять в Process Modelling Environment через стандартизованные интерфейсы. Стандарт отдельно рассматривает Unit Operations, Material Objects, термодинамические пакеты, параметры, solver'ы и другие части системы. ([colan.org][1])

### Что особенно важно забрать оттуда

**Unit Operation** имеет порты. Порты бывают входными, выходными и двунаправленными и могут передавать material, energy или information. Параметры установки отделены от портов. ([colan.org][2])

То есть концептуально:

```text
UnitOperation
 ├── Ports
 │    ├── MaterialInput
 │    ├── MaterialOutput
 │    ├── Energy...
 │    └── ...
 └── Parameters
```

Материальный порт связывается не непосредственно с другим реактором, а с **Material Object**. Именно Material Object представляет состояние вещества/потока и обеспечивает стандартную границу между установкой и окружающей средой. ([colan.org][2])

Это очень близко к тому контракту, который нужен твоей платформе.

# 3. Самая важная находка для твоей проблемы с псевдокомпонентами

У CAPE-OPEN есть отдельная спецификация **Petroleum Fractions**, причём её существенно пересмотрели совсем недавно — версия была опубликована в 2023 году.

Она предназначена именно для petroleum/gas applications и рассматривает **pseudo-compounds**, в том числе ситуации с refinery reactors вроде catalytic cracker и hydrocracker. Спецификация позволяет работать с нефтяными свойствами и даже выполнять runtime re-characterization нефтяной фракции — например, менять normal boiling point, molecular weight, specific gravity, critical temperature и другие характеристики псевдокомпонентов. ([colan.org][3])

Для твоего проекта это, возможно, **один из самых важных документов CAPE-OPEN вообще**.

Но есть принципиальная граница: CAPE-OPEN не даёт тебе универсальной магической функции

```text
3 lumps FCC → любые другие 16 lumps
```

и не может автоматически понять химический смысл совершенно разных lumping-схем.

Поэтому я бы сделал это фундаментальным правилом собственной архитектуры:

> **Единым должен быть контейнер потока, а не обязательно химическое пространство состава.**

# 4. Как я бы сейчас проектировал `MaterialStream`

Не надо пытаться создать один гигантский список всех возможных химических компонентов мира.

Гораздо устойчивее разделить **состояние потока** и **представление состава**.

Концептуально:

```text
MaterialStream
{
    stream_id

    state:
        temperature
        pressure
        total_flow
        flow_basis

    composition:
        schema_id
        components[]
        fractions[]

    property_context:
        property_package_id

    properties:
        ...

    metadata:
        ...
}
```

Ключевой элемент здесь:

```text
composition.schema_id
```

Например:

```text
fcc_feed_3_lumps_v1
fcc_products_16_lumps_v1
gasoline_blending_components_v1
pure_components_v1
```

Тогда твоя лабораторная FCC-модель совершенно легально может объявить:

```text
INPUT:
    composition_schema = fcc_feed_3_lumps_v1

OUTPUT:
    composition_schema = fcc_products_16_lumps_v1
```

Это **не нарушение универсальности платформы**.

Наоборот, это честное описание модели.

# 5. Нужен отдельный класс `Translator`

Вот это я сейчас считаю одним из наиболее важных архитектурных решений.

Если установка A отдаёт:

```text
fcc_products_16_lumps_v1
```

а установка B понимает:

```text
gasoline_blending_components_v1
```

ядро **не должно молча угадывать преобразование**.

Должен существовать явный объект:

```text
CompositionTranslator
    source_schema
    target_schema
    transform(...)
```

Причём преобразование может оказаться довольно сложной физико-химической моделью.

Очень приятно, что похожая концепция существует в **IDAES**: у него есть `Translator` для соединения разных property packages. Причём базовый Translator намеренно не придумывает преобразования самостоятельно — если state variables различаются, пользователь должен определить соответствующие constraints. ([idaes-pse.readthedocs.io][4])

То есть твоя архитектура может сделать следующее:

```text
Unit A
  ↓
Stream [schema A]
  ↓
Translator A→B
  ↓
Stream [schema B]
  ↓
Unit B
```

И это намного безопаснее идеи «ядро автоматически переводит любую химию в любую другую».

# 6. Единицы измерения: ответственность ядра

Здесь решение я бы уже считал практически принятым.

**Внутренний canonical representation — SI.**

CAPE-OPEN также определяет для физических свойств base SI units, а параметры имеют dimensionality; значения CAPE-OPEN Parameters возвращаются в SI. ([colan.org][5])

Плагин не должен самостоятельно заниматься хаотичными конверсиями.

Например:

```text
UI:            35 °C
                 ↓
Core:          308.15 K
                 ↓
Plugin A:      хочет K → получает K
Plugin B:      хочет °C → adapter даёт 35 °C
                 ↓
Core storage:  SI
```

Особенно важно хранить **не только unit, но и physical dimension / quantity type**.

То есть:

```text
Pressure != Temperature != MassFlow
```

даже если все три технически представлены `float64`.

Это позволит ядру остановить бессмысленную операцию вроде передачи `5 bar` туда, где ожидается `5 kg/s`.

### Очень полезная идея из FMI

FMI отдельно описывает Unit Definitions через комбинации семи базовых SI-единиц плюс коэффициенты и offsets. Это позволяет импортёру автоматически проверять совместимость и преобразовывать единицы между моделями. ([FMI Standard][6])

Для твоего ядра это отличный референс.

# 8. Property Package должен быть отдельным механизмом

Не надо заставлять каждую установку самостоятельно отвечать на вопрос:

> «А какая плотность этого потока при такой температуре?»

Лучше:

```text
UnitOperation
      │
      ↓ asks
PropertyProvider
      │
      ↓
density / viscosity / Cp / enthalpy / ...
```

Это хорошо совпадает и с CAPE-OPEN, и с IDAES.

В IDAES property package является отдельным слоем. `StateBlock` описывает состояние материала, а общий `PhysicalParameterBlock` содержит параметры модели свойств. Unit models используют этот слой, вместо того чтобы самостоятельно реализовывать всю термодинамику. ([idaes-pse.readthedocs.io][7])

IDAES также поддерживает свойства **as-needed**: необязательно вычислять всё подряд; property можно построить только тогда, когда конкретная модель его запросила. ([idaes-pse.readthedocs.io][8])

Для твоего `required / preferred / optional` это очень хорошая идея.

# 9. Я бы формализовал требования плагина к потоку

То, о чём мы говорили раньше, можно превратить в настоящий API.

Например:

```text
FCCModel requirements

REQUIRED:
    temperature
    pressure
    total_mass_flow
    composition:fcc_feed_3_lumps_v1

PREFERRED:
    density
    sulfur_content

OPTIONAL:
    viscosity
```

Ядро перед запуском делает validation.

Если отсутствует `density`, но подключён PropertyProvider, способный её получить — ядро вычисляет её.

Если отсутствует обязательный состав — модель даже не запускается.

Если отсутствует optional — ничего страшного.

Очень полезно также разрешить альтернативы:

```text
requires one of:

A:
    mass_flow

OR

B:
    volumetric_flow
    density
```

Тогда плагины становятся гораздо менее хрупкими.

# 11. Физическая модель и суррогат тоже не должны быть разными сущностями верхнего уровня

Это особенно важно для твоей идеи.

Можно сделать:

```text
Model
 ├── MechanisticModel
 └── SurrogateModel
```

но для остальной платформы оба реализуют одинаковый computational contract.

Тогда FCC может одновременно иметь:

```text
high_fidelity_model
surrogate_model
```

а Runtime решает, кого вызвать.

Например:

```text
evaluate(mode="fast")
    → neural surrogate

evaluate(mode="high_fidelity")
    → kinetic ODE model
```

Это даст очень красивую основу для оптимизации.

# 12. Твой предполагаемый surrogate workflow

Твоя идея сейчас выглядит так:

```text
устоявшаяся физически обоснованная
кинетическая модель
          ↓
Design of Experiments
          ↓
тысячи/десятки тысяч расчётов
          ↓
Dataset
          ↓
ANN / Kriging / другой surrogate
          ↓
быстрая batch evaluation
          ↓
NSGA-II / другой optimizer
          ↓
Pareto front
          ↓
выбранные решения
          ↓
HIGH-FIDELITY KINETIC MODEL
          ↓
валидация
```

И я бы сразу добавил ещё одну стрелку:

```text
если surrogate ошибся
          ↓
новая high-fidelity точка
          ↓
dataset
          ↓
retrain
```

То есть со временем можно перейти к **active learning / adaptive surrogate refinement**.

Это не обязательно делать в первой версии, но архитектура не должна этому мешать.

# 13. Не позволяй оптимизатору бесконтрольно эксплуатировать surrogate

Это отдельная серьёзная проблема.

Оптимизатор практически гарантированно будет пытаться находить странные точки, где surrogate ошибается в выгодную сторону.

Поэтому каждый surrogate желательно сопровождать:

```text
valid_domain
training_domain
input_bounds
accuracy_metrics
uncertainty_estimate (если доступна)
training_dataset_version
source_model_version
```

И делать различие:

```text
INTERPOLATION
NEAR_BOUNDARY
EXTRAPOLATION
OUT_OF_DOMAIN
```

Особенно важно это для твоего подхода, потому что оптимизатор будет активно исследовать пространство режимов.

# 14. Почему физическая генерация датасета действительно отличается от historical-data surrogate

Здесь находится реальное отличие от статьи 2026 года.

Мы её теперь точно идентифицировали:

**Ren-Chu He, Zhi-Bo Wang, Chao Fang, Zhi Li — “Collaborative optimization of refinery secondary unit scheduling and oil blending for fuel-to-chemical transformation”, Petroleum Science, опубликована online 25 июля 2026 года, DOI `10.1016/j.petsci.2026.07.042`.** ([ScienceDirect][9])

Авторы объединяют **secondary-unit operation/scheduling и product blending** в одной задаче оптимизации — то есть статья действительно очень близка к твоей идее на уровне постановки. ([ScienceDirect][9])

По опубликованному разбору методики, они использовали исторические MES/LIMS/RTO данные примерно за два года для построения **Kriging surrogate models** шести вторичных установок; затем использовали 74-мерную многокритериальную постановку и вариант NSGA-II с Latin Hypercube initialization. Рассматривались две FCC, continuous reforming, delayed coking, residue hydrotreating и hydrocracking. ([eBiotrade][10])

Это очень близко:

```text
secondary units
      ↓
surrogates
      ↓
plant-wide model
      ↓
blending
      ↓
multiobjective optimization
      ↓
Pareto solutions
```

Но источник surrogate у них и у тебя принципиально может различаться.

У них:

```text
REAL PLANT HISTORY
        ↓
Kriging
```

У тебя:

```text
PHYSICALLY GROUNDED KINETIC MODEL
        ↓
systematic exploration of domain
        ↓
ANN / Kriging / etc.
```

Плюс у тебя предполагается high-fidelity revalidation найденных optimum candidates.

Это хорошая и честная точка позиционирования проекта.

# 16. Очень важная новая находка: open-source refinery benchmark

Вот это я бы **обязательно скачал**.

В 2025 году опубликована работа:

**Wenli Du et al. — “A production planning benchmark for real-world refinery-petrochemical complexes”.**

Авторы предлагают открытый industrial-scale benchmark и, что особенно интересно для тебя, используют **port-stream hybrid superstructure** именно ради модульности и generalizability. Модель включает process units, mixers, splitters и blenders. ([arXiv][12])

И главное — у них открыт GitHub с данными и моделями трёх refinery cases, включая GAMS formulation и результаты BARON/ANTIGONE. ([GitHub][13])

Это потенциально отличный источник:

```text
какие сущности нужны для refinery-wide модели
как именуют потоки
как задают связи
какие constraints реально нужны
какие данные нужны optimizer'у
как выглядит industrial-ish test case
```

Плюс его можно когда-нибудь использовать для regression/integration testing твоего ядра.

# 17. DWSIM — главный open-source кодовый референс

DWSIM стоит изучать не только как программу, а именно **как исходный код архитектуры process simulator**.

Его Source Code Guide прямо говорит, что структура проекта была сформирована под влиянием CAPE-OPEN. `MaterialStream` реализует как внутренние интерфейсы DWSIM, так и CAPE-OPEN thermodynamic interfaces. ([GitHub][14])

Кроме того, DWSIM допускает пользовательские Unit Operations и пользовательские calculation routines, в том числе через Python; доступны также custom property/flash calculations. ([dwsim.fossee.org][15])

Поэтому DWSIM тебе полезен для двух разных вопросов:

```text
Как сделать внутреннюю архитектуру?
→ смотреть исходники.

Как дать исследователю подключать свою модель?
→ смотреть custom model / custom unit APIs.
```

# 18. IDAES — возможно, самый полезный референс для архитектуры данных

IDAES немного другой по философии, но некоторые идеи я бы буквально выписывал в отдельный файл.

У него flowsheet состоит из сети `UnitModel`, связанных streams/arcs. Состояние материала описывают `StateBlock`, а property calculations вынесены в property packages. ([idaes.github.io][16])

Особенно хороша мысль:

> state variables должны быть достаточными для полного определения extensive + intensive состояния материала.

IDAES прямо допускает разные наборы state variables в зависимости от property package; фиксированного единственного способа описывать состояние нет. ([idaes-pse.readthedocs.io][17])

Это прямо подтверждает нашу мысль:

> **универсальность не требует, чтобы все модели представляли вещество абсолютно одинаково.**

Нужны хорошо формализованные интерфейсы и translators.

# 19. FMI — смотреть для языконезависимых моделей

Если ты действительно хочешь когда-нибудь получить:

```text
Core = Rust/C#/C++
FCC plugin = Python
Reformer = C++
Old lab model = Fortran
ANN = Python/PyTorch
External proprietary model = binary
```

тебе очень полезно изучить **Functional Mock-up Interface**.

FMI определяет упаковку модели с machine-readable `modelDescription.xml`, exposed variables, types, units и capabilities; возможны Model Exchange, Co-Simulation и Scheduled Execution. В Co-Simulation модель может даже поставляться со своим внутренним solver'ом. ([FMI Standard][6])

Не обязательно делать свою платформу FMI-compatible с первой версии.

Но посмотреть, **как они отделили metadata модели от executable code**, очень полезно.

# 20. Оптимизатор тоже должен быть плагином

После всего разговора я бы оставил это решение.

Ядро не должно знать:

```text
NSGA-II
```

Оно должно знать:

```text
OptimizationProblem
```

Например:

```text
decision_variables
objectives
constraints
bounds
variable_types
evaluator
```

А дальше:

```text
NSGAIIOptimizer
BayesianOptimizer
DifferentialEvolution
ParticleSwarm
GradientOptimizer
WhateverComesIn2030
```

все реализуют:

```text
Optimizer
```

Тогда твой конкретный научный эксперимент с NSGA-II не превращается в пожизненное ограничение платформы.

# 21. Batch evaluation надо сделать частью архитектуры сразу

Это особенно важно из-за нейросетей.

NSGA-II может сформировать, например:

```text
Population = 1024 operating points
```

Плохо:

```text
for x in population:
    surrogate.predict(x)
```

Лучше:

```text
surrogate.predict_batch(population)
```

Тогда ANN можно одним вызовом прогнать на GPU/CPU vectorization.

Поэтому я бы уже в первой версии интерфейса оставил optional capability:

```text
supports_batch = true
```

Это практически ничего не стоит архитектурно сейчас и может дать огромное ускорение потом.

# 22. Разделить `Model`, `Unit`, `Optimizer` и `Execution`

Очень важно не смешать эти понятия.

Я бы мысленно держал такую структуру:

```text
                PLATFORM CORE
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
    Flowsheet     Property      Units/Types
       │
       ↓
 Unit Operation
       │
       ↓
    Model
  ┌────┼─────┐
  ↓    ↓     ↓
ODE   ANN  Kriging
```

Отдельно:

```text
Optimization Engine
        │
        ↓
   evaluates Flowsheet
```

И отдельно:

```text
Execution Backend
    Python
    Native
    External Process
    GPU
    Remote
```

Тогда ANN на PyTorch и старый Fortran solver могут выглядеть для верхнего уровня одинаково.

# 23. Что делать с «3 псевдокомпонента → 16 псевдокомпонентов»

На сегодняшний момент я бы выбрал максимально строгий подход.

Не:

```text
Stream contains universal composition
```

а:

```text
Stream
    └── CompositionRepresentation
```

Например:

```text
CompositionRepresentation:
    schema_id
    basis: MASS | MOLE
    components:
        id
        value
```

Каждый псевдокомпонент должен иметь стабильный machine-readable ID и metadata.

Например:

```text
fcc.lump.heavy_paraffins.v1
```

а не просто display string:

```text
"Heavy stuff 1"
```

Потом можно добавить metadata:

```text
normal_boiling_point
molecular_weight
specific_gravity
carbon_number_range
aromaticity
...
```

где они известны.

Это хорошо сочетается с идеями CAPE-OPEN Petroleum Fractions. ([colan.org][3])

# 24. Никаких скрытых преобразований состава

Это правило я бы даже сделал частью философии проекта:

```text
Units conversion:
    automatic

Composition-model conversion:
    explicit
```

Потому что:

```text
bar → Pa
```

математически однозначно.

А:

```text
16 FCC lumps → 8 gasoline blending components
```

может содержать химические предположения, корреляции, эмпирику и потерю информации.

Следовательно, первое является инфраструктурой.

Второе является **моделью**.

Это важнейшее различие.

# 25. Provenance данных тоже лучше заложить сразу

Для каждого вычисленного свойства полезно когда-нибудь уметь ответить:

```text
Откуда взялось это значение?
```

Например:

```text
density:
    value = ...
    source = PengRobinsonPackage
    model_version = 2.3

RON:
    value = ...
    source = gasoline_blending_model
    model_version = 0.4

    value = ...
    source = ANN_surrogate
    training_dataset = dataset_2027_04

```

Для исследовательского ПО это потом окажется невероятно полезным для воспроизводимости.

# 28. Какой первый vertical slice я бы теперь сделал

После нашего разговора я слегка изменил прежнюю рекомендацию.

Не Mixer.

Сначала сделать инфраструктурный proof-of-concept:

```text
Source
  ↓
MaterialStream
  ↓
DummyUnit Plugin A
  ↓
MaterialStream
  ↓
DummyUnit Plugin B
  ↓
Sink
```

Но уже обязательно должны работать:

```text
plugin discovery
ports
stream contract
units
dimensions
required/optional properties
composition_schema
validation
serialization
errors
```

Причём DummyUnit A может специально выдавать:

```text
schema_A
```

а B принимать:

```text
schema_B
```

и между ними вставляется:

```text
Translator A→B
```

Неважно, что химия пока выдуманная.

Ты проверишь **самую рискованную часть архитектуры**, ничего не зная о нефтехимии.

После этого я бы подключал настоящее **компаундирование бензинов** как первую серьёзную модель.

А потом уже FCC kinetic model.

# 29. Где, судя по текущему research, действительно может быть твоя ниша

Отдельно уже существуют:

```text
CAPE-OPEN → модульные process components
DWSIM → open process simulator
IDAES → modular process modeling + optimization
Aspen/HYSYS → мощное промышленное моделирование + custom models
NSGA-II → refinery/blending optimization
surrogates → ускорение дорогих моделей
plant-wide optimization → огромная литература
```

Aspen даже официально позволяет создавать custom high-fidelity equipment models через Aspen Custom Modeler и вставлять их в Aspen Plus/HYSYS; у HYSYS существуют extensibility mechanisms для custom Unit Operations, property packages и kinetic reactions. ([AspenTech][18])

То есть **ни одна из отдельных технологий сама по себе не является новизной**.

Но комбинация, которую имеет смысл исследовать, такая:

```text
OPEN SOURCE
        +
language/model agnostic plugin system
        +
explicit composition schemas + translators
        +
mechanistic / historical / surrogate models interchangeable
        +
high-fidelity ↔ surrogate dual execution
        +
batch surrogate evaluation
        +
optimizer plugins
        +
global multiobjective plant-network optimization
        +
Pareto front
        +
automatic high-fidelity validation
        +
eventual adaptive surrogate refinement
```

Вот это уже нормальная самостоятельная архитектурная концепция.

# 30. Один важный принцип для всего проекта

Я бы записал его прямо в README будущего репозитория:

> **The platform standardizes communication between models, not the internal mathematics of the models.**

Установка может внутри иметь:

```text
ODE
DAE
empirical equations
LP
MINLP
ANN
Gaussian Process / Kriging
lookup tables
external executable
```

Ядру всё равно.

Оно отвечает за:

```text
что входит
что выходит
что это физически означает
единицы
совместимость
соединения
validation
execution
optimization
provenance
```

А конкретный плагин отвечает за:

```text
как получить output из input
```

Мне кажется, это сейчас самый правильный фундамент твоей задумки.
