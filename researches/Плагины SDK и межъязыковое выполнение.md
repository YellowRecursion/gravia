# Плагины, SDK и межъязыковое выполнение

Вопрос: как автор создаёт расширение Gravia, пользователь добавляет его в проект,
а ядро вызывает модели на разных языках с приемлемыми накладными расходами?

Дата: 11 сентября 2026; актуализировано 20 октября 2026. Статус: транспорт,
жизненный цикл и границы первого этапа приняты владельцем; точный протокол, API
и предметный контракт нод разрабатываются по шагам. Модели, плагины и
межпроцессный обмен не запускались; производительность не измерена.

## Принятые решения

- Первый способ исполнения плагинов — внешние процессы. Готовый SDK сначала только для
  Python; нативные C# и WASM предусматриваются архитектурно, реализуются
  позднее. MATLAB-плагин не должен быть затруднён.
- Уточнение 20 октября 2026: в будущем нужны .NET DLL непосредственно внутри
  Gravia и ноды с пользовательским Python-кодом (OWN-49/50). Прежнее ограничение
  только внешними процессами не относится ко всем будущим способам исполнения.
- Gravia не знает язык плагина. Она работает со способом запуска, подключением
  и протоколом; запуск, подключение и языковые операции задаёт плагин.
- Управляющий обмен — TCP + JSON. Большие данные — memory-mapped files /
  shared memory. Gravia слушает loopback, плагин подключается клиентом.
- Первый протокол — JSON-RPC 2.0, одно сообщение на строку UTF-8. Первый
  проверяемый срез: подключение, `hello` и `log`; ноды и `describe` позднее.
- Управляемому плагину адрес передаётся аргументом командной строки. При ручном
  подключении Gravia показывает адрес. Порт выбирается заново при каждом запуске
  Gravia.
- Плагины подключаются и включаются отдельно для проекта. Путь к папке внутри
  проекта хранится относительно корня проекта. При открытии проекта включённые
  управляемые плагины запускаются автоматически; при закрытии проекта плагины
  выключаются. Несколько копий Gravia работают одновременно для разных проектов.
- Плагин — папка с `plugin.json`: ID, версия, команда запуска и аргументы.
- Первый этап возможностей — только ноды. Настройки приложения/проекта,
  оптимизаторы, единицы и определения свойств плагинами не добавляются;
  их будущий API не утверждён. Интерфейс ноды Gravia строит по `describe`.
- Расчётные модели — stateless-функции. Внешний контракт не требует живого
  экземпляра модели для ноды; входы, параметры и модельные данные определяют
  результат вызова. Веса и подготовленные структуры могут переиспользоваться
  внутри процесса.
- Пакетный API обязателен для тысяч оценок и больших матриц; одиночные вызовы
  также входят в сценарий. Внутренняя векторизация решателя не требуется.
- Контракт нод поддерживает переменное число подключённых материальных потоков,
  например входных труб компаундирования. Это не настройка количества портов;
  представление в описании и UI не выбрано.
- Python и MATLAB-среды поставляются с плагинами, а не с базовой Gravia.
- Обновление разрабатываемого плагина — явная кнопка. Управляемый процесс
  перезапускает Gravia и после подключения вызывает `describe`; внешний процесс
  перезапускает пользователь, после нового соединения Gravia вызывает `describe`.
  Автоматическое наблюдение исходников, hot reload и копирование снимков
  не используются.
- В одном проекте активно одно исследование; это не ограничивает внутренний
  параллелизм расчёта.
- NSGA-II обязателен для грантовых сценариев 2028 года, но не объявляется
  единственным оптимизатором продукта.

## Что проверено по источникам

- **Dakota.** Различает модель, интерфейс и метод; внешний драйвер запускает
  программу и обменивается файлами, direct — вызывает вычислитель в памяти;
  batch передаёт несколько оценок за запуск; Python-интерфейс и SDK скрывают
  часть обмена; C++ plugin interface — интеграция с библиотекой, не установщик
  пакетов. [Models](https://snl-dakota.github.io/docs/6.24.0/users/usingdakota/inputfile/model.html),
  [Interfaces](https://snl-dakota.github.io/docs/6.24.0/users/usingdakota/inputfile/interfaces/simulationinterfaces.html),
  [Batched evaluations](https://snl-dakota.github.io/docs/6.24.0/users/usingdakota/inputfile/interfaces/batchedevaluations.html),
  [Python](https://snl-dakota.github.io/docs/6.24.0/users/usingdakota/advanced/advancedsimulationcodeinterfaces.html#python),
  [dakota.interfacing](https://snl-dakota.github.io/docs/6.24.0/users/usingdakota/inputfile/interfaces/dakotainterfacing.html).
- **pymoo.** Ask/tell разделяет получение кандидатов, внешнюю оценку и возврат
  результатов. Применим к большинству эволюционных методов, но не ко всем
  алгоритмам. [NSGA-II](https://pymoo.org/algorithms/moo/nsga2.html),
  [ask/tell](https://pymoo.org/algorithms/usage.html).
- **SciPy least_squares** принимает вектор невязок, поддерживает границы и
  разные способы получения якобиана. Интерфейс обратной задачи не следует
  сводить к одному скалярному критерию.
  [least_squares](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.least_squares.html).
- **OpenMDAO MetaModelUnStructuredComp** задаёт обучающие входы/выходы и метод
  аппроксимации явно; разные выходы могут использовать разные суррогаты.
  [Metamodel](https://openmdao.org/newdocs/versions/latest/features/building_blocks/components/metamodelunstructured_comp.html).
- **MATLAB.** Есть `tcpclient`, `jsonencode`/`jsondecode` и `memmapfile`, чего
  достаточно для клиентского адаптера без реализации TCP-сервера. `jsondecode`
  преобразует недопустимые имена полей в идентификаторы MATLAB, поэтому имена
  полей сообщений фиксированные, а ID передаются строками. `jsonencode`
  по умолчанию превращает NaN/Inf в null; численная семантика задаётся явно.
  [tcpclient](https://www.mathworks.com/help/matlab/ref/tcpclient.html),
  [jsonencode](https://www.mathworks.com/help/matlab/ref/jsonencode.html),
  [memmapfile](https://www.mathworks.com/help/matlab/ref/memmapfile.html).
- **JSON-RPC 2.0** задаёт запросы, ответы, уведомления и ошибки независимо от
  транспорта, но не задаёт границы сообщений в TCP и формат числовых буферов.
  [Спецификация](https://www.jsonrpc.org/specification).
- **OpenMDAO, Heath/Gray, NASA Glenn, 2012** — свидетельство разделения
  вычислителя и организации исследования; не подтверждает наш транспорт.
  [PDF](https://openmdao.org/pubs/Heath_Gray-_2012_-OpenMDAO_Frameork_for_Flexible_Multidisciplinary_Design_Analysis_and_Optimization_Methods.pdf).
- **.NET** загружает плагины через `AssemblyLoadContext` и
  `AssemblyDependencyResolver`; это изоляция загрузки, не отдельный процесс.
  [Пример](https://learn.microsoft.com/en-us/dotnet/core/tutorials/creating-app-with-plugin-support).
  Python.NET технически возможен, но требует управления runtime и GIL;
  [документация](https://pythonnet.github.io/pythonnet/dotnet.html).
- **Среды.** CPython можно поставлять частной копией
  ([Windows](https://docs.python.org/3/using/windows.html#the-embeddable-package));
  MATLAB запускается без desktop через `-batch`
  ([Windows](https://www.mathworks.com/help/matlab/ref/matlabwindows.html));
  Compiler создаёт standalone-приложение, для него нужен соответствующий Runtime
  ([Compiler](https://www.mathworks.com/help/compiler/create-application-using-standalone-application-compiler-app.html),
  [Runtime](https://www.mathworks.com/help/compiler/install-the-matlab-runtime.html)).

## Сценарии, которые проверяют границы

| Сценарий | Пользователь задаёт | Система вычисляет | Проверка |
| --- | --- | --- | --- |
| Совместная оптимизация | Схему, переменные, цели, ограничения, метод | Оценки наборов кандидатов и итоговый набор | Соответствие кандидатов оценкам, допустимость, контрольные расчёты |
| Обратная задача кинетики | Модель, данные, параметры, правило невязки | Предсказания, невязки, параметры | Сопоставление с наблюдениями; критерии качества открыты |
| Кинетические кривые | Начальные условия, параметры, координату | Значения вдоль координаты | Контрольные точки и численная проверка модели |
| Построение суррогата | Ноду/фрагмент, входы, область, выходы, бюджет | Выборку, обученный артефакт, проверку | Отложенные данные и дополнительные случаи |

Точные модели, данные и критерии приёмки не выбраны. Протокол должен различать
пакет независимых кандидатов, набор опытов и точки одной кривой: наличие массива
само по себе не означает независимость элементов.

## NSGA-II и пакеты

Возможны два способа взаимодействия с внешним алгоритмом: явный ask/tell
(алгоритм выдаёт кандидатов, Gravia считает и возвращает оценки) и выполнение
алгоритма до завершения с callback-вызовами оценки через протокол. Для NSGA-II
предлагается ask/tell; для библиотек с обычной callback-функцией, включая
SciPy least_squares, естественнее второй способ. Выбор не утверждён.

Кандидат имеет стабильный ID; ответ содержит цели, ограничения и статус.
Ошибка модели не кодируется произвольным большим числом вместо результата.
Размер пакета не фиксируется размером популяции; уже оценённых родителей
не требуется считать заново. Состояние алгоритма сохраняется между шагами.

Номинальное число оценок NSGA-II: `P + (G − 1) × O`; при `P = O = 256` и
`G = 200` это 51 200 оценок и около 200 запросов, если популяция помещается
в пакет. Следующее поколение нельзя передать вместе с предыдущим.

Ориентир владельца — около 40 000 точек/с для суррогата, то есть 6,4 мс на
256 точек и 0,64 мс на 10% накладных расходов. Это оценка по памяти,
не измерение Gravia.

## Stateless-модели: проверка по исходникам

- `fcc_model.py`: конструктор хранит catalyst/MW и готовит индексы; `predict`/`run`
  заново создают `w0`/`n0`, `k` и интегрируют. Состояния установки между
  независимыми вызовами нет.
- `fcc_bench_utils.py`: `init_worker` создаёт один `FCCKineticModel` на процесс
  и использует его для разных строк с новыми входами.
- `fcc_surrogate_model.py`: predictor загружает scaler/state_dict один раз;
  `predict` имеет пакетную ветку и обрабатывает матрицу одним вызовом сети.
- `calc2.m`: globals, чтение/запись файлов и `pause`; текущий вызов не является
  изолированной функцией и требует адаптации.

Вывод: обязательные операции создания/удаления экземпляра модели на ноду
внешним контрактом не обоснованы. Конфигурация передаётся с вызовом; загрузка
весов и подготовка структур остаются внутренней деталью процесса.

## Протокол первого среза

- TCP, loopback, UTF-8, одно сообщение JSON-RPC 2.0 на строку.
- Gravia слушает; плагин подключается. Направление соединения не равно
  направлению запросов.
- `hello` (запрос плагина): `protocol`, `id`, `version`. Gravia сверяет ID
  с ожидаемой записью и версию протокола; при несовпадении отвечает ошибкой,
  закрывает соединение и показывает состояние «Ошибка».
- `log` (уведомление): `level`, `message`. Категория журнала выводится из ID
  плагина. stdout/stderr процесса служат диагностикой запуска и падения.
- Управляемый режим: Gravia запускает процесс и передаёт адрес аргументом.
  Ручной режим: пользователь запускает процесс с показанным адресом.
- Аутентификация в первом срезе не вводится; доступ ограничен loopback.

## Открытые вопросы

- Смысл `describe` и его связь с инициализацией; можно ли вызывать повторно.
- Схема описания ноды: порты, переменное число потоков, свойства, единицы,
  локализация; как UI строит форму.
- Формат числовых буферов, владение, освобождение и поведение при падении.
- Авторский API SDK: что скрывает SDK, как проверять плагин через Gravia,
  как готовить пакет.
- MATLAB-адаптер: подключение к уже открытой сессии, обновление функций.
- Поставка сред: версии Python/MATLAB, переиспользование, установка на чистой
  машине.
- Адресация при нескольких копиях Gravia и ручном подключении.
- Поведение при изменении исходников во время расчёта; по указанию владельца
  пока не проектируется.

## Расширение способов исполнения: DLL и Python-код в ноде

Вопрос: какую границу предусмотреть сейчас, чтобы добавить .NET DLL внутри
Gravia и программируемую Python-ноду без изменения предметного контракта?
Дата: 20 октября 2026. Статус: будущие сценарии подтверждены владельцем;
следующее устройство — предложение для обсуждения. Прототип не запускался,
стоимость вызовов и локальность изменений экспериментально не проверены.

### Сценарий и проверка

Пользователь подключает готовую модель либо добавляет Python-ноду и задаёт
код, входы, выходы и параметры. Gravia получает описание ноды, проверяет
соединения и передаёт входные данные для одиночного или пакетного расчёта.
Модель возвращает значения и диагностику. Проверка: согласованный численный
пример, соответствие результатов точкам пакета, ошибки отдельных точек,
одинаковые результаты при одинаковых входах независимо от предыдущих вызовов.
Для DLL отдельно проверяется вызов внутри процесса без TCP-сериализации.
В этом сценарии пользователь — автор кода; обычное использование готовой
модели не должно требовать написания Python.

### Сравнение вариантов

| Вариант | Достоинство | Цена и соответствие требованиям |
| --- | --- | --- |
| Все реализации оборачивать внешним процессом и единым RPC | Самый простой: один способ подключения; DLL загружает отдельная программа | Сохраняет первый срез, но не покрывает OWN-49: DLL должна уметь работать непосредственно внутри Gravia |
| Общие контракты возможностей и сменные адаптеры исполнения | Процессный и внутрипроцессный варианты предоставляют одинаковую семантику нод; транспорт остаётся деталью адаптера | Требует контракта жизненного цикла и проверок согласованности адаптеров; предварительно предпочтителен по OWN-18/49 |

Минимально различаются две оси: **что предоставляет расширение** и **как оно
подключается/исполняется**. Первый контракт возможности — ноды (OWN-44/46).
Позднейшие настройки или оптимизаторы получают свои контракты при разработке
сценариев (OWN-34), а не обязательные пустые методы каждого плагина.

Предлагаемые обязанности, без утверждения имён интерфейсов и новых сборок:

- Управление подключениями проекта: хранение ссылок, включение, выключение,
  состояние; необходимо по OWN-41/42/48. Не предполагает наличие PID или сокета.
- Адаптер исполнения: активация, получение доступных возможностей, освобождение
  ресурсов; процессный адаптер владеет TCP/JSON-RPC и управляемым процессом,
  будущий .NET-адаптер — загрузкой сборки и прямыми вызовами (OWN-28/30/49).
  Ручной процесс подключается через тот же процессный адаптер, но имеет другого
  владельца процесса. Обещать принудительную отмену или выгрузку одинаково для
  всех адаптеров нельзя; точная семантика требует отдельного обсуждения.
- Контракт нод: описание и вычисление; данные, смысл ошибок и одиночная/пакетная
  семантика общие, способы передачи буферов могут различаться (OWN-04/14/36/46).
  TCP hello и завершение процесса не входят в предметный контракт ноды.
- Python-нода предварительно может предоставляться обычным Python-плагином:
  он принимает код и его описание, выполняет в своей среде и возвращает
  результаты (OWN-29/50). Наличие ноды не обосновывает отдельный процесс на
  каждую ноду или обязательный Python в базовой поставке Gravia.

Ядро управляет проектом, проверяет общий контракт и передаёт данные. Модуль
определяет физику, вычислительный метод и внутреннее переиспользование ресурсов.
Пользователь выбирает модель, задаёт параметры и связи; в программируемой ноде
также отвечает за собственный код и объявление его входов/выходов. Решение о
конкретной химии не переносится в загрузчик или ядро (OWN-10/12/18).

### Проверенные источники и границы вывода

- [.NET: создание приложения с плагинами](https://learn.microsoft.com/en-us/dotnet/core/tutorials/creating-app-with-plugin-support):
  отдельная сборка публичного контракта, AssemblyLoadContext и
  AssemblyDependencyResolver. Это основание отделить .NET-контракт от внутренних
  реализаций Gravia; загрузчик сборок не заменяет управление проектом и не
  обеспечивает процессную изоляцию. Поддержка нативного C ABI этим не доказана
  и владельцем сейчас не запрошена.
- [AmsterCHEM: примеры Python Unit Operation](https://www.amsterchem.com/pythonunitoperationexample.html)
  и [редактор/API](https://www.amsterchem.com/pythonunitoperationhelp.html):
  пользователь задаёт Configure/Calculate, порты и параметры, проверяет скрипт
  в редакторе. Это подтверждает существование предметно близкого рабочего
  процесса; термодинамическая модель источника не переносится в Gravia.
- [ParaView: Programmable Filter](https://docs.paraview.org/en/latest/ReferenceManual/pythonProgrammableFilter.html):
  пользователь задаёт тип выхода и код обработки подключённых данных; в
  клиент-серверном варианте код исполняется на сервере. Применимый принцип —
  место ввода кода не определяет место исполнения. Модель данных VTK нам не нужна.
- [Heath/Gray, NASA Glenn, 2012](https://openmdao.org/pubs/Heath_Gray-_2012_-OpenMDAO_Frameork_for_Flexible_Multidisciplinary_Design_Analysis_and_Optimization_Methods.pdf):

и динамическое изменение схемы. Не выбраны ABI/версионирование .NET-контракта,
политика выгрузки DLL и общий API отмены. Предложение не исключает обязательный
