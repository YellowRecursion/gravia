# Плагины и SDK

Дата: 11 сентября 2026 года. Статус: начало обсуждения; архитектура, имена и API не утверждены.

Вадим предложил в этом чате закрыть неопределённость по созданию и добавлению плагинов, API/SDK, разным языкам и производительности, изучить решение Dakota и выбрать между терминами плагин/нода/модуль. Уточнил объём: «Общая система расширений, сначала модели».

Проверена официальная документация Dakota 6.24 по модели, внешнему и прямому вызову, Python и пакетам; раздел библиотечной интеграции прочитан по доступному latest_release. Обнаружены разные пути: внешний драйвер с файлами, прямой вызов, встроенный Python с NumPy и пакетами. `dakota.interfacing` скрывает часть различий обмена от автора драйвера. Слово plugin в библиотечном API Dakota не означает готовую систему установки пакетов для Gravia.

Подготовлено [сравнение и предложение](../researches/Плагины%20SDK%20и%20межъязыковое%20выполнение.md): плагин — единица установки; нода — экземпляр на схеме; модель — вычислительный компонент; отдельная сущность Module пока не нужна. Общий пакет может регистрировать разные возможности с отдельными контрактами. Первым подробно рассматривается контракт модели и SDK C#/Python.

Сравнены внешний CLI, выполнение внутри ядра, все модели в рабочих процессах и прямой C# плюс постоянный внешний процесс. Последний вариант предложен при условии выбора .NET, с общим предметным API. Для проверки транспорта сопоставлены простой JSON через stdio и gRPC/Protobuf; выбор остаётся открытым до обсуждения и измерений. Показаны операции подготовки, проверки, пакетного вызова и завершения, предложен сценарий установки и фиксации версий.

Главная проверяемая неизвестность — доля расходов межъязыкового обмена у реального быстрого суррогата. 40 000 точек/с — прежняя оценка владельца по памяти. Условный расчёт для 256 точек: 6,4 мс модель и 0,64 мс дополнительного времени при предлагаемом бюджете 10%. Ни эти времена, ни пригодность транспорта не измерены. Новых программных экспериментов и вызовов моделей не выполнялось. Продуктовые документы не изменены; фиксация исследования не означает согласование API.

## Уточнение поставки сред и версий

Владелец возложил сборку MATLAB-модели на автора плагина и потребовал совместить простой SDK с ограниченным числом поставляемых сред. После предложения одной версии Python и одного выпуска MATLAB Runtime попросил выбрать конкретные версии.

Предложены CPython 3.13.15 (обычный, с GIL) и MATLAB Runtime R2026a (26.1), первичная проверка дистрибутивов — Windows x64. Python 3.14.7 также имеет готовые сборки проверенных научных библиотек; он не отвергнут как несовместимый. Предпочтение 3.13 — консервативная база, не результат benchmark. Проверены метаданные PyPI и официальный список Runtime; готовые модели не запускались. Точный Update Runtime предстоит зафиксировать с учётом сборки автора плагина, номер не придуман. Детали и источники добавлены в существующее исследование. Номера версий ещё не подтверждены владельцем, установка не выполнялась.

В последующем обсуждении владелец указал, что единый R2026a заставляет авторов получать Compiler именно этого выпуска, а trial не решает постоянную разработку. Ассистент признал выбор обязательного R2026a преждевременным и отозвал эту рекомендацию. В исследовании сохранены исходные основания и причина пересмотра. Заново сопоставлены единый Runtime, поставка нужной среды с плагином и перенос модели; предложен необязательный MATLAB-вычислитель с зависимостью плагина. Политика ещё обсуждается. Пользователь скомпилированного плагина не обязан покупать или обновлять полный MATLAB: ему нужен соответствующий бесплатный Runtime.

## Примеры на реальных моделях и локализация

Вадим назвал пример делителя слишком отвлечённым, потребовал учитывать FCC, MATLAB-риформинг и входы будущего блендинга. Уточнил локализацию: en/ru/… с минимум одним языком от автора. Это требование внесено в OWN-03 и продукт, отдельно от обязательных RU/EN самой Gravia; точный fallback остаётся предложением.

Повторно прочитаны реальные predict FCC/суррогата, составы продуктов, MATLAB-выделение X6…X37, таблица компонент и описание файлов; прочитан Model_Description блендинга. Подготовлены [эскизы API на этих данных](../researches/Примеры%20API%20FCC%20риформинг%20и%20блендинг.md): словари локализации, Python-вызов готовой FCC и адаптер пяти продуктов, пакет суррогата, C#-преобразование конечного MATLAB-результата и требования блендинга. SDK не реализован, реальные модели не запускались.

Показано разделение: плагин производителя знает свои компоненты, потребитель задаёт требуемые свойства, пользователь выбирает паспорта/модели недостающих свойств. Граница ядра не расширяется химическими отображениями. Отмечены неоднозначные основы входов блендинга (mass/volume, ppm), условные поля кислорода/i-C4, отдельные цена и доступность. Риформинг требует неинтерактивного вызова с конечным состоянием до прореживания экспорта. Дополнительное предостережение в примере: нельзя добавлять положительный паспортный O к уже нормированным P/I/N/A=1 без согласования всего состава. Эти детали пока проект, не согласованная архитектура или готовая интеграция.

## Совместимость за пределами ИОЧ: масштаб НПЗ

В последующем диалоге владелец уточнил ответственность: расчёт ИОЧ обеспечивает автор предоставляющего его плагина, а не пользователь через собственную формулу и не ядро Gravia. Повторно проверен `calc2.m`: риформинг уже вычисляет `ONRM_rif` из `ON.txt` и массового состава продукта. Блендинг потребляет готовые свойства; назначать его универсальным источником ИОЧ входных потоков было ошибкой ассистента. Ручной ввод серы в инспекторе выходного потока владелец принял как сценарий; понятие выбора «паспорта» без конкретного интерфейса отверг как абстрактное. Формат импорта такими репликами не утверждён.

Идея общего словаря свойств с ручным сопоставлением нестандартных полей владельца не устроила. Он потребовал сравнить несколько направлений на разных установках, свойствах, составах и системах единиц. Подготовлен [разбор с 36 случаями](../researches/Совместимость%20свойств%20и%20потоков%20разных%20моделей%20НПЗ.md): от точного пересчёта расхода до сухой/влажной основы газов, разных перегонок, псевдокомпонентов, опор энтальпии и запаса против расхода. Использованы CAPE-OPEN, FMI, QUDT, IDAES, ASTM, NIST, EIA/EPA и свидетельства практиков AFPM. Арифметические примеры проверены отдельно; модели и GUI не запускались.

Сравнены свободное сопоставление, общие определения, структурированное описание величин и договорённости о целых представлениях потоков. Вывод исследования: распознавание смысла, получение требуемого представления и применимость источника — разные задачи. Это уточняет пространство обсуждения, но не утверждает архитектуру. Действующий проект материального контракта оставлен без изменений.

## Проверка системы единиц по реальным реализациям

После обсуждения расширяемых PropertyDefinition и единиц Вадим попросил остановить проектирование SDK и проверить чужие реализации. В существующий [разбор совместимости](../researches/Совместимость%20свойств%20и%20потоков%20разных%20моделей%20НПЗ.md) добавлено сравнение исходников DWSIM, UnitsNet maintenance/v5, документации Pint 0.25, Modelica 3.6 и FMI 3.0.2. Различены готовый каталог с явными конверсиями, алгебра составных единиц и типизированный каталог. Пересчёт через опорную единицу подтвердился как практикуемый подход; простая замена строки объектом не решает расширяемость. Строковые выражения могут быть полноценным вводом для механизма единиц. Единицы вычисления и отображения нужно рассматривать отдельно.

Предварительно предложено исследовать реестр с алгеброй единиц из-за требования пользовательских расширений. Библиотека и контракт не выбраны, спецификации не изменены. Выполнено чтение документации и кода; интеграционные эксперименты и замеры не проводились.

### Согласование ответственности и выполнения пересчёта

Вадим выбрал второй из обсуждённых вариантов: плагины явно объявляют свои единицы, Gravia готовит пересчёт к единицам получателя. Отдельно подтвердил, что ненужный перевод не выполняется. Решение внесено в продукт и OWN-11: подготовка вне цикла оптимизации, в проходах только необходимые численные преобразования, тождественные операции исключены. Это уточняет старый проект v0.1 с приведением величин адаптерами к каноническим единицам; не утверждает новый формат данных или библиотеку. Обсуждавшиеся 100 000 проходов — сценарий будущего измерения, не выполненный benchmark. Реализация не менялась.

### Предметная проверка и C# вместо преждевременного выбора системы

Владелец прямо отверг принятие предложенной системы единиц без доказательств на таблице свойств НПЗ и потребовал рассуждать в C#. Уточнены статусы в продукте и OWN-11: согласовано поведение пересчёта, механизм не выбран. Подготовлен [разбор всех 36 случаев с C#-экспериментом](../researches/units-dotnet-audit/README.md). Сопоставлены UnitsNet 5.75.1, EngineeringUnits 2.2.143 и минимальный численный исполнитель известных линейных преобразований. Запуск: .NET 10.0.10 / SDK 10.0.302, Windows x64, Ryzen 5 4600H.

Таблица выявляет семантику, опоры, фазу, метод, формы данных и зависимости текущего прохода, которые не покрывает обычный конвертер. °API — контрпример универсальности ax+b; массовая/мольная доля — контрпример достаточности размерности. У EngineeringUnits воспроизведено ограничение API температурных разностей: obsolete-конструктор вернул 0 вместо 10 K, а интерпретация разности как Temperature даёт неверное представление перепада в °C/°F. Ограничения сохранены, не объявлены исправленными; 39 остальных численных проверок прошли.

Медианы 7 прогретых измерений на 100 000 значений: подготовленный double-цикл 0,0431 мс / 0 байт, типизированный UnitsNet 1,8309 мс / 0 байт, динамический enum-путь 5,106 мс / 8 000 000 байт, EngineeringUnits Density 84,9193 мс / 10 400 000 байт. Подготовленная обработка 2 000 000 значений — 1,8924 мс / 0 байт. Это измерение синтетической конверсии одной величины, а не оптимизатора, модели, IPC или полного графа. Библиотека, SDK и бюджет затрат по этим данным не утверждены. Исходные модели и продакшен-код не менялись.

## 12 сентября: целостный проект для обсуждения реализации

Владелец попросил собрать понятную картину сущностей, конвертеров, каталогов и использования плагинами, достаточную для начала программирования. Подготовлен [проект контракта свойств, единиц и преобразований](../researches/Контракт%20свойств%20единиц%20и%20преобразований%20Gravia.md). Предложены отдельные определения свойства/единицы, поля портов и числовые буферы, InputBinding, операции PropertyTransform и подготовленный ExecutionPlan. Каталоги поставляются локальными пакетами, C#-константы ссылаются на разрешённые определения. Обоснование — межъязыковые плагины, расширение данных и ограничения, выявленные на36случаях.

Различены чистая смена единиц и преобразование, зависящее от текущих плотности/состава/состояния. Второе использует обычный механизм вычислительных операций модуля; инспектор может сохранять явно выбранный шаг без обязательного рисования отдельного блока. Это обсуждаемое развитие старого черновика, не молчаливое разрешение скрытой химии на ребре. Зафиксированы температура/перепад, статические и динамические условия, нелинейный API как отдельный показатель, запрет вывода смысла из безразмерности и границы прежнего микрозамера.

Документ содержит предлагаемый C#-синтаксис, который не выдаётся за уже существующий SDK. Библиотека, окончательный формат идентичности пакетов и весь контракт остаются неутверждёнными; новых численных замеров и реализации ядра не выполнялось. В продукт не внесены новые согласованные решения.

### Уточнение формата обсуждения и границы автоматики

Владелец отверг расширенный проект как не согласованную с ним картину и потребовал двигаться коротким диалогом от пользовательских сценариев. Напомнил о Unit / Definition / Value с условиями и затем отдельно подчеркнул, что прежнее обсуждение трёх сущностей не доказывает их правильность. Полезные результаты численных проверок сохраняются, но не подтверждают расширенную архитектуру.

Затем предложил автоматически конвертировать только однозначные случаи и не допускать неподдерживаемое соединение, пока пользователь не напишет преобразование; попросил оценить альтернативы. В существующее исследование добавлен короткий разбор официальных руководств Simulink, IDAES и COCO. Предварительно предложено сохранить строгую границу расчёта и разрешить выбирать готовое применимое преобразование, чтобы не требовать от каждого пользователя повторно писать известные методы. Выбор готового метода и собственный код не приравниваются к скрытой автоматической коррекции. Окончательное поведение не согласовано, требования не менялись.

### Согласовано: отдельная нода преобразования свойства

После примера пересчёта плотности владелец попросил альтернативы. Сравнены отдельная нода, преобразование в инспекторе связи, выдача нужного представления исходным плагином и общий пакет расчёта свойств. Владелец однозначно выбрал первый вариант. Зафиксированы OWN-12 и соответствующее поведение продукта: пользователь добавляет видимую ноду преобразования, готовую или свою; Gravia автоматически выполняет лишь обычные конверсии единиц при совместимости свойства/условий. Необходимый метод не исполняется скрыто в связи. Незавершённая передача не рассчитывается; точный способ рисования/показа такой связи пока не утверждён. Полный прежний проект SDK не принят, его статус уточнён. Реализация и новые тесты в этом уточнении не выполнялись.
