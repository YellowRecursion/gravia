# Проверка стека и границ реализации Gravia

Дата: 11 сентября 2026 года. Статус: сводка обсуждения, подтверждённые направления и исследование кандидатов; стек целиком не утверждён.

**Актуализация 20 октября 2026:** требования РНФ обязательны. Пакетный API обязателен, одиночные вызовы также входят в сценарий. Формулировки ниже об «условном» гранте и пересмотре batch считаются историческими; действует [текущий реестр требований](../docs/requirements.md).

Последующее изменение: при [исследовании CAPE-OPEN и сопряжения моделей](2026-09-11%20CAPE-OPEN%20и%20сопряжение%20моделей.md) Вадим предложил рассмотреть стандартный вызов вместе с пакетным расширением. Поэтому зафиксированное ниже историческое требование «только пакетный API» находится на пересмотре; необходимость эффективных пакетов сохраняется. Окончательный состав API ещё не выбран.

Повод: в обсуждении готовых компонентов возникла неточность о темах Ant Design. Вадим попросил повторно проверить весь стек по требованиям, прежде чем его фиксировать. Дополнительно сообщил языки существующих моделей и прислал подготовленную GPT подборку литературы.

Прочитаны `docs/product.md`, `docs/requirements.md` и оба материала в `researches`. Последние используются как исследовательский контекст, а не как утверждённая спецификация. Уточнения владельца внесены в продукт и реестр требований. Условные требования РНФ сохранены условными.

По просьбе Вадима эта же запись дополнена всеми основными выводами чата, включая последующие уточнения о переносе моделей и универсальном API. Продолжение находится в одном файле с аудитом, чтобы не разносить обсуждение одного вопроса по нескольким записям. Ниже разделены слова владельца, предложения ассистента и результаты проверок; обсуждение кандидата не означает его окончательное принятие.

Аргументы в пользу C# в обсуждении: знакомый владельцу язык, статическая типизация и инструменты сопровождения для предметного ядра и контрактов, возможность отделить управление приложением от вычислительных библиотек. Это аргументы удобства разработки и устройства платформы. Они не доказывают ускорения конкретной кинетики по сравнению с Python-кодом, который вызывает нативный решатель. Производительность модели и платформы следует измерять отдельно.

Ожидаемые основные задачи проекта: согласовать представления потоков между разными моделями; обеспечить проверяемый пакетный обмен; организовать длительные расчёты и быстрый инференс; связать оптимизацию с ограничениями и ошибками моделей; сохранить научную воспроизводимость; предоставить удобный редактор и анализ результатов. Выбор UI-библиотек покрывает только часть этих задач.

## Вывод для обсуждения

Сочетание C#/.NET для ядра, Electron + React + TypeScript для оболочки, Ant Design для стандартных компонентов, React Flow для схемы и Dockview для панелей соответствует обсуждённому направлению. Найденные ограничения не требуют переходить всей платформой на Python или привязывать её к Windows. Однако назвать эту комбинацию полностью проверенным стеком пока нельзя: есть ошибка деклараций зависимостей, не проверены упакованное приложение и реальные модели, остаются предметные архитектурные вопросы.

Предложение: сохранить эту комбинацию ведущим кандидатом; добавить библиотеку локализации собственных строк, например i18next/react-i18next. Python-библиотеки вычислений выбирать для конкретных модулей. Транспорт расчётов, хранилище проектов и математический решатель не считать выбранными вслед за GUI.

### Темы и языки: исправление неточностей

В Ant Design светлая тема является стандартной. Для тёмной есть `darkAlgorithm`, для плотного интерфейса — `compactAlgorithm`, который можно комбинировать с алгоритмом цвета. Переписывать готовые компоненты ради светлой/тёмной темы не требуется. Цвета собственных областей можно получать из токенов. Статические `message`, `notification` и `Modal` не следует считать автоматически подключёнными к контексту: использовать контекстные API через `App`/hooks. [Темизация Ant Design](https://ant.design/docs/react/customize-theme/).

RU/EN в Ant Design переводят стандартные компоненты, а не строки Gravia. Если используются даты, их библиотека также требует настройки локали. [Локализация Ant Design](https://ant.design/docs/react/i18n/). Для научных числовых полей нужны явные правила точки/запятой, экспоненциальной записи, округления, вставки и недопустимых значений. `InputNumber` предоставляет `decimalSeparator`, `parser` и `formatter`; наличие RU-локали не доказывает корректность этих сценариев. [InputNumber](https://ant.design/components/input-number/).

React Flow поддерживает `light`, `dark`, `system` и CSS-переменные. Текстовые подписи доступности настраиваются через `ariaLabelConfig`; собственные ноды переводит приложение. [Темы React Flow](https://reactflow.dev/learn/customization/theming), [подписи](https://reactflow.dev/api-reference/types/aria-label-config).

У Dockview есть готовые светлая и тёмная темы. В декларациях реально установленного `dockview-core@8.3.0` проверены `messages?: Partial<DockviewMessages>`, функции `closeTab`/`closeTabPlain` и сообщения о перемещении/закрытии панелей. Это точки подключения переводов, а не обещание полного встроенного русского каталога. Собственные меню и заголовки нужно переводить, не пересоздавая документ. [Темы Dockview](https://dockview.dev/docs/core/theming/).

Предлагается один источник настройки языка и темы в приложении, который конфигурирует все библиотеки. Автоматически единым визуальным стилем они не обладают. Нужны согласованные токены фона, границ, текста, выделения и состояний ошибки.

### Ant Design и объём собственного интерфейса

Ant Design остаётся обоснованным ведущим кандидатом: интерфейс Gravia предполагает много параметров, таблиц, деревьев и инспекторов. Это оценка соответствия задачам, не доказанное универсальное превосходство над Mantine. Заменять его после проверки причин не найдено.

Готовые компоненты сокращают работу над элементами управления. Редактор состава потока, сопоставление входов модели, настройка целей/ограничений, анализ результатов и сравнение сценариев остаются предметной работой. Универсальная генерация любых форм из метаданных не появляется от установки Ant.

Ant Table поддерживает виртуализацию; для неё `scroll.x` и `scroll.y` должны быть числами. Полноценные операции электронной таблицы не следует обещать как базовую возможность. Отдельный тяжёлый grid нужен только при подтверждённых требованиях к такому редактированию. [Table](https://ant.design/components/table/).

### React Flow и Dockview: бесплатные возможности и границы

Базовый React Flow имеет MIT-лицензию. Готовый пример undo/redo на сайте относится к Pro: это не встроенная история предметного документа. Можно реализовать собственную историю без покупки Pro. Автораскладка подключается отдельно; библиотека не обещает инженерную трассировку труб с обходом всех препятствий. [Undo/redo](https://reactflow.dev/examples/interaction/undo-redo), [раскладка](https://reactflow.dev/learn/layouting/layouting).

У Dockview основные docking-возможности, вкладки, floating/popout, сериализация и темы доступны бесплатно. Enterprise-функции включают, в частности, закреплённые/многострочные вкладки, auto-hide и историю расположения. Нельзя называть весь Dockview либо платным, либо безоговорочно бесплатным. Для обсуждённой базовой настройки панелей Enterprise не требуется. [Матрица лицензирования](https://dockview.dev/docs/overview/licence/).

История редактирования схемы, история расположения панелей и история расчётов — разные сущности. Сохранение Dockview JSON не сохраняет проект. Popout требует синхронизации окон, темы, состояния и закрытия; предлагается сначала проверить одно окно. Это предложение порядка реализации, а не новое продуктовое ограничение.

При 80 нодах нет оснований заранее заменять React Flow самописным canvas. Но сложность нод, число связей и частота обновлений важнее одного числа. Нужны стабильные компоненты/обработчики и ограниченные подписки на состояние; проверка простых 80 прямоугольников не подтверждает производительность редактора НПЗ. [Рекомендации React Flow](https://reactflow.dev/learn/advanced-use/performance).

### Electron и альтернативы

Electron предпочтителен здесь как кандидат благодаря одинаковой браузерной основе на разных ОС и прямой совместимости React-библиотек. Это не обещание минимального потребления памяти, малого установщика или отсутствия платформенных различий. [Документация Electron](https://www.electronjs.org/docs/latest/).

Tauri также способен запускать внешний .NET-процесс, но добавляет Rust-оболочку и разные системные WebView. Его стоит выбирать при подтверждённой ценности меньшей оболочки, сопоставив реальные сборки. Сам по себе C# не делает Tauri проще Electron. [Процессы Tauri](https://v2.tauri.app/concept/process-model/), [sidecar](https://v2.tauri.app/develop/sidecar/). WPF/WebView2 противоречит текущему предпочтению не связывать архитектуру с Windows.

Существенные уточнения к поставке Electron:

- Встроенный `autoUpdater` обслуживает Windows/macOS; для Linux документация рекомендует системный менеджер пакетов. Единого готового механизма обновления для трёх ОС обещать нельзя. Само автообновление пока не отдельное требование Gravia. [autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater).

[Forge](https://www.electronjs.org/docs/latest/tutorial/forge-overview), [Vite plugin](https://www.electronforge.io/config/plugins/vite).
- Исполняемые файлы .NET/Python и необходимые ресурсы нужно размещать так, чтобы ОС могла запускать их как обычные файлы, учитывая ограничения ASAR. `utilityProcess` не является универсальным запускателем произвольного .NET exe. [ASAR](https://www.electronjs.org/docs/latest/tutorial/asar-archives).
- Предметные вычисления не должны блокировать renderer или Electron main. Нужен узкий интерфейс preload к операциям приложения; renderer не должен получать произвольный запуск команд. Внешний процесс сам по себе не является песочницей недоверенных плагинов. [Безопасность Electron](https://www.electronjs.org/docs/latest/tutorial/security).

## Пакеты, оптимизация и производительность

Подтверждён только пакетный внешний расчёт. Рекомендуемые свойства контракта для согласования: версия схемы; идентификаторы строк или строго заданный порядок; единицы, размерности и типы массивов; отдельное описание параметров; ошибки уровня точки и пакета; отмена; явные сведения о модели и её версии. Отсутствующее свойство не равно нулю. Ошибочная точка не должна превращаться в успешный результат с нулями или незаметным NaN.

Числа в протоколе не локализуются. Выбор float64 для обычных научных числовых массивов — разумная исходная гипотеза, но не запрет на другие dtype у моделей. Нельзя неявно терять точность при переходе к JavaScript; большие целые идентификаторы можно передавать строками. Конкретная схема потоков и свойств ещё требует обсуждения.

Постоянно работающий процесс модели амортизирует импорт библиотек и загрузку весов. Но нельзя заявить, что JSON, gRPC, Arrow или shared memory уже доказанно достаточны/необходимы. Сначала нужно измерить реальный размер пакета, сериализацию, копирование и полный путь. Shared memory и внешнее автоматическое распараллеливание не включаются в обязательную архитектуру по умолчанию.

Для NSGA-II при начальной популяции P, числе потомков O и G поколениях, включая начальное, номинальное число оценок равно `P + (G − 1) × O`. Если O = P, это `P × G`. Фактическое число меняют правила остановки, кэш, дубликаты и другие настройки. Один вызов оптимизатора, оценка одной точки, пакет и один вызов ODE-правой части — разные счётчики.

Пример: P = O = 256, G = 200 дают 51 200 номинальных оценок и около 200 запросов пакетов, если популяция помещается в пакет и один запрос оценивает всю задачу. Граф из нескольких моделей добавляет вызовы его модулей; итерации рециклов также могут увеличивать объём работы. Нельзя передать все поколения одним пакетом: следующее зависит от результата предыдущего. В pymoo есть vectorized `Problem` и интерфейс ask/tell, пригодный для такой организации NSGA-II. [Problem](https://pymoo.org/problems/definition.html), [ask/tell](https://pymoo.org/algorithms/usage.html).

Сообщённые по памяти 40 000 точек/с дают идеализированные 6,4 мс на 256 точек только при сохранении этой пропускной способности на малом пакете. Это нельзя считать измерением. Если на каждый из 200 пакетов добавляется 1 с обмена, получится 200 с накладных расходов; если 1 мс — 0,2 с. Следовательно, «секунда несущественна» верно для некоторых медленных моделей, но не универсально для суррогатов. Ускорение 4 000 раз из слов владельца арифметически соответствует около 10 точкам/с у сравниваемого восьмиядерного расчёта, а не у всех кинетических моделей.

План измерений после появления реального адаптера: пакеты 1, 32, 256, 512, 1024; холодный и прогретый процесс; время модели отдельно от полного вызова; размеры входов/выходов; пропускная способность и задержки; CPU/GPU и память. Проверять ещё полный цикл оптимизации. Размеры — предложение эксперимента, а не обещание оптимальных значений.

GUI должен получать прогресс и нужные пользователю результаты с ограниченной частотой, а не каждое промежуточное значение всех популяций и нод. Подробные результаты можно сохранять отдельно. Это уменьшает связь отзывчивости интерфейса со скоростью модели.

## Научные и предметные пробелы, которые GUI-библиотеки не решают

ASP-01 требует данных, схемы превращений, идентификации и проверки кинетики. ASP-02 — воспроизводимого анализа компаундирования. ASP-03 — постановки оптимальных рецептур с ML и математическим программированием: подключение NSGA-II само по себе это требование не закрывает. ASP-04 — совместной работы реальных моделей, включая согласование составов, свойств и единиц.

Для предметного контракта остаются вопросы:

- Стационарные расчёты или также динамика; допустимы ли рециклы и кто обеспечивает сходимость. Редактор визуально допускает циклы, но это не вычислительный алгоритм.
- Материальные потоки и управляющие данные: типы портов, размерности, массовая/мольная основа состава, отсутствующие свойства, область допустимости модели. Нельзя автоматически приравнять одинаково названные поля разных моделей.
- Перевод представлений потоков: какие преобразования допустимы, где нужна отдельная модель свойств или явный адаптер. Конкретную химию не переносить в ядро.
- Как представляются дискретные/непрерывные переменные, ограничения, неуспешные расчёты и нарушения области применимости суррогата.
- Какие графики и экспорт нужны первому сценарию: Pareto, сходимость, сравнение кривых, таблицы. Библиотека научных графиков ещё не выбрана; Ant/React Flow не закрывают эту задачу.

Проектный файл должен сохранять предметную схему, параметры и ссылки/версии моделей. Для воспроизводимости расчёта нужны снимок входов, версии моделей и данных, настройки решателя/оптимизатора и seed, где он применим. Одинаковый seed не гарантирует побитовую идентичность GPU-вычислений. Сериализация библиотек GUI не заменяет этот формат.

Нужно различать предметный документ, расположение панелей, журнал расчётов и кэш. При открытии проекта с отсутствующим модулем нельзя молча подменять его другой версией. Формат, миграции, хранение больших массивов, autosave и экспорт пока открыты; SQLite/HDF5/Arrow или иной формат этой проверкой не выбирались.

## Предлагаемая проверка до объявления стека готовым

Документационный аудит завершён в пределах доступных источников; практическая готовность требует следующего небольшого сквозного эксперимента после согласования направления:

1. Упакованная оболочка запускает C#-ядро и один Python-адаптер из пути с пробелами/кириллицей; есть готовность, ошибка запуска, отмена и корректное завершение без оставшихся процессов.
2. Через один пакетный контракт проходят 1 и несколько точек, ошибка одной точки и ошибка всего процесса; результат соответствует конкретному снимку задания.
3. Около 80 предметных нод с характерными связями и панелями: перетаскивание, масштабирование и ввод остаются отзывчивыми во время расчёта. Число связей и измеримые критерии согласовать, не выдумывать как требования.
4. Четыре сочетания RU/EN × light/dark, числовой ввод, уведомления, таблицы и подписи доступности. Переключение сохраняет ввод и расчёт.
5. Закрытие/восстановление панели не уничтожает данные; сохранение/открытие проекта и undo работают независимо от расположения окон.
6. Проверка упакованного приложения на каждой заявляемой ОС; успех React-сборки на Windows недостаточен. Для риформинга после просмотра исходников можно выбрать перенос или адаптер; обязательная MATLAB-интеграция исключена из предварительных условий выбора стека по уточнению владельца ниже.

Ни один из этих ещё не выполненных пунктов не помечается пройденным. Их цель — проверить наиболее дорогие предположения до большой реализации, а не предсказать все будущие ошибки. Стек остаётся предметом обсуждения с владельцем.

## Уточнение после обсуждения результатов аудита

Вадим предложил не зацикливаться на сохранении исходного языка кинетической модели: перенос готового кода, в том числе с помощью LLM, может оказаться проще специальной интеграции. Это принимается как допустимое направление; предыдущая рекомендация обязательно проверить MATLAB-путь до фиксации стека была чрезмерно ограничительной.

Если доступны явные уравнения, параметры и обычный численный решатель, перенос может быть локальной инженерной задачей. Сложность конкретной модели пока не оценена без исходников. LLM может помочь перевести код, но сам перевод не доказывает сохранение численного поведения. Необходимо сопоставить результаты исходной и перенесённой реализаций на характерных входах и границах применимости с согласованными допусками. Настройки решателя, единицы, инициализация и обработка неуспешной сходимости входят в сравнение; повторная идентификация параметров не требуется автоматически только из-за смены языка.

Выбор стека платформы продолжается независимо от неизвестного языка модели изомеризации и предположительного MATLAB у риформинга. Предпочтение межъязыкового контракта сохраняется для расширяемости, но поддержка каждого существующего runtime не становится обязательной.

## Последнее уточнение: универсальный и удобный API модулей

Прямое указание Вадима: «Нам просто на сколько это возможно надо будет предоставить универсальный хороший API». Подтверждён приоритет качества общего контракта, а не обязательной поддержки конкретного языка каждой существующей модели.

Рабочее понимание этого направления: автор модуля выбирает язык, библиотеки и внутренний способ вычислений; Gravia получает описание модуля и работает с ним через одинаковый предметный контракт. Универсальность проверяется на разных реальных моделях НПЗ, а не объявляется по одной реализации. Это не задача заранее описать любой вычислительный процесс вне предметной области.

В ответ предложены следующие части API. Их точный состав, обязательность полей и сигнатуры ещё не согласованы:

| Часть | Предложенное содержание |
| --- | --- |
| Описание модели | Стабильный идентификатор, версия, входы и выходы, параметры, единицы и допустимые значения. |
| Вычисление | Только пакетная операция; однозначное соответствие результатов входным точкам; ошибки отдельных точек и всего пакета. Сам пакетный принцип уже прямо подтверждён владельцем. |
| Выполнение | Готовность модели, отмена и диагностика; прогресс там, где он полезен для длительных расчётов. Семантика отмены и частичных результатов требует спецификации. |
| Совместимость | Версия контракта и понятная проверка совместимости модуля с платформой. |
| Удобство разработки | Небольшие SDK для C# и Python, пример модуля и набор проверок соответствия контракту. SDK обслуживает обмен, автор сосредоточен на вычислениях. Это предложение ассистента, а не утверждённый состав поставки. |

Спецификация API и SDK решают разные задачи: первая задаёт обязательства сторон независимо от языка, второй уменьшает объём шаблонного кода. Конкретный транспорт, сериализация, способ запуска и программные интерфейсы SDK в этом чате не выбраны. Возможность прямого вызова C#-модулей внутри процесса также не считается автоматически принятой архитектурой.

Чтобы проверить, что контракт не подстроен под одну модель, предложено применить его к нескольким различающимся реальным моделям, включая медленную кинетику и быстрый суррогат. Количество моделей, критерии готовности SDK и срок такой проверки ещё не заданы.

Итоговый статус после просьбы сохранить выводы: документирована общая линия обсуждения и её основания. Не принимались новые решения о стеке или деталях API только из-за внесения этой записи в логбук.

## 12 сентября: подключение согласованного веб-стека

Статус: выполнено по прямому запросу владельца «Все библиотеки можешь к вебу
подключить», после обсуждения QoL-инструментов. Предыдущее ограничение на установку
фронтовых библиотек снято. Ограничение на первый экран сохраняется. Интерфейс
владелец проверяет сам; Vitest/Testing Library/Playwright остаются отложенными.

Сценарий этого изменения: Run Gravia.Host в Rider собирает веб и открывает пустое
окно Gravia Lab. Программа пока ничего предметного не вычисляет. Проверяем загрузку
React, изоляцию renderer и совместное завершение процессов, не дизайн или UX.

Подключены React/React DOM, TypeScript/Vite, Ant Design/иконки, Dockview, React Flow,
i18next/react-i18next, TanStack Query, Zustand, ESLint/Prettier и Orval. Точные версии
и lockfile находятся в [Desktop](../src/Gravia.Desktop/package.json). Корневые
провайдеры Ant/Query и RU/EN инициализированы. Dockview, React Flow, иконки и Zustand
доступны без создания демонстрационных панелей, нод или пустых хранилищ.

Простые альтернативы остаются допустимыми: локальное состояние React вместо
Zustand; ручной fetch вместо генератора для одиночного запроса. Orval подключён
для будущего растущего C# API, чтобы не поддерживать DTO/клиент вручную. Он использует
fetch и Query, без дополнительного Axios. Генерация отделена от сборки, требует
реального OpenAPI через GRAVIA_OPENAPI. Фиктивного API не создавали; вызов без
контракта проверен и заканчивается явным сообщением. Сами HTTP-ошибки и отмену
нужно согласовать и проверить с первым API, они не решаются наличием генератора.

Host собирает Vite и копирует только dist в Desktop/wwwroot; C# Domain/Application
не зависят от веб-пакетов. Electron по-прежнему отвечает только за окно. В renderer
нет Node/preload/IPC. CSP разрешает same-origin скрипты и запросы, inline-стили нужны
Ant/React Flow; inline-JavaScript и eval не разрешены. Самостоятельный Vite dev
доступен для просмотра веба; Run Host использует production-сборку без отдельного
dev-процесса. Предметные слои фронтенда этим изменением не выбраны.

Совместимость проверена в Windows, Node 24.12.0/npm 11.6.2/.NET SDK 10.0.302:

- TypeScript 7.0.2 не входит в peer-диапазон typescript-eslint 8.70.0 (<6.1.0).
  Закреплён совместимый стабильный TypeScript 6.0.3. Peer-проверка не обходилась.
- strict и типизированный lint включены. При skipLibCheck:false повторились две
  TS2430 из предыдущего эксперимента Ant; проверка инструментов также выявила
  недостающие типы debug/picomatch/faker и WebAssembly в декларациях зависимостей
  Orval. Включён skipLibCheck:true — известный обход внешних .d.ts, не исправление
  зависимостей и не отключение проверки собственного кода или обращений к API.
- npm install и повторный npm ci в сборке Host прошли со strict-peer-deps.
- npm run check: lint, форматирование, типы, Vite и 10 существующих Node-тестов прошли.
- npm audit, включая dev-зависимости: 0 найденных уязвимостей на момент проверки.
- Debug/Release .NET build: 0 предупреждений и ошибок. Все 76 .NET-тестов прошли.
- npm run smoke: оба реальных Windows-сценария прошли; React main смонтирован,
  окно пустое, ошибок console renderer нет, Node недоступен. При закрытии окна и
  принудительном завершении только Host завершаются все 4 наблюдаемых Electron PID.
- Первая проверка HTTP обнаружила ошибку MSBuild metadata batching при копировании
  ресурсов. Исправлена отдельным набором _DesktopWebAsset; build-выход очищен и
  пересобран. HTTP-тест проверяет доступность JS/CSS и недоступность конфигурации и
  исходников; smoke теперь берёт именно результат сборки Host, а не исходный dist.

Размер этого пустого renderer: JS 400.74 kB (gzip 130.40), CSS 145.12 kB (gzip 13.65).
Это не оценка готового редактора или его производительности. Linux/macOS, полноценная
поставка Electron, реальный API и предметные экраны не проверялись в этом изменении.
